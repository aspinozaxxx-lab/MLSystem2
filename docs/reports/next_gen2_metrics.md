# Проверка низких метрик next-gen2

Проверка 7 сентября 2026 года для `Переувлажнения/test_ml`, запуск
`48b6b39f-8d60-4ee0-ae96-3aac13150601`, MLflow `57dfaeeb90724e66a2254fb8b6bbdf37`.
Версия данных: `managed:1:git:757b1fad03ddc311a24088f2c29c246f0378d810`.

Этот отчёт описывает исторический запуск с разбиением ноутбука. Последующая
[проверка пространственной независимости](next_gen2_tile_split.md) обнаружила пересечение
соседних train/validation окон; новые запуски исключают пересекающиеся обучающие тайлы и выбирают best по F1.

## Данные и независимый расчёт

В запуск поступили 14 сцен Иркутска, 17 569 train-тайлов и 5 856 validation-тайлов.
Для 42 окон всех сцен, включая наиболее заполненные положительной разметкой,
входные массивы совпали с прямым чтением TIFF, а маски — с независимой растеризацией
положительных GeoJSON без пространственного индекса приложения. Каналы, CRS и размеры проверены.

Объект занимает 0,07645% обучающих пикселей и 0,07352% validation-пикселей.
Только 390 train-тайлов превышают порог положительной площади 0,001.
Sampler ноутбука с весами 15/1 повышает ожидаемую долю таких тайлов в batch до 25,4%.
Веса CrossEntropy `[0.001529, 1.998471]` совпали с весами в чекпойнте: относительное
усиление класса объекта примерно 1307 раз. В validation 1273 полностью нулевых тайла;
они сохраняются по правилам исходного ноутбука.

Лучший по loss чекпойнт эпохи 4 зафиксирован отдельной копией до окончания обучения.
SHA-256: `ce262dd5e0d15e4aadc815171fff8452e835475f23cf4a7cfa1be8366df37fe2`.
Независимый проход по всем validation-тайлам при штатном batch 32 дал validation loss
`0.04634201039605942`; в обучении записано `0.04634200992276434`.
F1 пересчитан по потоковой матрице ошибок NumPy, отдельно от функций метрик приложения:
`0.10458534911969782`, точно как в MLflow. Получены TP = 1 095 102, FP = 18 718 140,
FN = 33 442. Ошибки формулы F1 или подмены входных тайлов проверка не обнаружила.

При пороге 0,5 полнота выбранного чекпойнта около 97,0%, точность — 5,53%.
Сеть выделяет около 1,29% всех validation-пикселей при размеченных 0,0735%:
примерно 18,7 млн ложноположительных пикселей против 1,10 млн истинноположительных.
Это избыток предсказаний относительно имеющейся разметки; проверка не оценивает полноту
самой экспертной разметки вне отмеченных объектов.

## Почему сохранённая сеть хуже по F1, чем поздние эпохи

| Эпоха | Validation loss | F1 при 0,5 |
|---|---:|---:|
| 4, выбранный best | 0,04634 | 0,10459 |
| 10 | 0,06939 | 0,35960 |
| 12 | 0,12025 | 0,47367 |
| 13, последняя | выше минимума эпохи 4 | 0,51839 |

В исходном train-ноутбуке выбор весов, scheduler и early stopping используют validation loss,
а не F1. Next-gen2 воспроизводит это правило. После эпохи 4 loss не улучшался девять эпох;
поэтому запуск штатно завершился на эпохе 13, хотя верхний предел был установлен в 100.
MLflow и интерфейс показывают F1 именно выбранного best, а не максимум F1 другого чекпойнта.

Таким образом, низкое качество сохранённых весов связано с расхождением критериев:
минимальный взвешенный CrossEntropy здесь не выбирает максимальный F1. Сильное усиление
редкого класса совместно с oversampling согласуется с наблюдаемой высокой полнотой и
избыточными срабатываниями. На фиксированных весах эпохи 4 диагностический порог 0,99
поднимает F1 примерно до 0,338; это только проверка, рабочий порог не изменён.

Выбор checkpoint по F1, пересмотр весов или подбор порога изменят алгоритм исходного
ноутбука. В ходе этой проверки такие изменения не вносились. Ускорение передачи данных
и проверки градиентов не меняет loss, sampler, split, порог validation и правила выбора checkpoint.

## Отличия псевдоразметки от eval-ноутбука

Дополнительная проверка `eval_full_pipeline_заболачивание.ipynb` обнаружила отдельную ошибку
интеграции инференса. В завершённом задании `938321d1-76c9-4b59-9e34-fc7677353bfa`
использовался порог checkpoint `0.5`. Во втором ноутбуке задан `theshold = 0.9`.
Кроме значения порога различался порядок объединения окон.

| Параметр | Прежняя псевдоразметка | Исправленная ветка next-gen2 |
|---|---|---|
| Бинаризация | Порог 0,5 для каждого тайла | Строго `> 0.9` после усреднения вероятностей |
| Перекрытия | Объединение бинарных масок | Гауссовы веса с центром `patch_size/2`, sigma `patch_size/4` |
| Края | Дополненные окна | Только полные окна; непокрытые края нулевые |
| Nodata | Маскирование и пропуск пустых окон | Исходные значения TIFF, как в ноутбуке |
| Batch | Из настроек обучения | 32 по выбору пользователя для серверной GPU |
| Постобработка | Автоматически по числу сцен | Без автоматической морфологии и упрощения |

В обеих реализациях вероятность положительного класса вычислялась корректно:
`sigmoid(z1-z0)` эквивалентен `softmax([z0,z1])[:,1]`. Для прямого сопоставления новая
ветка использует две исходные головы и softmax. Диагностика обучения остаётся на пороге
0,5, а псевдоразметка и независимая контрольная оценка используют профиль eval-ноутбука.
Явные пользовательские настройки inference-шаблона продолжают применяться.

Эталонный eval-ноутбук сохранён в `tests/fixtures/next_gen2_eval.ipynb` с SHA-256
`0e9e2abac0a2390737419da01c7a274ed2f1eea8ccf204e6d26a272b07b0507b`.
Синтетические TIFF проверяют перекрытия, нулевые окна, маску TIFF, непокрытый край и снимок
меньше окна; вероятности и маски побитово совпали с выполненными функциями исходного ноутбука.
Проверка всего пути до GeoJSON и контрольных TP/FP/FN также пройдена.
На серверной CUDA и прежних весах эпохи 4 сравнили реальный фрагмент SCN05 размером
1391×1277, 12 окон. Для каждого batch 1, 8 и 32 различие вероятностей и масок между
реализациями равно нулю. Между самими размерами batch возможны различия округления CUDA;
рабочий инференс по выбору пользователя использует batch 32.
