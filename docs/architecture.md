# Архитектура

MLSystem 2.0 — простая система командной строки с явными границами модулей.
Обучение и основной CLI-инференс используют локальные подготовленные изображения. AOI-инференс QGIS
дополнительно поддерживает независимый выбор локального или разрешённого внешнего источника снимков.
Основной принцип реализации системы и построения архитектуры - необходимо и достаточно. Это касается документов, интефейсов, модулей, функционала и всего остального что есть в проекте.

## Ахритекутурные правила обязательные к соблюдению зафиксированы тут: 
- Данный документ - главный источник правды для всего проекта. 
- Архитекутурные правила в архитектурных документах должны абсолютно соблюдаться
- Любые изменения в архитектурных документах - согласуются.
- В репозитории не должно быть функционала повторяющиего функционал модулей.
- Недопустимо оставлять deprecated wrapper в репозитории.
- Новые модули и код не принадлежащий к какому либо модулю создавать запрещено без отдельного согласования

## Статистика использования Гровики

Сбор и отчёты находятся в Яндекс Метрике; собственных отчётов и таблиц аналитики в Гровике нет.
`training_ui_api` выдаёт вошедшему пользователю номер счётчика из `MLSYSTEM2_METRICA_COUNTER_ID`
и стабильный `UserID`: первые 32 шестнадцатеричных символа HMAC-SHA256 канонического логина
с ключом сессии и префиксом `grovika-usage:`. Логин не передаётся в параметрах аналитики.
Frontend подключает счётчик только после авторизации, включает Вебвизор и карту кликов.
Для SPA автоматические просмотры отключены: принятый переход и переключение типа шаблонов
отправляют один `hit` с названием и адресом категории страницы, без ключей датасетов и query.
При выходе или смене аккаунта счётчик останавливается, очередь старой сессии очищается.

Явные операции HTTP получают `X-Grovika-Action` с кодом функции и `X-Grovika-User` с ID сессии;
запоздавший ответ другой сессии не учитывается. Общий клиент
отправляет параметры события и цель `grovika_<код>` с функцией, исходом и `UserID`.
Чтение API, фоновые POST просмотра и сравнения, сверка F1 и автосохранение черновиков
в этот список не входят. Сбой счётчика не блокирует работу приложения. Вебвизор отдельно
записывает взаимодействие с интерфейсом. Настройка отчётов и связь ID с аккаунтами описаны
в `docs/runbooks/grovika_usage_metrica.md`.

## Новости пользовательского функционала

Главная страница Гровики показывает раздел «Новости» вместо таблицы последних событий обучения.
Ссылки «Grafana» и «Снимки» представлены кнопками с иконками справа от заголовка
«Рабочая панель», у правого края колонки. На широком экране кнопки имеют подписи и обычную ширину,
в компактной версии — только иконки. Карточек MLflow и Mapflow на главной нет.
Статьи хранятся с кодом frontend в `frontend/src/News.tsx` и публикуются вместе с изменением функционала;
изображения — в `frontend/public/news/`. Новость имеет дату, постоянный адрес `#/news/<slug>`, краткое
описание на русском языке. Новая существенная возможность требует большой статьи: польза, расположение
в интерфейсе, порядок использования и обязательная подходящая иллюстрация — реальный скриншот или явно
обозначенная схема с альтернативным текстом, без секретов и персональных данных. Мелкие доработки,
улучшения и исправления публикуются компактным списком `updates`: по одной строке на изменение, без
большой статьи и обязательной картинки. Список виден целиком в своей карточке и имеет постоянный адрес.
На главной две независимые плашки фильтра: «Фичи» показывают большие статьи, «Исправления» — записи
`updates`. По умолчанию включены только «Фичи»; можно включить обе категории или выключить обе.
Состояние хранится в компоненте списка, фильтры не ограничивают открытие новости по постоянному адресу.
Внутренние технические изменения без изменения пользовательского поведения не требуют новости.
Новости выходят вместе с кодом. История публикаций и их адреса сохраняются. Новые
таблицы, HTTP endpoints и редактор публикаций не вводятся; события результатов остаются на странице результатов.

Основное приложение обучения:

```bash

```

Основное приложение инференса:

```bash

```

Веб-интерфейс обучения:

```bash
mlsystem2-training-ui-api
mlsystem2-training-ui-worker
python frontend/build.py
```

`training_ui_api` — отдельный модуль MLSystem2 и единственная серверная точка доступа frontend к
данным UI обучения. Frontend не обращается к Postgres напрямую. Управляемый каталог классов и
датасетов, шаблоны, очереди, custom datasets и результаты хранятся в отдельной Postgres БД/схеме. Инфраструктура
Postgres разворачивается вручную по runbook и не входит в CI/CD. UI-сервис может читать публичные
данные MLflow для списка experiments, best checkpoint и скачивания checkpoint, но не открывает
training runs и не пишет MLflow-метрики; запись метрик выполняет `train_pipeline`.
Подготовленные снимки остаются обычными файлами в `/data/mlsystem2/prepared_images`. Существующий
обратный прокси публикует этот каталог только для авторизованного просмотра и скачивания по HTTP из
подключения только для чтения; отдельная объектная копия снимков в MinIO не создаётся. MinIO
сохраняется как внутреннее хранилище артефактов MLflow.

Каталог `dataset_classes` → `datasets` является источником истины для названий, основной метрики,
основного датасета, типа снимков класса и источника разметки. Тип `kanopus` использует строго четыре канала
`RED, GRN, BLU, NIR` из `/data/mlsystem2/prepared_images/kanopus`, тип `ortho` — строго три канала
`RED, GRN, BLU` из `/data/mlsystem2/prepared_images/orto`. Синхронизация с MLMarkup при
старте и при изменении дешёвой ревизии папок class/dataset только добавляет неизвестные папки и вычисляет файловую версию: она не удаляет
историю и не перезаписывает ручные настройки. Пути источников хранятся относительно корня MLMarkup. Первый
импорт сохраняет исторические `dataset_key`; сущности, обнаруженные позднее, получают независимые UUID.
Удаление датасета мягко архивирует его строку в Postgres и исключает её из активного каталога, но не удаляет
задания, результаты и данные MLflow.
Название в классе и пара `source_type/source_path` уникальны только среди активных датасетов:
частичные уникальные индексы `datasets` ограничены `deleted_at IS NULL`. Удалённые строки сохраняют
свои ключи, названия, пути и связи истории, но не резервируют название или путь для нового набора.
Явное повторное создание получает новый ключ, а не восстанавливает прежнюю строку. Синхронизация
каталога по-прежнему не воскрешает удалённые наборы из ещё не переключённого live-релиза.
Переименование меняет название в каталоге, не перемещая источник. Если при копировании под свободным
названием одноимённая физическая папка принадлежит активному переименованному набору, редактор
выбирает свободную соседнюю папку с числовым суффиксом, сохраняя запрошенное название в каталоге.
Активный набор и его файлы никогда не перезаписываются; существующая папка без активного владельца
также не затирается автоматически.

MLMarkup поддерживает legacy и per-image форматы. Legacy сохраняет `TXT + positive GeoJSON + optional
hard-negative GeoJSON`, включая legacy multiclass. Per-image не содержит TXT: каждому TIFF соответствует файл
разметки `<родительская_папка>_<имя_TIFF_без_расширения>.geojson` и companion-файл фактической valid-data mask
`<родительская_папка>_<имя_TIFF_без_расширения>_footprint.geojson`. Footprint хранится в CRS TIFF, не является
разметкой и не участвует в подсчёте сцен, объектов или supervision. Исторические per-image наборы без companion-файла
остаются читаемыми, но редактор создаёт пару для каждого нового снимка и пересборки. Binary per-image сохраняет
прежнюю совместимость ролей. Multiclass per-image определяется файлом `.mlsystem2-dataset.json`: manifest хранит
версию схемы, классы с ID/slug/color/priority, source-ревизии, build ID и baseline-хеши, а каждый GeoJSON строго
повторяет schema/task/classes. Positive feature имеет `_mlsystem2_role=positive` и известный `_mlsystem2_class`.
В обычном multiclass-наборе hard negative содержит только роль; в материализации управляемого датасета он может
дополнительно содержать `_mlsystem2_class` исходного типа, для которого является отрицательным примером. ID и
origin-key стабильны. Коллизии формулы, несовпадающая схема,
неоднозначные и отсутствующие TIFF делают датасет невалидным. Пустой управляемый per-image датасет доступен
редактору, но не запуску обучения.

### Снимки и версии разметки в датасетах

Снимок — сущность `annotation_images` с UUID и уникальной парой «тип съёмки, путь TIFF относительно
корня этого типа». Файл TIFF не копируется. В `annotation_versions` хранятся UUID снимка и класса,
название, GeoJSON, номер редактирования и признак удаления. Это редактируемые варианты разметки,
а не ветки или коммиты Git. `dataset_annotations` выбирает одну версию снимка для каждого обычного
per-image датасета. Выбор другого снимка или другого класса запрещён. Удаление снимка из датасета
снимает только эту связь; версии и связи других датасетов сохраняются.

Источник истины для вариантов и связей — БД Гровики. Существующие файлы при первом открытии снимка
импортируются без изменения геометрии: каждый прежний датасет получает отдельную версию, даже при
совпадающих файлах. Копирование датасета сохраняет независимость его разметки. Явный выбор существующей
версии в другом датасете создаёт совместное использование без изменения её исходной геометрии:
обрезанное по footprint представление редактора само по себе не считается правкой версии.
Новая версия копирует текущий черновик либо
начинается пустой. Неиспользуемая версия остаётся доступной у снимка; удаление версии требует другую
сохраняемую версию для всех её активных использований. Исторические данные обучения не переписываются.
Внешнее изменение уже импортированного GeoJSON распознаётся по хешу и импортируется как отдельная
версия этого датасета: оно не перезаписывает общую версию остальных наборов.

Список снимков показывает число вариантов кликабельной плашкой. Она открывает закрывающееся по
клику снаружи или Escape меню карточек: название, даты создания и изменения, использующие датасеты
(включая зависимые управляемые наборы), переключение кликом, корзинка удаления с заменой и создание
версии внизу. Отдельной панели выбора над картой нет. У виртуального
multiclass-набора выбор выполняется в исходном датасете соответствующего класса. Создание, переключение,
изменение нескольких версий и замена удаляемых входят в один личный черновик `dataset_editor_drafts.annotation_versions`;
работают автосохранение, отмена одного действия и общая отмена. До публикации другие пользователи,
обучение и Git видят прежние варианты. Ревизия каталога фиксирует варианты и связи; конкурентная
публикация возвращает 409, а существующие чужие черновики не заменяются.

Публикация одной общей версии собирает одинаковые GeoJSON во всех использующих её обычных датасетах,
сохраняя остальные файлы и footprint. В Git публикуются только актуальные собранные датасеты и служебный
`.mlsystem2-annotation-selections.json` с выбранными UUID и ревизиями, без внутреннего каталога всех
вариантов. Для этого конкретного служебного файла публикация явно обходит правила игнорирования Git;
остальные файлы и каталоги принудительно не добавляются. Смена выбора меняет этот файл даже при одинаковой геометрии; штатная автоматизация получает
новую файловую версию. Изменения через управляемый редактор и пересборку проходят тот же механизм
распространения. Worker копирует сведения о выборе вместе с GeoJSON в неизменяемый snapshot задания.

Согласование выполняется под существующим межпроцессным write lock. Перед записью файлов журнал
`annotation_publications` сохраняет намерение и ожидаемые ревизии; Git-коммит получает UUID операции
в trailer. После подтверждения push применяются изменения сущностей БД. Ошибка отправки сохраняет
черновики; неопределённый исход не считается отменой. Перед следующим обращением к каталогу версий
или публикацией незавершённая операция проверяется в remote: принятый коммит завершает БД
идемпотентно, локальный неотправленный коммит повторяет штатный push, отсутствие обоих отменяет
намерение и восстанавливает затронутые пути. Git не управляет сущностями версий; журнал закрывает
разрыв между внешним репозиторием и БД. Резервная копия вариантов должна включать UI-БД.

Каталог версий возвращает `updated_at` из БД в UTC. Редактор показывает его в локальном времени
рядом с выбранной версией и в списках выбора/замены. Дата меняется при публикации правок, но не при
сохранении черновика или выборе версии другим датасетом. У импортированных прежних файлов это дата
начала учёта версии в Гровике, не восстановленная историческая дата создания исходной разметки;
интерфейс явно объясняет это. Новому неопубликованному варианту дата публикации не приписывается.

Прежние файлы без ID получают стабильные виртуальные идентификаторы при чтении: они не меняют
содержимое файла или ревизию версии и сохраняются в GeoJSON только при следующей публикации.
История полигона относится к его стабильному ID в конкретном варианте разметки. Таблица
`annotation_feature_events` хранит неизменяемые состояния геометрии, свойства, CRS, действие и автора;
событие связано с `annotation_publications`. Запись происходит только после подтверждения push,
в одной транзакции с завершением журнала и применением плана версий. Черновики, отмены, чтение,
переключение варианта и публикация без изменения объекта не создают событий. Повторное завершение
публикации идемпотентно. Прежний контур перед первой учитываемой правкой сохраняется как baseline:
его неизвестные автор и дата не выдумываются. Новый полигон получает автора и дату первой публикации.
Истории независимых вариантов не смешиваются; управляемый редактор читает историю в исходном
варианте соответствующего класса. HTTP-чтение истории проверяет класс, снимок и вариант. При выборе
полигона frontend показывает автора и дату, список опубликованных изменений и независимый
слой просмотра «до/после». Исторический просмотр не меняет черновик и не может попасть в публикацию.
Добавление таблицы выполняется штатной миграцией `20261019_0036`; веса, задания и TIFF не изменяются.

Разовое обслуживающее объединение выполняет приватная команда `training_ui_api._annotation_deduplication`:
предварительный отчёт не импортирует файлы и не меняет БД, применение повторно проверяет его отпечаток
под блокировкой публикации. Совпадение означает точные отдельные полигоны, отверстия, кратности, CRS,
роли и классы; порядок объектов/колец и произвольные атрибуты не учитываются. Невалидные и пустые
геометрии не объединяются. Приоритет сохраняемого варианта — использование в `main`, затем число
активных использований, ранняя дата создания записи и UUID. Название, данные и дата сохраняемой версии
не меняются. Каталоги снимков/классов с личными черновиками, включая зависимые управляемые наборы,
пропускаются. Независимое копирование и обычный импорт по-прежнему не объединяют версии автоматически.
Операция использует тот же журнал и мягкое удаление с заменой; Git сохраняет материализацию каждого
датасета. Журнал хранит соответствия UUID и точные итоговые ревизии обычных/зависимых датасетов,
исключённые из автоматического обучения и псевдоразметки. До завершения операции автозапуск для её
датасетов отложен; синхронизация автоматизации согласована с блокировкой разметок. Другие ревизии,
правила, текущие задания и история результатов не меняются. Схема БД и HTTP API не расширяются.

Управляемый датасет — виртуальный multiclass-набор, состав которого хранится в Postgres как упорядоченные
ссылки на несколько обычных binary per-image датасетов. У каждого источника свой тип объекта, цвет и приоритет;
пока допускается не более одного источника от класса. Отдельной папки управляемого датасета в MLMarkup нет.
Каждый класс каталога имеет уникальное редактируемое `technical_name`. Публичный `slug` типа управляемого
multiclass-датасета всегда равен `technical_name` исходного класса; числовой `id=1..N` остаётся внутренним
номером выходного канала модели. Смена технического имени не меняет веса или порядок каналов: схемы исторических
результатов, метрик и псевдоразметок канонизируются, а старый checkpoint получает актуальную схему при запуске
и экспорте без переобучения.
Редактор классов позволяет изменить название, набор источников, их приоритеты и цвета без смены ключа датасета
и потери истории. Изменение состава или схемы блокируется, пока у любого пользователя есть неопубликованный
черновик этого управляемого датасета. При изменении только приоритета или цвета ID и slug существующих типов
сохраняются; при добавлении или удалении источника ID снова приводятся к последовательности `1..N`.
Для редактора и неизменяемого snapshot обучения он детерминированно материализуется в служебный cache из
актуальных исходных GeoJSON; версия включает состав, приоритеты, явно добавленные сцены и файловые версии всех
источников. Поэтому публикация обычного источника автоматически меняет версию зависимого управляемого датасета
и обрабатывается его действующим правилом автоматизации.
HTTP-процесс никогда не строит этот cache: чтение каталога только вычисляет требуемую версию, возвращает
последнюю готовую сводку и идемпотентно создаёт файловый запрос. Отдельный worker выполняет не более одной
материализации одновременно; атомарный межпроцессный lock исключает параллельную сборку одной версии. До готовности
нового cache обучение остаётся в очереди, редактор показывает состояние пересборки, а остальные страницы продолжают
работать. В готовом cache постоянная сводка хранит число снимков и объектов, поэтому повторное чтение каталога не
разбирает все GeoJSON. Companion-footprint копируется из исходного датасета и рассчитывается по TIFF только при его
отсутствии. После успешной сборки сохраняются текущая и одна предыдущая версии cache; ошибки повторяются worker с
ограниченной экспоненциальной задержкой.

Контрольная оценка сети управляемого датасета строится не по отдельной тестовой разметке составного класса,
а по основным тестовым разметкам всех его исходных классов. На разметке каждого источника оценивается только
соответствующий выходной канал multiclass-сети; остальные каналы не считаются фоном этого класса. Для каждого
типа независимо сохраняются pixel/object precision, recall и F1. Общий F1 управляемой сети — невзвешенное
арифметическое среднее поклассовых F1, поэтому размер одной выборки не увеличивает её вклад. Связка
`класс → sample_id → revision → enabled tiles` входит в сигнатуру оценки: смена основной выборки или её состава
делает результат устаревшим. После первого полного расчёта изменение одного исходного класса ставит inference-job
только для его канала, объединяет новый результат с сохранёнными метриками остальных классов и пересчитывает
среднее; при отсутствии полной сохранённой структуры выполняется составной расчёт всех каналов. Обычный binary-датасет
по-прежнему оценивается на одной основной выборке своего класса.

Снимок, добавленный через управляемый редактор без объектов, хранится только в `managed_dataset_scenes` и не
создаёт пустые GeoJSON в источниках. При публикации positive снимок и объект записываются только в источник
выбранного типа; для hard negative выбирается один, несколько или все исходные датасеты. Материализация помечает
каждую такую геометрию типом её источника, а одинаковые копии из всех источников схлопывает в общий отрицательный
пример. Удаление снимка остаётся черновым действием и при публикации удаляет его явное членство и связанные
исходные файлы. Все source-изменения одной публикации образуют один Git-коммит пользователя. Удалить обычный
датасет, пока на него ссылается активный управляемый, нельзя; удаление самого управляемого датасета мягко архивирует
только строки БД и не затрагивает источники.
Ревизия алгоритма материализации входит только в ключ локального кэша: обновление системной семантики пересобирает
виртуальные GeoJSON, но само по себе не меняет продуктовую версию датасета и не запускает массовое автообучение.

Одноразовая миграция исторических наборов «Переувлажнения и заболачивания/main» и «Опустынивание и ветровая
эрозия/main» сохраняет `dataset_key`, историю jobs, checkpoint, MLflow и псевдоразметок, а их materialized-папки
заменяет ссылками на актуальные базовые источники. Полнота перехода проверяется относительно последнего полного
Git-снимка combined-папок, а не только относительно ручных изменений после первой сборки: отсутствующая
положительная геометрия добавляется в соответствующий источник как разность с его текущей разметкой, поэтому
более поздние правки источника не удаляются. Исторические и более поздние hard negative объединяются,
дедуплицируются и с одним origin-key записываются во все источники. Восстановительная операция идемпотентна,
проверяет покрытие каждой исторической геометрии и после успешного запуска должна давать пустой dry-run.
Миграция и восстановление выполняются только после резервной копии и при пустой очереди. На время применения
автоматизация выключается. При работе из серверного клона её прежнее состояние восстанавливается после
успешных Git-публикации и транзакции БД; в архивном режиме она остаётся выключенной до подтверждения нового
MLMarkup release-marker. Это исключает обучение на переходной версии. Существующие успешные результаты засчитываются новой
файловой версии; для базовых источников обновляется только псевдоразметка, переобучение не запускается.
Рабочий MLMarkup после завершающей миграции содержит только per-image источники с обычными именами
`main`, `test`, `strict` и другими без суффикса `_new`. Строки прежних legacy-источников мягко архивируются,
а их jobs, результаты обучения, псевдоразметки, тестовые разметки и ссылки на MLflow переводятся на
соответствующий действующий per-image датасет; сами исторические MLflow runs и checkpoint не переписываются.
Чтение legacy остаётся частью совместимого контракта для архивных и внешних наборов.

Размеченные зоны хранятся в тех же per-image GeoJSON как Polygon/MultiPolygon с ролью
`annotation_zone` и стабильным ID. Это служебная территория, не класс модели и не объект метрик.
В управляемом редакторе зона относится к исходному классу либо ко всем классам; общая зона публикуется
с единым origin-key во все источники и схлопывается при материализации. Доступное покрытие multiclass —
пересечение объединений зон каждого класса; отсутствие зон класса означает весь снимок. Каждая исходная
зона после ограничения общим покрытием становится отдельной виртуальной сценой. Пересекающиеся зоны
не объединяются. Нет зон — прежний полный снимок; пустое пересечение никогда не означает полный снимок.
`dataset_preparing` сохраняет в PreparedScene исходный scene ID, zone ID, геометрию и пиксельное окно.
`tile_preparation` читает исходный TIFF по окнам без новых растров: весь вход, включая контекст, за зоной
становится nodata. Маска зоны пересекается с фактической raster mask/alpha; пустые окна исключаются,
краевые и маленькие зоны дополняются nodata. Аугментации синхронно преобразуют valid mask с постоянным
заполнением; после них nodata восстанавливается. Во всех профилях зональные valid_pixels исключены из loss,
статистики, sampling и метрик. Граница зоны не является целью boundary head object f1.
Поснимочные split удерживают зоны одного TIFF вместе; оконный split next-gen2 сохраняется. Геометрия зон
и связь с TIFF входят в артефакты и идентичность данных. Инференс и псевдоразметка работают по полным
исходным снимкам. Новые эталонные тестовые тайлы целиком находятся внутри одной допустимой зоны.
Редактор предоставляет отдельный инструмент и видимость зон в обычном и полноэкранном режиме, считает
зоны отдельно и показывает «Используется весь снимок» при их отсутствии. При завершении рисования
и изменения зоны, positive или hard negative редактор автоматически пересекает полигон с полезным
контуром TIFF, включая прозрачность, отверстия и раздельные части footprint; сохраняются ID, роль,
тип и свойства. Сервер повторяет обрезку при сохранении и публикации, включая управляемые источники.
Полностью внешний новый полигон не добавляется; полностью внешняя геометрическая правка отменяется
с пояснением. Сервер не позволяет обрезке удалить все поступившие зоны и молча вернуть весь снимок.
Прежняя зона, целиком лежащая вне снимка, остаётся видимой с предупреждением: её нужно перенести
или явно удалить. Чтение редактора не должно незаметно стирать последнюю зону из будущей публикации.
Подготовка сохраняет дополнительную защитную обрезку для исторических и внешних файлов: внешняя
территория не создаёт дополнительных окон; полностью внешние зоны пропускаются с диагностикой,
при отсутствии пригодных сцен возникает ошибка без перехода на весь снимок. Применяются штатные черновики,
undo, Git-публикация, копирование и пересборка; исторические файлы не мигрируют.

Страница `#/dataset-editor` редактирует только per-image датасеты. TIFF выбираются из существующего
`prepared_images` по одному или прямыми файлами папки, без загрузки TIFF из браузера и рекурсии. OpenLayers отображает
авторизованный GeoTIFF через HTTP Range без экранной интерполяции пикселей, допускает nearest-neighbor overzoom до
`1000%` с умеренным экранным контрастом и позволяет полностью скрыть разметку отдельной кнопкой. Доступны
Draw/Modify/Snap, смена роли/типа, удаление и undo.
Общий редактор датасетов и тестовых разметок позволяет вырезать отверстие в одном выбранном объекте:
отдельный режим Draw не добавляет эскиз в слой объектов, а дописывает внутреннее кольцо в копию
`Polygon` либо подходящую часть `MultiPolygon`. Контур должен быть простым, ненулевой площади,
строго внутри одной части объекта, без касания, пересечения или охвата существующих отверстий.
При ошибке исходная геометрия остаётся неизменной. Сохраняются ID, свойства, роль и тип объекта;
вырез — одно действие общей истории и штатного автосохранения черновиков. `Esc` отменяет эскиз;
вершины отверстия затем доступны обычному Modify. Публикация, экспорт и маски используют внутренние
кольца GeoJSON; отверстие не становится отдельным объектом, его пиксели не относятся к этому полигону.
Отмена распознаётся по физической клавише `Z`, поэтому
`Ctrl+Z` и `Ctrl+Я` одинаково работают при латинской и русской раскладках. Рабочее поле вместе с панелью
инструментов раскрывается отдельной кнопкой в полноэкранный режим: используется браузерный API, а при его запрете —
эквивалентный режим на всю область окна поверх страницы. `Esc` возвращает обычный вид, а карта после каждого перехода
пересчитывает размер. В полноэкранной панели кнопки «Предыдущий снимок» и «Следующий снимок» со счётчиком
переключают снимки в текущем порядке списка, сохраняя черновики; на границах списка переход недоступен.
Снимок перемещается перетаскиванием с зажатым колесом;
нативная автопрокрутка браузера внутри карты подавляется, поэтому страница при этом остаётся неподвижной.
Левая кнопка протягивает рамку выбора всех попавших в неё вершин. У выбранных полигонов видны все вершины:
клик по ребру добавляет вершину. Нажатие внутри карты переводит клавиатурный фокус в неё, поэтому `Delete`
обрабатывается тем же действием, что и кнопка удаления. Клавиша удаляет выбранную группу вершин и автоматически
замыкает кольцо. Внешний контур оставшейся части сохраняет не менее трёх вершин; внутреннее кольцо удаляется целиком, если
после удаления осталось бы меньше трёх вершин, включая выбор всех вершин отверстия. У `MultiPolygon` таким же
образом удаляется выбранная часть вместе с её отверстиями, если остаётся хотя бы одна другая часть. Это
покрывает вынесенное отверстие, которое серверное восстановление топологии превратило в самостоятельную
часть. Если выбраны последние вершины всех частей, их внешние контуры не удаляются: произвольный остаток
или пустая геометрия не создаются, для удаления всего объекта используется обычное выделение полигона. Остальные кольца и части
`MultiPolygon`, ID и свойства объекта сохраняются. Если вершины не выбраны, та же клавиша удаляет выделенный полигон. Обе
операции проходят через общую проверку геометрии и историю undo; проверка footprint не ограничивает зоны разметки.
В режиме Modify выбранные объекты исключаются из целей Snap: вершина не притягивается к собственному
прежнему контуру во время перетаскивания. Привязка к другим видимым объектам сохраняется; при снятии
выбора, рисовании нового полигона или отверстия цели привязки восстанавливаются.
Обновление подсветки вершин меняет ревизию векторного слоя, а не объекта: `feature.changed()`
вне изменения геометрии запрещён, поскольку Modify при этом удаляет сегменты текущего перетаскивания.
Ответ автосохранения и визуальная фильтрация не прерывают удержание вершины.
Отложенные `singleclick` и выбор вершины после interactions принимаются только для текущего поколения
завершённого жеста; событие прошлого нажатия не снимает выбор даже после быстрого следующего перетаскивания.
Его состояние задают реальные `pointerdown` на карте и `pointerup`/`pointercancel` документа с учётом
идентификаторов всех указателей; таймеры не имитируют отпускание кнопки.
Для binary остаётся positive/hard negative. Для обычного multiclass segmented control содержит смысловые типы и
общий hard negative, а для управляемого — отдельный hard negative каждого исходного типа; типы имеют цвета manifest, hard negative
красный, выбранный объект — голубой контур. Легенда и счётчики считаются по типам; в списке снимков каждое
число окрашено тем же цветом, что и соответствующий контур, а под заголовком списка показывается сумма объектов
каждого типа по текущему состоянию всех снимков с учётом черновиков и пометок удаления. Псевдоразметка multiclass также использует сохранённые
цвета каждого типа из схемы сети, а не единый цвет слоя. В многоклассовом редакторе плашки легенды над снимком
переключают видимость типа сразу в разметке и псевдоразметке. Наведение или клавиатурный фокус подсвечивает
его видимые объекты только на включённых слоях. Фильтр сохраняется при смене снимка, сбрасывается при смене
датасета и не меняет разметку, черновики или счётчики; скрытые объекты исключены из выбора и привязки вершин.
Черновик каждого снимка хранится в Postgres
отдельно для пользователя и датасета, автоматически восстанавливается после обновления страницы и не меняет
MLMarkup. Редактор классов показывает сверху агрегированный список черновиков вошедшего пользователя; переход
открывает соответствующий датасет, где работа продолжается с восстановленного серверного состояния. Клиент автоматически сохраняет изменённые черновики с короткой задержкой и показывает состояние
сохранения; отдельной ручной кнопки сохранения нет. Перед записью черновика сервер восстанавливает полигональную
топологию и пересекает каждый объект positive/hard negative с фактическим valid-data footprint TIFF: частичный выход и попадание во
внутренний nodata-провал автоматически подрезаются, а полностью внешний объект после пересечения удаляется.
Нормализованный GeoJSON возвращается клиенту как сохранённое состояние, поэтому выход за footprint не срывает
автосохранение всего снимка. Проверка попадания в footprint учитывает машинную точность координат
и длину границы объекта: микроскопическая погрешность пересечения не блокирует сохранение,
но реальный выход за контур по-прежнему отклоняется. Отмена удаляет все черновики пользователя и возвращает
опубликованную разметку, а только отдельная публикация отправляет изменения одним batch. Удаление снимка является
тем же отменяемым черновым действием: до публикации GeoJSON остаётся в MLMarkup, пометка переживает обновление
страницы и снимается через undo либо общую отмену. Новые объекты до
публикации рисуются пунктиром; заливка отключается независимо от разметки. Для четырёхканального Канопуса доступны
экранные сочетания `RGB`, `NRG`, `NGB`, для трёхканального ортофото переключатель не показывается. Сервер обязательно
строит footprint по фактической valid-data mask TIFF, обрезает выдаваемые для редактирования и сохраняемые в
черновик объекты positive/hard negative этим контуром и проверяет CRS, `Polygon/MultiPolygon` и валидность всех геометрий; свойства и feature ID
сохраняются. Проверка неизменности пользовательских атрибутов сравнивает числа по значению: `1` и `1.0`
равны, в том числе во вложенных массивах и словарях. Изменение значения, типа или состава атрибутов
по-прежнему отклоняется; логические значения и строки не приравниваются к числам.
Optimistic lock использует Git blob revision, а у обычных датасетов также UUID и ревизию выбранной
версии в БД; конфликт возвращает `409`, автоматического слияния
геометрий нет. Исторический материализованный комбинированный датасет получает индикатор `current|stale` по всей каждой исходной папке `main`.
Перед пересборкой endpoint preview фиксирует target/source trees и показывает локальные изменения и конфликты;
`merge` сохраняет ручную версию конфликтующего объекта, `replace` полностью заменяет per-image файлы. Любое изменение
после preview даёт `409`, успешная замена каталога и публикация выполняются атомарно одним Git-коммитом.

Кнопка «Загрузить GeoJSON» принимает сразу несколько файлов разметки новых снимков (до 100, суммарно до 50 МиБ).
Имя `<папка>_<имя_TIFF>.geojson` должно однозначно соответствовать существующему серверному TIFF того же типа
снимков; уже добавленные сцены и собственные черновики не перезаписываются. `POST /api/v1/dataset-editor/datasets/{dataset_key}/drafts/import`
сначала проверяет весь пакет: FeatureCollection, явный CRS снимка, Polygon/MultiPolygon, роли, геометрии и
multiclass-схему. В binary отсутствие роли означает positive. Некорректный файл отклоняет весь пакет.
Если единственная проблема — выход объектов за footprint, ответ `400` с кодом
`annotation_outside_footprint` перечисляет файлы и число выходящих и полностью внешних объектов; ничего
не сохраняется. Кнопка «Обрезать и загрузить» повторяет запрос с `clip_to_footprint=true`
(по умолчанию false): существующая обрезка пересекает полигоны с valid-data footprint, учитывая внутренние
nodata и отверстия, и исключает пустые результаты. Весь пакет повторно проверяется и сохраняется атомарно
в черновики. ID и пользовательские свойства сохраняются. Зоны `annotation_zone` автоматически
обрезаются и без отдельного подтверждения; если исчезли бы все зоны, импорт отклоняется,
чтобы не расширить обучение на весь снимок.
При неверной роли или типе сообщение указывает файл, номер объекта, поле, ошибочное значение и допустимые
значения для текущего датасета; для отрицательной разметки явно приводится `"_mlsystem2_role": "hard_negative"`.
Альтернативные названия ролей, включая `negative`, не распознаются. Клиент показывает ошибку внутри окна
импорта, сохраняя выбранные файлы и текущий снимок; допустимые роли и multiclass-типы также видны до загрузки. ID и
пользовательские атрибуты сохраняются; служебное происхождение задаётся заново, чтобы импорт не выдавал
объект за существующий объект исходного датасета. До «Опубликовать» сцена существует только в
`dataset_editor_drafts` владельца с `base_revision="new"`: список и карта показывают её вместе с черновиком,
редактирование и автосохранение работают штатно. Обновление страницы сохраняет состояние, отмена убирает
новую сцену; обучение, экспорт датасета и другие пользователи её не видят. При публикации отсутствие целевого
файла повторно проверяется, появившийся файл даёт `409`. Новые и существующие сцены публикуются одним
Git-коммитом, companion-footprint строится сервером. В управляемом наборе объекты публикуются в соответствующие
исходные классы; явное членство новой сцены добавляется только при публикации, включая пустую разметку.
Новых таблиц и миграций нет.

Опубликованная файловая проекция датасетов для обучения, экспорта и автоматизации — рабочий Git-клон
`/data/mlsystem2/mlmarkup-editor`; `MLSYSTEM2_MLMARKUP_ROOT` указывает на тот же каталог.
Все мутации сериализуются межпроцессным lock в этом клоне
`/data/mlsystem2/mlmarkup-editor`, принадлежащем `MLMarkup_deploy_user` и использующем отдельный write deploy key.
Чтение рабочего клона не выполняет fetch; перед каждой Git-мутацией fetch и fast-forward обязательны,
перед push повторно проверяется blob revision. Читатели используют shared lock того же клона,
публикация — exclusive lock до завершения push и транзакции БД либо отката; вложенные обращения одного потока не захватывают
lock повторно. Поэтому каталог, материализация управляемых наборов, подготовка тестовых разметок и снимки
данных заданий не читают промежуточные файлы. Материализация сначала копирует источники под коротким shared lock,
а геометрию и footprint строит по этой копии без блокировки рабочего клона; снимок сохраняет SHA источника.
Чтение редактора и проверка публикации также используют shared lock без ожидания фоновых читателей.
Ошибка push/fetch откатывает неопубликованный коммит;
личные черновики сохраняются. Обучение и инференс фиксируют отдельные копии файлов для запуска;
версия результата обучения соответствует этой копии, включая ручные задания, ожидавшие в очереди.
Сохранение серверного черновика не выполняет Git-коммит,
push или инференс. Одиночный save совместим, а batch-публикация всех черновиков, включая помеченные на удаление
снимки, создаёт один атомарный commit. Для обычного датасета добавление папки пропускает уже присутствующие GeoJSON,
создаёт разметку и footprint одним commit; для управляемого пустые сцены добавляются только в БД без Git-публикации.
Публикация удаления убирает соответствующие исходные файлы. В браузере снимков уже добавленные TIFF остаются в исходном порядке, показываются зелёной
рамкой и не имеют повторного выбора. Канонический вошедший пользователь является реальным Git author/committer,
а его имя дополнительно сохраняется trailer. Разрешён один rebase/retry для постороннего коммита, но не для изменения целевого
GeoJSON.
Удаление всего датасета доступно из редактора классов: после проверки отсутствия активных заданий папка обычного
датасета удаляется отдельным Git-коммитом, а виртуальный управляемый датасет архивируется без Git. Основной датасет
класса снимается, строка `datasets` сохраняется с временем удаления. Повреждённое содержимое не читается;
если папка уже отсутствует в Git, запись архивируется без нового коммита. Защита от удаления корня,
вложенных активных источников и источника управляемого датасета сохраняется. Удаление и копирование
сразу видны читателям рабочего клона после завершения операции.
Копирование из редактора классов всегда создаёт новый ключ и не назначает копию основной. Для обычного датасета
копируется зафиксированное в Git опубликованное дерево в соседнюю папку с новым именем и одним авторским коммитом;
пользовательские черновики, шаблоны, задания и результаты обучения не переносятся. Файл выбора версий не
копируется: копия получает собственные варианты при импорте в каталог сущностей. Для виртуального управляемого
датасета без Git-коммита копируются его связи с общими исходными датасетами, приоритеты, цвета и явно добавленные
снимки; исходная и новая конфигурации после этого редактируются отдельно.

Успешная публикация по-прежнему создаёт commit и отправляет его в MLMarkup на GitHub, сохраняя актуальную
историю. `published` определяется ancestry относительно HEAD рабочего клона; доставка с GitHub не нужна.
Внешние README-коммиты допускаются, версия конкретного датасета определяется последним изменением его пути.
Workflow MLMarkup `deploy-markup-to-gpu.yml` отключён через GitHub Actions, но сохранён для будущего
ручного восстановления. Прежние неизменяемые каталоги `/data/mlmarkup-runtime/releases/<commit>`,
`current` и `/data/MLMarkup` остаются архивом; текущий код может явно читать архивный корень через
конфигурацию. В архивном режиме `publishing|published` проверяется по `.mlsystem2-release`.

Автоматизация обучения и псевдоразметки является частью `training_ui_api`. Она хранит правила
`датасет × модель` в Postgres, отслеживает управляемую версию датасета и файловую версию его источника
MLMarkup по git-коммиту, release metadata или filesystem mtime fallback и создает auto jobs только через те же очереди, что
и ручной запуск. Jobs диспетчеризуются общей очередью: ручная псевдоразметка выше ручного обучения,
ручное обучение выше auto псевдоразметки, auto псевдоразметка выше auto обучения. Auto jobs отменяются
изменением правила автоматизации или заменяются при новой версии конкретного датасета; frontend не
имеет прямого доступа к БД и не запускает процессы напрямую.
Ручной запуск обучения может явно запросить последующую полную псевдоразметку: только после успешного завершения
worker ставит в inference-очередь обычное штатное задание по всем снимкам обучающего датасета и связывает его с
полученным результатом. Счётчик рядом с пунктом «Очередь» показывает число active jobs, а переход из строки очереди
открывает тот же экран задания, что и кнопка Job в результатах.
Колонка «Автор» очереди читает `JobSummary.started_by` из `ui.started_by`, как и `JobDetail`.
Сессия HTTP-запроса фиксирует канонический логин только у новых ручных `JobRow` перед первым flush;
повторное использование существующего задания автора не меняет, тело запроса его не задаёт.
Ручное обучение сохраняет логин и для заказанной после него псевдоразметки. Автоматизация показывается
отдельно; историческим заданиям без сведений автор не приписывается.
Экран задания обучения содержит переход к результатам его датасета и кнопку открытия сохранённого запуска MLflow в новой вкладке; до создания
запуска кнопка MLflow недоступна.
HTTP API и исполнители очередей запускаются разными systemd-сервисами. Обучение и его дочерние DataLoader-процессы
наследуют ограниченный worker-cgroup, низкие CPU/IO weights, `nice` и `ionice`; часть CPU остаётся доступной API.
В серверном профиле используются восемь DataLoader workers и Torch pools `4/2`. `prefetch_epochs=1` сохраняется:
`prefetch_factor` автоматически компенсирует меньшее число workers, поэтому целевое количество готовых batch не уменьшается.
Дочерние загрузчики всех профилей запускаются через `spawn`, без наследования блокировок фоновых потоков основного процесса; ожидание batch ограничено 180 секундами. При `num_workers=0` отдельные процессы и таймаут не применяются.
Поснимочная псевдоразметка редактора и автоматические оценки новой эффективной сети
после завершения обучения имеют срочный inference-приоритет. Ручной F1 имеет обычный
ручной inference-приоритет, без срочности и второстепенности; активное обычное обучение не прерывает.
Оценка новой сети, не назначенной эффективной, имеет низкий приоритет и кооперативно уступает GPU
между тестовыми TIFF. Фонового подбора исторических сетей для автоматического пересчёта нет. Срочные queued-задания
обгоняют обучение независимо от ручного или автоматического источника. Если GPU занят обучением, train loop на
границе batch переносит модель и optimizer state в CPU, освобождает CUDA и подтверждает состояние `paused`;
worker запускает срочный инференс только после этого подтверждения, затем возвращает тот же процесс и тот же
MLflow-run на GPU. DataLoader workers прекращают чтение и растеризацию новых тайлов только после
подтверждения `paused` с token текущего `pause.request`, чтобы не блокировать получение batch или сброс
итератора до освобождения GPU. Накопленный префетч не сбрасывается. Обычный running-инференс не прерывается.
Ручное обучение может быть запущено со второстепенным приоритетом. Такое обучение и заказанная после него
полная псевдоразметка выполняются только при отсутствии обычных заданий. При появлении обычной работы обучение
кооперативно освобождает CUDA на границе batch, PyTorch-псевдоразметка — между снимками, а Geoalert-псевдоразметка
между снимками выгружает модель из Triton. После опустошения обычной очереди тот же процесс продолжает работу;
готовые снимки псевдоразметки повторно не обрабатываются. Обычный running-инференс по-прежнему не прерывается.
При остановке выполняющегося ручного обучения UI предлагает сохранить результат с лучшей уже полученной
валидационной F1 либо отменить job без результата. Первый вариант доступен только после полной валидации хотя бы
одной эпохи: API создаёт `stop-and-save-best.request`, train loop на ближайшей границе batch отбрасывает текущую
незавершённую эпоху и штатно завершает `train_pipeline`. В MLflow публикуется только `best.pt` лучшей завершённой
эпохи; `final.pt` из текущего состояния не создаётся, запуск и результат обучения считаются успешными. Для binary
лучшей считается F1 выбранной `quality_metric`, для multiclass — macro pixel F1. Остановка без сохранения остаётся
немедленной отменой с `SIGTERM`, удалением незавершённого результата и статусом MLflow `KILLED`.
Завершённое нативное обучение можно продолжить из результатов датасета. Это новый ручной training job и
новый MLflow run от выбранных весов: `checkpoints/best.pt` либо `checkpoints/final.pt` исходного завершённого
запуска. Последний вариант недоступен, если файл не сохранён, в том числе после остановки с сохранением
лучшего результата. В диалоге меняются дополнительные эпохи, время обучения, patience, псевдоразметка
после обучения и второстепенный приоритет. Две опции очереди изначально наследуются от исходного задания,
но явно выбранные значения применяются к новому этапу; отсутствие полей в старом API-запросе сохраняет
наследование. Псевдоразметка использует штатный механизм для всех снимков датасета, её приоритет наследуется
от нового этапа так же, как в мастере запуска обучения. Остальные параметры
сохраняются. `TrainingContinuationCreate.dataset_source=original|current` выбирает состав:
По умолчанию `original` восстанавливает снимок выбранного этапа и сохраняет поведение старых запросов и заданий.
`current` берёт тот же активный датасет по постоянному ключу. При отправке и старте проверяются
доступность, задача, ID/slug выходных классов и каналы. На старте под блокировкой MLMarkup штатный
`_dataset_config` копирует актуальные опубликованные TXT/GeoJSON/manifest и выбирает текущий корень TIFF.
Добавления, удаления и правки за время ожидания учитываются; личные черновики не входят. Версии job/result
обновляются до фактически скопированной редакции; дальнейшие правки этот snapshot не меняют.
Несовместимая схема, удалённый или пустой набор дают ошибку, без подмены прежними данными; custom-upload
использует `original`. Выбор, исходная и фактическая версии сохраняются в `ui.training_continuation`.
Результат вычисляет `continued_from_dataset_source` без миграции БД; старые продолжения считаются `original`.
Оптимизатор, scheduler, ранняя остановка и счётчики нового этапа
инициализируются заново: нынешние checkpoint содержат веса и метаданные, без состояния оптимизатора.
Исходный результат, основная сеть класса и её псевдоразметки не заменяются. Дочерний результат хранит
происхождение в серверном `JobRow.config["ui.training_continuation"]` и использует обычную очередь, паузу,
остановку, публикацию checkpoint и проверки качества. Повтор запроса с тем же `request_id` идемпотентен.
Каждый результат получает постоянный `dataset_number` из атомарного счётчика `training_result_counters`
по ключу датасета (`class_key` результата). Миграция `20261018_0035` нумерует прежние неотменённые
запуски от старых к новым по `created_at,id`; каждый датасет начинает с 1. Новые ручные, автоматические
и продолженные обучения используют тот же счётчик; отмена и архивирование номера не переиспользуют.
Перед названием сети UI показывает жирный `#N`. Общий текстовый `comment` хранится в результате,
отдельно от параметров и метрик; под автором — текст с карандашом, при пустом значении только карандаш.
Редактирование встроенное, потеря фокуса сохраняет через PUT с обязательным `expected_comment`;
конфликт возвращает 409 без перезаписи, ошибка сохраняет черновик в открытой строке.
Подтверждённое удаление результата устанавливает `archived_at` и `archived_by`, сохраняя задания,
псевдоразметки, веса в MLflow, метрики и комментарии. Активное обучение и задания, использующие сеть,
блокируют удаление. Архив исключён из результатов, истории, выбора сетей, просмотра F1/псевдоразметки,
продолжения и экспорта; отменённые архивные записи защищены от фоновой очистки.
Если сеть была основной, назначение снимается; далее действует обычный выбор доступной сети.
Архив не имеет страницы или HTTP API восстановления. Обслуживающее восстановление на сервере очищает
`archived_at/archived_by` по проверенному UUID, не меняет номер и не назначает сеть основной автоматически.
Служебная категория `Custom` не является классом каталога и показывается в результатах только при наличии
неархивированных, неотменённых собственных обучений либо видимых псевдоразметок с `class_key=custom`.
Разовые прогнозы настоящих классов с техническим `dataset_key=custom` не создают эту категорию.
После удаления последних собственных результатов пустая карточка исчезает; ручная загрузка данных сохраняется.
Автоматизация учитывает архивный запуск как уже выполненный: удаление не вызывает повторного обучения.
Результаты группируются по связям исходной сети и её продолжений, включая ответвления и цепочки;
каждый этап сохраняет собственные оценки и псевдоразметки. У псевдоразметки и в её просмотрщике
показаны выбранные веса и их эпоха. При ручном создании псевдоразметки в результатах обучения
можно выбрать лучший чекпойнт (по умолчанию) или последний `final.pt`. Выбор сохраняется в JSON
задания; worker читает эпоху, порог и метаданные из выбранного файла, не из лучших весов.
Отсутствие последнего файла и импортированная сеть без него дают явную ошибку, без подмены весов.
Автоматизация, F1, источники тестовых наборов и подсказки редактора остаются на лучших весах;
ручной прогноз последних весов доступен отдельно для просмотра и сравнения.
Эпохи нового этапа имеют собственный отсчёт.
Чекпойнты прежних запусков остаются в MLflow и не перезаписываются продолжением.
Перед запуском worker проверяет выбранный артефакт завершённого MLflow run и скачивает именно его через
`mlflow_adapter.api`; отсутствие файла завершает задание ошибкой, запуск с новыми весами запрещён.
Параметры восстанавливаются из `config/resolved_train_config.json`, а для исторического запуска без этого
артефакта — из его `run.yml` или `config/train_config.yaml`. Исходные txt/geojson/manifest копируются в
рабочую папку дочернего задания из сохранённого снимка, при его отсутствии — из артефактов `dataset`.
Текущие шаблоны не подмешиваются; новая редакция данных используется только при явном выборе `current`.
При старте любого нового
training job валидированный полный снимок настроек обучения `SystemSettings` (без блока `inference`) записывается в `run.yml` до запуска процесса
и затем публикуется в MLflow, чтобы дальнейшая смена общих настроек не меняла параметры повторного этапа.
`settings` допускает `initial_checkpoint_uri` в next-gen2/object_f1 для продолжения; остальные ограничения
фиксированного профиля сохранены, совместимость весов проверяет существующий загрузчик `train_pipeline`.

Глобальное отключение автоматизации отменяет все active auto jobs, останавливает running automatic
process и помечает известный MLflow run как `KILLED`; повторное включение создает jobs заново по
текущим правилам и версиям датасетов.
Шаблоны обучения в `training_ui_api` бывают базовыми для сети и привязанными к конкретному
датасету. При создании job сервис сначала ищет шаблон `(architecture, dataset_key)`. Если ключ датасета
сменился при миграции, каталог однозначно восстанавливает связь по каноническому имени `класс\датасет`;
только при отсутствии такого шаблона используется базовый `(architecture, null)`. Одинаковый выбор применяется
ручным запуском и автоматизацией, поэтому frontend не дублирует эту бизнес-логику.
Шаблоны инференса — общие именованные наборы с необязательным описанием, без деления по модели,
датасету и типу снимков. Nullable FK `dataset_classes.inference_template_id` назначает классу один шаблон.
Все классы показаны плашками; меню переносит класс в другой шаблон или снимает привязку.
Новые классы остаются без назначения. Удаление архивирует шаблон, атомарно снимает все его привязки
и требует предупреждения в UI о затронутых классах. Исторические записи и снимки конфигурации заданий сохраняются.
Параметры общего шаблона применяются ко всем сетям и датасетам его классов; сброс восстанавливает baseline
самого шаблона. Выбор по классу обучающего датасета общий для ручной и автоматической псевдоразметки,
AOI, F1 и экспорта. Привязка независима от источника снимков и от смены типа снимков класса.
Мастер обучения и продолжение показывают предупреждение у галочки псевдоразметки и отключают её
без активного шаблона. Ручная форма предупреждает и блокирует запуск. API запрещает псевдоразметку,
AOI и обучение с последующей псевдоразметкой без шаблона; автоматизация пропускает такой инференс.
Миграция `20261007_0031` сохраняет ID старых шаблонов в архиве и выбирает действующие параметры
эффективной основной сети класса (явная основная либо последняя успешная). Без успешной сети используется
наиболее частый нормализованный набор активных вложенных настроек; при равенстве — поздний `updated_at`,
затем больший ID. При отсутствии прежних настроек используются стандартные defaults.
Одинаковые наборы объединяются в общие шаблоны с привязкой существующих классов.
Инициализация не создаёт корней и не восстанавливает снятые привязки.

Обучение и нативный инференс используют единый контракт окна: `tile_preparation.tile_size` задаёт полный вход сети, `tile_preparation.context` — исключаемую рамку, полезный центр равен `tile_size - 2 × context`. Для действующих шаблонов с входом `768` используется context `128` и центр `512`; `context=0` сохраняет старое поведение. Подготовка строит окна с отрицательным начальным смещением, а loss, validation и выбор checkpoint считаются только по центру. В `legacy` nodata, raster mask и padding внутри центра остаются обучающим фоном. В `next_gen` они передаются отдельной valid-mask и исключаются из loss и TP/FP/FN; после встроенного в модель preprocessing невалидные значения равны нулю. Seed подготовки задаёт Python, NumPy, Torch и CUDA до создания модели и сохраняется в MLflow/checkpoint.

Псевдоразметка Training UI запускается отдельным процессом, а backend определяется типом снимков модели.
Модели Канопуса сохраняют совместимый `pytorch_one_off`: runner загружает нативный checkpoint через
`models.load_checkpoint` либо проверенный по SHA-256 TorchScript из ZIP импортированного результата и после
обработки освобождает CUDA cache. Для всех моделей ортофото используется только
`geoalert_workflow_engine`: оркестратор экспортирует конкретный checkpoint в кешированную GPU-модель Triton,
загружает её через explicit model-control API, запускает штатный Geoalert `Compose` в отдельном окружении и
после задания выгружает модель. Нативные модели проходят через `SplitRaster`, `Segmentation`,
`MaskMorphology`, `VectorizeMasks` и настроенные vector bricks; внешние ЗУ500 и ОКС500 используют их
собственные pipeline с `NSPDParcels`, NMS, коррекцией топологии и footprint. Python-backend ЗУ500 получает
`torch/torchvision` из read-only mount окружения MLSystem2; это runtime-зависимость Triton, а не альтернативный
predictor. Каждая raster-стадия штатного pipeline пишет в отдельную промежуточную маску; чтение и перезапись одного
имени в одном `MaskMorphology` запрещены, поскольку дают зависимую от размера TIFF ошибку GDAL.
Для `next_gen2` Compose runner регистрирует поставляемые вместе с `training_ui_api` расширения:
`SlidingWindowSegmentation` вызывает штатный Triton adapter для полных окон и усредняет вероятности
с Gaussian sigma 0.25 до применения порога. В RAM хранится только полоса высотой в одно окно;
непокрытые края остаются нулевыми. `SplitRaster(apply_mask=False)` сохраняет исходные пиксели под маской TIFF.
Без этого флага используется прежний брик Geoalert. Регистрация выполняется до загрузки YAML и не требует
ручного изменения установленного окружения Geoalert при деплое.
Кеш экспорта сохраняет тип выхода и порог модели: изменение постобработки пересобирает YAML
с тем же вероятностным профилем без повторного экспорта сети.
Для внешней модели, возвращающей готовые классы (ОКС500), порог остаётся `null`;
создание кеша и восстановление YAML допускают его отсутствие и сохраняют исходный внешний pipeline.
При загрузке Compose передаётся пустой `enable_blocks`: все блоки экспортируемых конвейеров обязательны,
а Geoalert требует явный словарь даже при отсутствии необязательных блоков.
В TorchScript ОКС500 пустой encoder skip в рабочей и экспортной копиях наследует устройство входа,
чтобы один архив работал на CPU и GPU. Исходный ZIP в MLflow и веса сохраняются; кеш этой внешней модели
использует версию 5 для пересборки прежних копий с привязкой skip к CPU.
Вариант конвейера передаётся в задания псевдоразметки и F1: у `next_gen2` число снимков не включает
общий профиль с фильтрацией площади и упрощением контуров. Необходимые ограничения задаются
явно в шаблоне класса или соответствующего типа снимков.
Имя feature collection, созданной `VectorizeMasks`, без преобразования передаётся как `input` и `output`
последующей `UnifiedVectorProcessing`; raster-имя бинарной маски `mask` не используется как имя векторного слоя.
Речной inference-шаблон помечает полигоны в полосе одного пикселя от четырёх сторон растра и выполняет в UTM
`FilterSmallObjects → RemoveSmallHoles → FilterCompactObjects → Smooth → Simplify → RemoveTags`.
Перед загрузкой Compose процесс регистрирует расширения VectorizeMasks, FilterSmallObjects и оба режима compact-фильтра из поставляемого кода; те же расширения включены в экспорт. Ошибка загрузки конвейера сохраняется в отчёте с причиной.
Промежуточная конфигурация сохраняет направление compact-фильтра из шаблона: `keep_compact`
использует `FilterNonCompactObjects`, `remove_compact` — `FilterCompactObjects`. Объектная ветка
сохраняет параметры пометки краёв `VectorizeMasks` вместе с `instance_id`; защитные фильтры
получают тот же служебный тег, что и в остальных профилях. Смена эффективной постобработки
пересобирает сценарий кеша без изменения весов сети.
`FilterCompactObjects` принимает решение только по isoperimetric quotient и minimum rotated rectangle, без
ограничения площади; граничные и вырожденные геометрии сохраняются, а невалидные не приводят к ошибке
compact-фильтра. Для озёр compact-фильтр и сглаживание не включаются, поэтому их прежний vector pipeline не
меняется. Совместимый `pytorch_one_off`
повторяет тот же порядок геометрических операций.
Контейнер Triton для Python-backend запускается с `/dev/shm` не менее `1 GiB`: стандартных Docker
`64 MiB` недостаточно для входа ЗУ500 `1884×1884` и переменного instance-выхода. Один и тот же backend применяется
для полной и поснимочной псевдоразметки, AOI и F1 тестовых разметок; альтернативного локального predictor для
ортофото нет. Сцены разрешаются через публичный
`dataset_preparing.resolve_scene_images`: точное имя `SCNxx` не расширяется до соседних сцен, а одинаковые
имена в подпапках выбираются по GeoJSON датасета. Эффективный inference-шаблон выбирается по классу обучающего
датасета модели независимо от источника снимков. Для трёхканального checkpoint этот одноразовый инференс принимает
RGB и совместимые RGBA GeoTIFF, читая из RGBA только первые три канала; остальные несовпадения числа каналов
отклоняются. `external_torchscript` является только inference-архитектурой, отсутствует в каталоге обучаемых
сетей и использует общие правила выбора inference-шаблона класса. Нативная псевдоразметка читает полный вход, записывает только полезный центр и при ненулевом context идёт с шагом размера центра; старые jobs без context используют прежнюю сетку. Её манифест в исходном `JobRow.config` фиксирует адаптер, MLflow artifact,
SHA-256, RGB-вход, разрешение, окна и постобработку. ЗУ500 сохраняет instance ID и confidence, выполняет NMS и
не объединяет соседние участки; ОКС500 строит крышу из классов `1,2` и корректирует footprint по стенам класса
`4`. Оба профиля обнуляют alpha/nodata. Нативный multiclass checkpoint использует `softmax → argmax → общий confidence threshold`; перекрытия окон и сцен разрешаются по confidence, затем priority и class ID. Морфология, векторизация и слияние выполняются отдельно по типам. Каноническая псевдоразметка остаётся одним FeatureCollection с родительским `class_id` и `object_type_id/slug/name/color`; дополнительный endpoint отдаёт ZIP с GeoJSON по типам. Подготовка датасета, обучение и основной CLI-инференс сохраняют строгую проверку каналов.
Перед обучением worker копирует legacy-файлы либо все per-image GeoJSON в неизменяемый snapshot задания. Для
псевдоразметки per-image набора временный TXT строится из строго сопоставленных TIFF, а в runner передаются все
файлы разметки этого набора. Полная псевдоразметка считается успешной и публикуется в `stored_files` только при
обработке всех выбранных снимков без `failed` и `missing`; диагностический `partial` остаётся в отчёте задания,
но job и результат получают `failed/error`, а неполный GeoJSON не становится готовой псевдоразметкой.
Редактор per-image датасета по умолчанию не показывает псевдоразметку. Для подсказки редактора явно назначенная
основная сеть имеет приоритет только если обучена на открытом датасете; иначе выбирается последняя успешная
сеть этого датасета. Основной датасет класса не влияет на выбор, сети других датасетов не подставляются.
Выбор сети общий с созданием тестовых разметок; явный dataset_key имеет приоритет над историческим class_key.
По явному переключателю редактор сначала берёт последнюю успешную
полную псевдоразметку лучших весов выбранной таким образом сети, чей список сцен содержит выбранный TIFF, независимо от исходного
датасета или папки результата, и обрезает её по valid-data footprint. Нормализация ссылки
удаляет только явное расширение TIFF и сохраняет точки внутри имени сцены. Исторический `scenes_file` с одним
именем файла без подпапки принимается только тогда, когда оно однозначно разрешается в тот же TIFF внутри корня снимков.
Если legacy-TXT был удалён миграцией, полный результат того же датасета принимается по точному совпадению
`dataset_key` и управляемой версии: версия фиксирует состав снимков, в том числе сцены с пустым предсказанием.
Если результат не покрывает снимок,
клиент сначала выполняет read-only проверку готового результата и только после ответа `unavailable` запрашивает
создание. Затем создаётся идемпотентное срочное задание: одноэлементный список сцен проходит через общий
`pseudo_config.yaml` и выбранный по типу снимков backend штатной псевдоразметки; уникальный ключ включает сеть,
TIFF и effective inference-конфигурацию.
Повторные клики и конкурентные запросы используют ту же строку job, готовый GeoJSON хранится как StoredFile, а
frontend сохраняет состояние по снимкам при переключении. Polling идёт по лёгкому endpoint `job_id` без Git и полного
сканирования каталога. Выбранная сцена принадлежит конкретному успешно загруженному списку: при смене датасета
выбор синхронно очищается, а запросы прежней сцены отбрасываются до обращения к API. Запоздавшие ответы также
принимаются только для всё ещё открытого датасета. Ошибочное задание повторяется только явным действием
пользователя. Готовая псевдоразметка остаётся отдельным нередактируемым слоем. В явном режиме выбора картограф
может выбрать один или несколько её объектов, назначить им тип текущего multiclass-датасета либо `hard_negative`.
Для управляемого набора при добавлении hard negative выбираются один, несколько или все исходные датасеты, после
чего геометрия копируется в пользовательский черновик. Служебные свойства прогноза при копировании не переносятся,
операция попадает в общую историю отмены и сохраняется тем же автоматическим серверным сохранением, что и ручное
рисование; публикация в MLMarkup по-прежнему выполняется отдельно.
Просмотр готовой полной псевдоразметки доступен по `#/pseudo-markup/<result_id>` через маленькую иконку
рядом со скачиванием GeoJSON, без пункта меню. Страница только читает сохранённый результат и показывает
сеть, обучающий датасет, общую мозаику исходных TIFF и отдельный слой полигонов с цветами типов.
Состав мозаики берётся из зафиксированных обработанных путей `JobRow.config.pseudo_processed_images`,
для старых результатов — из отчёта runner либо сохранённого списка сцен с однозначным сопоставлением.
Снимки без объектов включаются. Текущий состав датасета допустим только при точном совпадении сохранённой
версии; неизвестный исторический состав, неоднозначность и недоступные файлы явно показываются, не подменяются.
Новые успешные полные задания сохраняют обработанные пути в существующем JSON задания, без миграции БД.
`GET /api/v1/results/pseudo-markup/{result_id}/view` возвращает описание мозаики; соседний
`/raster/{scene_id}` отдаёт HTTP Range только для TIFF из этого результата внутри prepared_images.
Все маршруты требуют входа. `/footprint/{scene_id}` лениво возвращает контур фактической valid-data mask
в EPSG:3857 с теми же проверками состава и файловой ревизии. Расчёт маски и его ограниченный кэш общие
с редактором (`_raster_valid_data`): до 4096 пикселей по длинной стороне, с сохранением топологии контура.
TIFF читаются браузером по видимой области с ограниченными кешами, без новых
растров; по умолчанию снимки отображаются в RGB, alpha/nodata сохраняют прозрачность. Для RGB+NIR доступны
те же сочетания RGB/NRG/NGB, что и в редакторе датасета, с общей таблицей каналов. Наличие NIR определяется
по каналам TIFF отдельно от alpha и передаётся в `PseudoMarkupSceneInfo.has_nir`; RGB/RGBA в смешанной мозаике
сохраняют естественные цвета. Переключение меняет только стиль, сохраняя охват карты и источники снимков.
Колесо масштабирует карту при наведении, без предварительного клика; кнопки «+» и «−» не отображаются.
Список подсвечивает снимки, чьи bounds пересекают текущую область карты, и показывает их количество.
Расчёт выполняется по кадру OpenLayers при перемещении, масштабе, повороте и изменении размеров; React
обновляет список только при смене состава. Поиск не меняет состав видимых снимков на карте, выключение
растров скрывает подсветку. Для счётчика и подсветки списка дополнительных запросов не требуется.
Глаз строки независимо включает и выключает её снимок; выключенные снимки исключены из отображения
и счётчика, а готовый кадр подложки сбрасывается, чтобы скрытый снимок не оставался на карте.
Наведение или клавиатурный фокус выделяет контур данных без nodata; нажатие на имя приближает снимок
и сохраняет выделение после ухода курсора. Повторное нажатие снимает выделение без смены охвата карты,
даже если курсор остаётся над строкой. Контуры загружаются по требованию с отменой устаревших запросов;
клиент хранит не более 32 контуров. Псевдоразметка остаётся отдельным слоем.
Загрузчик повторяет временные сетевые ошибки ограниченное число раз; отменённый запрос не объявляется
отсутствующим файлом. Ошибочные тайлы OpenLayers повторно загружаются явно, так как состояние ERROR
само не возвращается в очередь. Предупреждение учитывает только невосстановленные ошибки, различает
отсутствие файла, смену ревизии и потерю доступа и позволяет перечитать снимки без перезагрузки страницы.
Кнопка в правом верхнем углу карты разворачивает просмотр на весь экран, сохраняя карту, список снимков,
каналы и настройки слоёв. Повторное нажатие или Esc возвращает обычный вид. Управление полноэкранным
режимом общее с редактором датасета (`useMapFullscreen`); при недоступности браузерного API используется
разворачивание внутри окна. Изменение размеров не пересоздаёт карту и её источники.
Недавно просмотренные источники сохраняются в ограниченном пуле; видимые снимки и опорные схемы каналов
не вытесняются. Два нижних масштаба подгружаются заранее. Один готовый кадр растровой мозаики остаётся
под новыми тайлами и преобразуется вместе с картой до завершения загрузки, включая скачки через несколько
масштабов; слой полигонов в него не включается. При смене сочетания каналов сохранённый кадр сбрасывается.
Полученные HTTP Range хранятся в IndexedDB до суток: общий предел 512 МиБ для всех вкладок сайта,
не более 10% квоты браузера и половины доступного места на момент открытия кэша. При записи одной транзакцией
удаляются просроченные и затем наиболее давно использованные фрагменты; ответ целого TIFF не кэшируется.
Ключ включает пользователя, URL с файловой ревизией и диапазон; вход и доступ к результату проверяются
при открытии страницы, выход очищает кэш. URL растров содержит `v` из размера и времён изменения файла;
несовпадение версии возвращает 412, ответы содержат ETag и `private, no-store`, поэтому обычный HTTP-кэш
не обходит этот предел. Недоступность IndexedDB или исчерпание квоты не препятствует сетевой загрузке.
Просмотр не запускает инференс.

Просмотрщик также сравнивает от двух до двенадцати готовых псевдоразметок разных классов, датасетов и
этапов обучения. Иконка в результатах добавляет разметку в общий список, который живёт в авторизованной
frontend-сессии и сохраняется при переходах между датасетами. `#/pseudo-markup/compare/<id1,id2,...>`
открывает общий просмотрщик с выбором одного снимка, прежними TIFF/Range/кэшем, каналами и полным экраном.
Снимки объединяются только по идентичному сохранённому пути TIFF (`PseudoMarkupSceneInfo.id`),
не по имени файла или географическому совпадению. Состав снимков берётся из обычных авторизованных view.
Каждая разметка включается отдельно кнопкой с глазом, номером и цветом на снимке; боковой список
идентифицирует класс, датасет, сеть, дату и эпоху. Подсветки, подложка, каналы и полный экран также
управляются на карте. При открытии выбран первый общий снимок, если он есть.
Канонические полигоны EPSG:4326 растеризуются по центрам пикселей
нативной сетки TIFF без nodata/alpha; семантические типы внутри разметки объединяются в один foreground.
Предварительный географический отбор использует bbox с уплотнёнными краями преобразования CRS,
а окончательный — нативные окна: кривизна проекционных границ не отсекает краевые объекты.
Точные счётчики читают TIFF окнами до 512×512; просмотр не создаёт задания инференса, файлы или строки БД.
Первый кадр сравнения не ждёт точных счётчиков: frontend передаёт `viewport` — bounds EPSG:3857
и размер карты, сервер растеризует только видимую область на сетке обзора со степенью двойки.
Размер рабочей маски ограничен размером карты; при приближении шаг становится одним исходным пикселем.
Перемещение, масштаб и полный экран обновляют слои; предыдущий кадр остаётся до готовности нового.
Счётчики этого экранного слоя отсутствуют, приближённые площади не выдаются за точные значения.
Для точного счёта frontend запрашивает `scene_id` отдельно: сначала выбранный снимок,
затем остальные общие TIFF последовательно в фоне. Готовые значения появляются в списке сразу;
общая сумма публикуется только после всех снимков, до этого виден прогресс. При переключении,
смене слоёв и уходе запрос отменяется; сервер проверяет разрыв соединения и прекращает работу
на границе окна/геометрии, не кэшируя частичный результат. Завершённые сцены повторно не считаются.
Зелёный показывает покрытие минимум двух активных слоёв, цвет каждого слоя — только его уникальные пиксели.
Подсветки пересечений и различий независимы, яркость и непрозрачность совпадают с просмотром тестового F1.
Для ровно двух активных разметок доступны пересечение и два направленных различия в пикселях по снимкам
и их сумме. Сумма включает только общие доступные TIFF; отсутствие снимка не считается пустым прогнозом.
Отдельные исходные TIFF считаются независимо, даже если географически перекрываются. Это сравнение
прогнозов без эталона, не F1. Новые авторизованные POST-маршруты `.../pseudo-markup/compare/counts` и
`.../pseudo-markup/compare/{scene_id}/layers` выполняют только чтение: проверяют готовность каждого результата,
его точный состав, принадлежность снимка и ревизии подложки (412 при изменении).
Ограниченные кэши геометрий, счётчиков и слоёв учитывают ревизии TIFF и GeoJSON; доступ проверяется до кэша.

Доставка frontend через `frontend/deploy.py` сохраняет хешированные JS/CSS и декодеры предыдущих
сборок в `assets`: открытая вкладка может загрузить их уже после обновления сайта. Зависимости
публикуются раньше атомарной замены `index.html`; удаление всего старого `assets` при деплое запрещено.
Хранение ограничено семью сутками и общим целевым размером 128 МиБ, текущая сборка защищена от очистки.
HTML отдаётся с `no-store`. При `vite:preloadError` очень старого просмотра допустима однократная
автоматическая перезагрузка с защитой от цикла (минута, sessionStorage, только при наличии сети).
Этот механизм ограничен страницей псевдоразметки и не перезагружает редактор или формы.

Распознавание AOI для QGIS является дополнительным HTTP-контрактом того же `training_ui_api` и проходит
через общую inference-очередь и тот же выбранный по типу модели backend. Клиент передаёт класс, выбранный источник,
Polygon или MultiPolygon и CRS. Сервер фиксирует основную сеть класса. Источник выбирается независимо:
локальные `kanopus` и `ortho`, OpenAerialMap либо настроенные XYZ/TMS/WMTS. Внешние тайлы существуют только
в scratch задания. Для перекрёстного запуска источник приводится к медианному размеру пикселя обучающих TIFF;
импортированная модель всегда использует точное разрешение манифеста, включая локальное ортофото;
трёхканальная модель читает RGB, четырёхканальная получает RGB+NIR только от Канопуса, а для RGB-источника —
RGB и нулевой NIR. Альфа-канал является только маской валидности. Сервер выбирает все пересекающие TIFF,
обрабатывает AOI окна и расширяет соседний контекст до окончания связных объектов. Полностью внешние объекты
удаляются, а пересекающие AOI сохраняются целиком с площадью и средней уверенностью в `stored_files`.
Метаданные результата фиксируют источник, схему каналов, целевое разрешение, лицензию и attribution.
QGIS-плагин находится в отдельной корневой папке
`mlsystem_plugin`, не импортирует пакет сервера и связан с ним только HTTP. Решения пользователя сохраняются
в одном каноническом локальном GeoPackage staging. Для multiclass сохраняются object type ID/slug/name/color,
фильтр типа меняет ту же единую очередь и общие review-статусы. Пользователь выбирает один категоризированный
слой либо группу синхронизированных представлений по типам. Плагин также фильтрует кандидаты по площади и уверенности, позволяет разбить
один или все прошедшие фильтры крупные объекты и создаёт по явной команде новый временный слой из текущего
отбора. Существующие слои проекта плагин не изменяет и поля с ними не сопоставляет.
Страница экспорта моделей в `training_ui_api` показывает последние успешные training results по датасетам
MLMarkup и по умолчанию выбирает основные датасеты классов. Каталог хранит у датасета историческую основу
имени модели, полученную из имени positive GeoJSON прежнего legacy-формата; миграция в per-image не меняет её.
Интерфейс предлагает имя `<историческое имя>_<тип снимков>`: `<имя>_kanopus` для Канопуса и исторически
совместимое `<имя>_orto` для ортофото. Пользователь может изменить предложенное имя перед выгрузкой. Экспорт
скачивает `checkpoints/best.pt` либо внешний ZIP из MLflow по сохраненным run id,
собирает временный общий zip-архив для `models-serving-service` и Triton через тот же сборщик, что одиночный
экспорт, отдаёт его пользователю и не пишет данные в Postgres, MLflow, S3 или рабочий каталог сервиса инференса.
Одиночный и пакетный экспорт результата разрешают актуальный effective inference-шаблон по
каноническому классу обучающего датасета, а `export_metadata.json` фиксирует нормализованный postprocess-конфиг и его SHA-256;
низкоуровневый экспорт загруженного `.pt` не подбирает классовые настройки. ONNX получает полный вход;
его выходной semantic channel фиксируется в метаданных графа, чтобы strict model config Triton не отвергал
HF-граф с символически выведенным числом каналов. Geoalert YAML получает `bounds=context` и
`sample_size=полезный центр`. Для старого checkpoint без metadata
context экспорт использует `bounds=0`; оператор может явно задать context. Binary ABI остаётся прежним.
Multiclass ONNX возвращает `uint8 [B,N,H,W]` one-hot foreground-каналов после threshold; pipeline содержит
semantic `output_labels` и отдельный GeoJSON каждого типа, а export metadata — task, полную schema, threshold,
размеры окна и checkpoint metadata.
Сборщик каждого одиночного экспорта сохраняет прежний локальный `<имя>_triton.yaml` и отдельные
`<имя>_pmo.yaml` / `<имя>_pmo.base64.txt` для вкладки pipeline существующего сценария и его API.
Вариант ПМО использует `models-serving.service.consul:18070` и обязательный блок `Recognition`,
не меняя формулы инференса или постобработки. Для другого контура меняется адрес адаптера;
наличие нужных бриков проверяется отдельно, YAML не устанавливает runtime автоматически.
Групповой экспорт включает те же файлы, отдельные инструкции в `instructions/` и общий `runtime/`;
конфликт версий расширений отклоняется. Инструкция сохраняет остальные этапы существующего сценария.
Страница создания списка сцен в `training_ui_api` принимает GeoJSON и тип снимков, рекурсивно сопоставляет
полигональные объекты с фактическими валидными пикселями TIFF только внутри соответствующего корня
`prepared_images/kanopus` или `prepared_images/orto` и возвращает ZIP с UTF-8 TXT полных относительных путей
внутри выбранного корня без расширений и GeoJSON реальных футпринтов тех же снимков в WGS84. GeoJSON содержит
по одному объекту на строку TXT и позволяет проверить покрытие разметки в QGIS. Файлы не сохраняются в БД или
постоянном хранилище; их имена повторяют имя загруженного GeoJSON. Совпадающие имена TIFF в разных папках
различаются путём; сцена, где вся площадь пересечения приходится на `nodata`, исключается. Совпадение
относительного пути без расширения считается неоднозначностью. Старый HTTP-режим
без флага футпринтов продолжает возвращать только TXT.
Нарезка тестовой разметки является самостоятельной функцией `training_ui_api` и не входит в конвейер обучения,
training/inference-очередь или автоматизацию. Она читает исходные TIFF только из `MLSYSTEM2_IMAGES_ROOT` с серверным значением
`/data/mlsystem2/prepared_images`, выбирает полностью валидные непересекающиеся тайлы по положительной разметке
датасета MLMarkup и формирует TIFF, GeoJSON, PNG class-ID mask и цветное PNG-превью. Для per-image источника каждый TIFF
использует только свои features с ролью `positive`; hard negative в тестовую разметку не попадает. Multiclass-отбор
гарантирует оба типа при наличии кандидатов, стремится к равным квотам и сообщает о дефиците. Совместимые endpoints
`/markup-export` хранят временный ZIP один час в `scratch_root`. Основной интерфейс создаёт постоянные тестовые
разметки: описание и состояния тайлов хранятся в Postgres, а файлы — в
`MLSYSTEM2_TRAINING_UI_STORED_FILES_ROOT/test-samples/{uuid}` без TTL. Разметку можно переименовать, удалить,
а тайлы — выключить и включить обратно; ZIP содержит только включённые тайлы.
`TestSampleCreate.creation_mode=manual` создаёт пустую постоянную разметку без нарезки или инференса;
совместимый default `automatic` сохраняет нарезку. Нулевые количества снимков, объектов и территорий допустимы.
Маршрут `#/test-markups/{uuid}/edit` использует тот же `DatasetEditorPage` с отдельным HTTP-контекстом
`/api/v1/test-samples/{uuid}/editor`, без копии карты и изменения MLMarkup. Доступны серверные TIFF выбранного
типа, импорт GeoJSON, эталонные positive-полигоны, типы multiclass, редактирование и удаление снимков.
Личные черновики используют существующую таблицу `dataset_editor_drafts` с изолированным ключом
`test-sample:{uuid}`; общий список черновиков обучающих датасетов их не включает. Публикация проверяет
ревизии GeoJSON, uint8, каналы и EPSG:3857 снимков, обрезает объекты по valid footprint, атомарно обновляет
файлы, class-ID маски и счётчики вместе с транзакцией БД; при ошибке возвращает прежние файлы и черновики.
Исходные TIFF не меняются; RGB-alpha преобразуется в RGB с внутренней маской, Канопус сохраняет RGBNIR.
Производные превью пересоздаются лениво, их URL включает content_revision. F1 получает отдельный
неизменяемый снимок файлов под межпроцессной блокировкой; публикация правок не смешивает ревизии расчёта.
Если публикация заняла хранилище во время подготовки задания, worker откатывает только подготовку
и освобождает строки БД без запуска GPU и ошибки оценки; диспетчер затем перечитывает то же задание.
Явное объединение соседних объектов бинарной выборки создаёт новую редакцию с отдельным UUID через
`POST /api/v1/test-samples/{sample_id}/merge-annotations`. Запрос содержит ожидаемую `content_revision`
и группы существующих feature ID по тайлам. Несовпадение ревизии даёт `409`; удалённые друг от друга
участки, несовпадающие пользовательские свойства и изменение хотя бы одного пикселя маски отклоняются.
TIFF копируются побитово с проверкой SHA-256, состав включённых тайлов сохраняется, контуры и миниатюры
строятся заново. Прежняя выборка, её метрики и исходный MLMarkup не изменяются; новая редакция не назначается
основной автоматически; отдельная штатная оценка запускается вручную, старые объектовые метрики и кэши не переносятся.
Повтор того же запроса возвращает ту же редакцию; файлы новой редакции удаляются при откате её транзакции.
В `annotation_revision.json` сохраняются автор, исходные UUID/ревизия, группы ID и контрольные суммы.
Галерея редактора загружает
отдельные JPEG-миниатюры до `384×384`: отсутствующие строятся непосредственно из уменьшенного TIFF,
маски классов и GeoJSON с отдельными контурами, без создания или декодирования большого PNG. Готовые
совместимые миниатюры исторических наборов используются повторно; собственная версия и ревизия файлов защищают кэш. Полноразмерный PNG загружается только по клику и открывается в модальном
просмотрщике: режим «Вписать» сохраняет пропорции и показывает изображение целиком по обеим сторонам доступной
области, а перемещение работает и при базовом масштабе. PNG сохраняет все пиксели TIFF; размер проверяется
при выдаче. Масштаб подписан относительно исходных пикселей, режим «1:1» доступен и на узком экране. При скачивании тайлы получают
последовательные имена `tile001..tileNNN` независимо от внутренних индексов. Пользователь выбирает полный
состав либо вариант без превью, содержащий строго TIFF и GeoJSON. Полный состав дополнительно включает
PNG-маску и сформированные на лету полноразмерные JPEG-превью с жёлтым контуром разметки и без него:
для трёхканального ортофото
только RGB (`RED, GRN, BLU`), для четырёхканального Канопуса дополнительно NRG (`NIR, RED, GRN`) и
NGB (`NIR, GRN, BLU`); адаптивное качество
ограничивает каждый JPEG размером `300 KiB`. Тестовая разметка принадлежит классу, а сохранённый `dataset_key`
является только неизменяемым указанием, на основе какого датасета сформированы её тайлы. Для класса с объектовой
основной метрикой при создании можно исключить объекты, выходящие за границу тайла. В этом режиме объект включается,
только если его исходная геометрия целиком покрывается footprint тайла; пересекающий границу объект отбрасывается
до подсчёта квот, выбора состава и записи GeoJSON, mask и preview. Настройка сохраняется в batch-запуске и тестовой
разметке, а значение `false` сохраняет прежнее обрезание геометрии по тайлу. При создании набора с оптимизацией,
предварительной оценке и оптимизации его состава используется зафиксированная явная пара: успешная сеть,
обученная на выбранном датасете, и её полная псевдоразметка строго этого же `dataset_key`, включая результат
ручного запуска. Если звезда класса указывает на сеть этого датасета, выбирается она; иначе используется последняя
успешная сеть именно выбранного датасета. Сеть либо псевдоразметка другого датасета класса не подставляется.
Ревизия полигонов датасета
не участвует в проверке пригодности прогноза: проверяются идентификатор сети и фактическое покрытие всех текущих
TIFF по сохранённому списку сцен. Результат другой сети либо результат с неполным покрытием не подходит. Если подходящего
результата нет, редактор показывает выбранную сеть и её обучающий датасет и предлагает идемпотентно запустить
штатную полную псевдоразметку исходного датасета. Для неё
редактор считает пиксельный и объектовый F1 с `IoU ≥ 0,5`; multiclass-оценка возвращает per-class, macro, micro и
foreground-метрики. Один протяжённый объект в разных непересекающихся тайлах считается отдельным объектом в каждом
из них. Общий F1 и F1 каждого типа multiclass показываются раздельно. Черновой расчёт не изменяет сохранённую контрольную метрику, а название, основной статус и полный состав
применяются одной атомарной операцией. Каждый тайл хранит отдельный кэш pixel/object F1 по псевдоразметке для
оптимизатора; карточка выбирает значение по `quality_metric`. Чтение редактора не рассчитывает отсутствующий кэш;
он обновляется при обработке псевдоразметки и явной оптимизации.
PNG-маска тайла остаётся семантической маской классов для пиксельной метрики. При выключенном исключении граничных
объектов GeoJSON сохраняет отдельную feature для каждого обрезанного исходного объекта и без преобразования
копируется в скачиваемый ZIP. Контуры в PNG и
помеченных JPEG строятся отдельно по instance-ID этих feature, поэтому соприкасающиеся объекты визуально не
сливаются. Объектовая метрика также сопоставляет векторные feature один к одному и не восстанавливает объекты как
connected components семантической маски.
Создание одной тестовой разметки доступно на `#/test-markups/create`; форма использует тот же критерий готовности, что и сервер:
набору старого формата нужны TXT и общий GeoJSON положительной разметки, а поснимочному набору — непустой каталог однозначно сопоставленных
с TIFF GeoJSON без диагностик. Мастер и каталог открываются после авторизации без ожидания общих
справочников обучения. Лёгкий индекс классов и счётчиков читается из Postgres без обхода файлов;
мастер запрашивает подробные варианты только выбранного класса. Уже собранное описание датасета
повторно используется для проверки состава псевдоразметки. Каталог читает только карточки выбранного
класса, необходимые поля тайлов и состояния оценки, без файловых проверок готовности оптимизатора;
эти проверки остаются обязательными в редакторе и при запуске. Сверка оценок выбранного класса
выполняется после первого показа и не блокирует карточки. Запоздавший ответ другого класса не
подменяет текущий выбор. На широком экране классы расположены слева, карточки занимают оставшуюся
ширину; на телефоне используется селектор сверху. Выбор сохраняется в браузере и восстанавливается
после обновления; исчезнувший класс заменяется первым доступным. Общий список для скачивания
загружается по нажатию кнопки. Карточный каталог и редактор доступны на
`#/test-markups` и `#/test-markups/{id}`; технические HTTP-контракты сохраняют имена `test-samples`.
Форма выбирает один класс и один его датасет; изменённые параметры сохраняются в строке датасета в Postgres
и возвращаются при следующем открытии. Минимальная площадь объекта в м² (`min_object_area_m2`, по умолчанию 0)
фиксируется в задании; 0 отключает фильтр. Площадь исходного объекта до нарезки считается на эллипсоиде WGS84
после преобразования из CRS GeoJSON, с учётом отверстий и всех частей MultiPolygon. Меньшие объекты исключаются
до поиска кандидатов и подсчёта количества объектов в обоих режимах создания; зоны разметки сохраняются.
Существующие разметки не изменяются. Размеры квадратных тайлов: 512, 768, 1024, 1536, 2048, 2560, 3072,
3584 и 4096–8192 с шагом 512 (по умолчанию 1536).
До создания форма оценивает объём итоговых TIFF для обеих границ количества: площадь тайла × количество
× фиксированные 3 байта/пиксель для Канопуса либо 4 для ортофото, включая сжатие и пирамиды. Тип источника
передаётся в существующем ответе вариантов датасетов; неизвестный тип не подменяется. Оценка приблизительная,
без превью, масок, GeoJSON и выключенного запаса, пересчитывается без чтения растров и дополнительных запросов.
Каждый запрос создаёт одно задание в отдельной очереди нарезки,
которая не является очередью обучения или инференса. Ожидающие задания можно двигать вверх/вниз и удалять;
выполняющееся — только отменять. Отдельный исполнитель `training_ui_api` обрабатывает строго одно задание
за раз; очередь и текущий этап восстанавливаются после перезапуска. Блокировка очереди сериализует постановку,
изменение порядка, отмену и завершение. Отмена проверяется при поиске кандидатов, записи тайлов и перед
публикацией; выполняемый слот освобождается после очистки временных файлов и отката записи разметки.
Для диапазона `Nmin..Nmax` и минимума `M` объектов строится непересекающийся пул до `3 × Nmax` тайлов.
С оптимизацией сохраняется прежний подбор по точной полной псевдоразметке выбранной сети этого датасета,
с целью `3M` объектов в пуле. Без оптимизации случайно выбирается допустимый итоговый состав в заданном
диапазоне с минимумом `M` объектов, а остальные тайлы пула остаются выключенными для ручного выбора;
обученная сеть, её прогноз и предварительная оценка F1 не требуются. Галочка оптимизации недоступна без
успешной сети датасета, пояснение доступно наведением и касанием. Геометрия проходит `make_valid` после
преобразования CRS. При неудаче быстрого поиска MILP проверяет геометрические ограничения и квоты;
допустимый результат принимается только после проверки. Для невыполнимых ограничений показывается
достижимый максимум объектов. На широком экране источник и параметры расположены рядом,
мобильная форма использует два столбца параметров; списки датасетов и
заданий отображаются целиком без внутренних вертикальных прокруток и ограничения высоты. Очередь
показывает все ожидающие и выполняемые задания, дополняя список последними завершёнными до пяти строк;
без активных заданий видны пять последних завершённых, при количестве активных более пяти история скрыта.
Для каждой сохранённой тестовой разметки, включая неосновные разметки и датасеты `main`, `test`, `strict` и
архивные строки того же класса, итоговые pixel/object-метрики рассчитываются прямым инференсом эффективной
сети класса. Задание `test_sample_f1` с `metric_target=test_sample` проходит через общую
inference-очередь, обрабатывает только включённые TIFF и сохраняет агрегированные TP/FP/FN, threshold и
multiclass-структуру в `test_samples`; поснимочный кэш псевдоразметки при этом не заменяется. Оценка актуальна только
для той же эффективной сети, ревизии состава, эффективного inference-шаблона, профиля и версии алгоритма. Смена
эффективной сети, шаблона или состава, создание набора и старт сервиса не запускают инференс; сверка только
отмечает устаревшие оценки. Страницы опрашивают уже активное задание. Старые значения сохраняются с
признаком устаревания, результат потерявшего актуальность задания отбрасывается, а ошибка той же сигнатуры не
перезапускается автоматически до ручной команды.
Размер TIFF тестовой разметки задаёт только площадь итогового сравнения и никогда не подменяет размер входа сети.
Каждый включённый TIFF полностью покрывается окнами модели: для нативного checkpoint размер полного входа и context
берутся из его metadata, а для старого checkpoint без этих полей — из исходного задания обучения. При ненулевом
context шаг равен полезному центру; граничные окна читаются с padding, но в итог записывается только пересечение
центра с TIFF. Поле `JobRow.tile_size` и служебные `inference_*` задания F1 фиксируют именно фактическое окно сети,
а не ширину тестового тайла.
Для класса может быть не более одной основной тестовой разметки. Для обычных датасетов она применяется к успешным
сетям всех датасетов этого класса. Для управляемого датасета исполнитель собирает основные разметки его исходных
классов, сопоставляет их с ID/slug выходных каналов и считает каждый класс только на его собственной выборке;
общий pixel/object F1 равен арифметическому среднему соответствующих поклассовых F1. Исполнитель проверяет
канонический класс, схему типов и идентификаторы текущих основных разметок, но
не требует совпадения исходного датасета её тайлов с датасетом обучения сети. По ней для каждой успешной сети считаются
отдельные пиксельный и объектовый F1: задание с назначением `test_sample_f1` проходит через общую inference-очередь, загружает
best checkpoint с threshold либо внешний ZIP без вымышленных метрик, применяет действующий inference-шаблон и независимо обрабатывает каждый
включённый TIFF-тайл. Компоненты прогноза, касающиеся границы TIFF, считаются обрезанными фрагментами и не
удаляются фильтрами минимальной площади и компактности; для внутренних компонентов inference-шаблон применяется
полностью. Для ЗУ500 объектовая метрика использует настоящие instance ID вместо connected components. Внешнее
предсказание сначала выполняется в разрешении модели, затем возвращается в исходную сетку TIFF. TP/FP/FN
суммируются без объединения совпадающих географических областей. Метрика хранится в Postgres,
не пишется в MLflow и считается актуальной только для тех же `sample_id` (либо полного набора `sample_id` для
управляемой сети), ревизии состава, профиля и версии
эффективного inference-шаблона и алгоритма оценки. Результат показывает метрику, сохранённую вместе с запуском
обучения. Только успешное завершение обучения автоматически ставит оценку новой сети; если она стала
эффективной сетью класса, также ставятся её прямые оценки тестовых разметок. Исторические сети, смена
основной разметки, состава, сети, профиля или шаблона, создание псевдоразметки и старт сервиса не запускают
пересчёт. Сохранённое число остаётся с отметкой устаревания. Круговая стрелка рядом с F1 вызывает
`POST /api/v1/results/training/{result_id}/test-f1` для выбранной успешной сети либо явный `/evaluate`
для основной сети класса в карточке тестовой разметки; повтор активного расчёта не создаёт дубль.
Одна ручная команда на странице результатов датасета
ставит оценки всех его успешных сетей с обычным ручным приоритетом и повышает приоритет уже ожидающих фоновых оценок
без дубликатов; автоматическая сверка не понижает такие ручные задания. Команда доступна и во время расчёта.
Круговая стрелка ожидающей оценки позволяет перевести её из фоновой очереди в обычную ручную;
после нажатия повтор блокируется до смены состояния, выполняющаяся оценка не дублируется.
Приостановленный F1 остаётся активным при сверке и повторном ручном запросе; в карточке оценки
показывается как выполняющийся, в очереди — как приостановленный. Повышение не меняет PID;
отмена неактуального расчёта завершает также приостановленный процесс.
Для управляемой сети изменение основной выборки одного исходного класса только помечает F1 неактуальным.
Явный полный пересчёт оценивает весь текущий состав. Низкоуровневая очередь сохраняет поддержку явно заданного
частичного пересчёта semantic-канала с атомарной заменой его метрик и пересчётом невзвешенного среднего;
при отсутствии полной поклассовой структуры требуется полный расчёт. Устаревший результат задания
отбрасывается без автоматической постановки нового; ошибка не повторяется без ручной команды.
Тестовый F1 в карточке датасета и строке сети открывает `#/test-f1/<training_result_id>`. Просмотр использует карту,
TIFF, Range, ограниченный растровый кэш, каналы и полный экран существующего просмотра псевдоразметки.
Общий просмотрщик использует пропорции редактора датасета: компактная шапка с оценками F1 справа и большая
карта. У общей и поснимочной оценок явно указан тип F1: пиксельный или объектовый. Иконки снимков, разметок,
показа всего снимка и меню RGB/NRG/NGB находятся на карте, легенда — внизу
внутри неё. Прозрачность фиксирована; ползунка нет. Та же компоновка сохраняется в полном экране и на телефоне.
При расчёте сохраняются сжатые эталонная и предсказанная маски каждого независимого TIFF, исходные идентификаторы
объектов и пары их сопоставления из того же расчёта объектового F1, его геопривязка,
ревизия исходного файла, имя/ревизия выборки и фактические поснимочные pixel/object TP/FP/FN. Worker переносит
артефакты из scratch в `stored_files_root/test-f1/<job_id>` до очистки; `metrics.viewer_jobs` связывает оценку с
этими запусками. Частичный managed-пересчёт заменяет только ссылки своего класса, сохраняя остальные.
GET не ставит заданий. Историческая оценка без масок или сохранённых объектов получает явную кнопку подготовки: идемпотентный POST
ставит один полный штатный F1-job выбранной сети, карта появляется после успешного расчёта. Сохранившийся
устаревший снимок оценки доступен с предупреждением; новая разметка не подставляется под старый прогноз.
Авторизованные view/layers/raster/footprint-маршруты разрешают только артефакты этой сети и TIFF из test-samples;
изменённый TIFF даёт 412, удалённый допускает просмотр слоёв без подложки. Каждый снимок выбирается отдельно,
даже если географические области совпадают. Эталон и прогноз переключаются независимо; совместное отображение
окрашивает TP/FP/FN в зелёный/красный/жёлтый. На карте переключается пиксельный или объектовый режим:
первый показывает точное пересечение масок, второй — полные сопоставленные объекты, лишние прогнозы и
пропущенные эталоны. Обе оценки F1 показаны одновременно, счётчики и легенда соответствуют выбранному режиму.
Multiclass позволяет выбрать тип, managed-снимок сравнивает только свой канал. Переключение использует
сохранённые артефакты без повторного инференса; страница не ожидает загрузки общего справочника датасетов.
Полигонизация слоёв использует одну среду GDAL на запрос без повторной инициализации на каждый объект.
Геометрии передаются без упрощения и потерь через gzip; кэш готового сжатого JSON ограничен 64 МиБ
и различает ревизии масок и исходного эталона, геопривязку, класс, схему и режим метрики. Приватный
HTTP-кэш обязан перепроверять ETag; ответ 304 разрешён только после авторизации и проверки принадлежности
снимка сети. Общий просмотрщик разбирает полученный GeoJSON один раз, включая первое открытие.

Класс может хранить явную ссылку на основную успешную сеть, которую пользователь назначает звездой на странице
результатов и снимает повторным нажатием на заполненную звезду. Снятие очищает ссылку, но не удаляет результат.
Если ссылка отсутствует, эффективной считается последняя успешная сеть среди всех датасетов класса:
этот выбор не записывается в БД и не показывает звезду. Завершение обучения также не назначает звезду, но при
смене неявно выбранной последней сети запускает сверку зависимых метрик. Эффективная сеть используется групповым экспортом,
публичным тестовым F1 класса, прямой оценкой всех тестовых разметок класса и AOI-инференсом QGIS. Создание и
последующая оптимизация тестовой разметки используют зафиксированную сеть выбранного датасета и её точную
псевдоразметку. Поснимочная подсказка редактора датасета является отдельным
контекстом: использует основную сеть только своего датасета либо его последнюю успешную сеть, чтобы переиспользовать
его готовую полную псевдоразметку. При отсутствии такой сети редактор сообщает об этом. Редактор тестовой разметки явно показывает имя сети и датасет её
обучения как для сохранённой метрики, так и для поставленного нового расчёта.
Плашки датасетов в каталоге результатов расположены внутри класса по убыванию времени последнего успешного
обучения, независимо от выбора основной сети; для исторических результатов без `trained_at` используется
`created_at`. Датасеты без успешного обучения идут последними, при одинаковом времени порядок задаётся
названием и ключом датасета. Под названием класса строка «Обновлено» не отображается.
Каталог результатов выделяет назначенный основной датасет класса и выбирает сеть отдельно для каждой карточки:
если явно отмеченная основная сеть обучена на этом датасете, используется она, иначе — последняя успешная сеть
этого датасета. Метрика каждой выбранной обычной сети берётся из оценки по основной тестовой разметке класса, а
управляемой сети — из составной оценки по основным разметкам всех классов-источников с отдельными поклассовыми F1
и их средним; основная сеть одного датасета не подменяет F1 остальных датасетов и отдельный инференс при открытии
каталога не запускается. Страницы результатов читают свои данные без ожидания общего `bootstrap`;
справочник для запуска псевдоразметки, продолжения обучения и экспорта загружается при открытии диалога.
Сохранённые метрики, необходимые основные разметки с тайлами, классы, шаблоны и задания читаются пакетно,
повторные проверки в одном HTTP-запросе используют этот снимок данных. Между запросами он не кэшируется;
проверка текущих ревизий и сигнатуры оценки сохраняется. Синхронизация каталога читает уникальные исторические
ключи, без выгрузки дубликатов из всех заданий и результатов.
Поклассовые метрики multiclass во всех карточках и подробных таблицах отображаются по
русскому алфавиту названия типа, независимо от порядка ключей в сохранённом JSON.
На странице результатов обучения тот же временный zip-экспорт доступен для успешного training result: сервис
скачивает нативный `checkpoints/best.pt` либо исходный ZIP импортированной модели из MLflow. Для внешней модели
безопасно переименовываются корневая папка и `config.pbtxt`, добавляется профиль pipeline; общий batch может
содержать оба вида результатов.

Каноническое место хранения результатов обучения — MLflow. Локальные директории используются как временная
рабочая область, кроме явно постоянных файлов UI: загруженных файлов и тестовых разметок в
`MLSYSTEM2_TRAINING_UI_STORED_FILES_ROOT`.

## Конвейер Обучения

В Гровике выбираются архитектура, `legacy`, `next_gen2`, `next_gen3` или `next_gen4` и галочка «Предобученные веса».
Четыре SegFormer B0/B1/B2/B3 используют SMP и поддерживают эти конвейеры; у остальных сетей доступен `legacy`.
Галочка управляет `train.pretrained`: включённая загружает ImageNet-веса соответствующего MiT encoder,
выключенная оставляет случайную инициализацию всей сети. Голова создаётся заново в обоих случаях.
Выбор весов сохраняется при смене конвейера, SegFormer и датасета. В legacy с предобученными весами
модель делит raw-вход на 255 и нормализует RGB по ImageNet mean/std; NIR использует параметры RED.
Эта обёртка определяется сохранённым ModelSpec.pretrained, работает в checkpoint и ONNX и не маскирует nodata.
Прежний legacy без предобучения сохраняет raw-вход. HF не предлагается для новых ручных и автоматических
обучений; его исторические задания, результаты, checkpoint, шаблоны инференса, псевдоразметка и экспорт сохраняются.
Явный выбор конвейера сохраняется при смене архитектуры или датасета, если он поддерживается;
для multiclass доступны `legacy`, `next_gen2`, `next_gen3` и `next_gen4` у SegFormer B0/B1/B2/B3. Профиль берётся из шаблона выбранной архитектуры.
`next_gen` снят с новых ручных и автоматических запусков: его поля убраны из схемы формы,
старые шаблоны переводятся на `next_gen2` при штатном обновлении каталога.
Исторические jobs, MLflow и checkpoint сохраняют `next_gen`; его исполнение и чтение оставлены
для уже созданных заданий и результатов. Новые HTTP API и миграции БД не требуются.
`train.pipeline_variant` в контрактах — `legacy|next_gen|next_gen2|next_gen3|next_gen4|object_f1|object_f1_v2`. Конфигурация и checkpoint без
этого поля всегда трактуются как `legacy`; его оконный split, balanced validation, аугментации только
positive/hard-negative, cosine scheduler, пороги и обработка nodata не меняются. `next_gen` не является
отдельным верхнеуровневым модулем: он реализован приватными ветками тех же фасадов `settings`,
`dataset_preparing`, `tile_preparation`, `models`, `train`, `train_pipeline`, `mlflow_adapter` и
`training_ui_api`. Первая версия допускает только binary Kanopus с четырьмя каналами
`RED, GRN, BLU, NIR` и архитектурами `smp_segformer_b0` или HF `segformer_b0`.

`next_gen` делит целые сцены на детерминированные fold по SHA-256 `seed+scene_id`; число validation-сцен
равно `max(1, floor(scene_count × val_fraction + 0.5))`. Пространственный purge исключает train-окно,
если полный вход пересекает valid footprint held-out сцены, расширенный на пиксель исходного TIFF.
Validation содержит все оставшиеся окна held-out сцен в естественном соотношении. Valid-mask исключает
nodata, raster mask и padding из loss и метрик. Preprocessing (`scale_255`,
`imagenet_rgb_red_nir`, `robust_percentile`) находится внутри model wrapper; robust p2/p98 рассчитывается
потоковой 256-bin histogram только по train-сценам.

HF B0 с `train.pretrained=true` загружается из
`nvidia/segformer-b0-finetuned-ade-512-512` на закреплённой revision
`489d5cd81a0b59fab9b7ea758d3548ebe99677da`: RGB-ядра первого convolution копируются, NIR получает RED,
а head заменяется на один logit. Полная HF-конфигурация сохраняется в `ModelSpec`; локальная загрузка
checkpoint строит модель из неё без Hugging Face Hub. В `next_gen` AdamW сочетается с
`ReduceLROnPlateau` по scene-macro pixel F1. Полная validation выполняется на эпохе 1, затем по заданному
интервалу и перед штатным завершением; patience измеряется validation-событиями. Порог либо фиксирован,
либо выбирается по 4096-bin histogram с tie-break по precision и большему threshold. Опциональный Gaussian
A/B выполняется только после обучения на лучшем checkpoint и не меняет production core-crop, ONNX или
Geoalert metadata.

`next_gen2` использует профиль `segFormer_train_hlam_main_v2.ipynb` внутри существующих модулей.
Он поддерживает бинарные и мультиклассовые датасеты Канопус (RED, GRN, BLU, NIR) и ортофотопланов (RED, GRN, BLU),
HF SegFormer B0 или SMP SegFormer B0/B1/B2/B3. Бинарная голова имеет два logits; мультиклассовая — N+1 по схеме, включая фон.
Исторический HF B0 сохраняет закреплённые веса ADE20K; SMP с включённым предобучением использует
соответствующий MiT encoder с весами ImageNet из smp-hub и новую голову по схеме датасета.
Без предобучения сеть инициализируется случайно, остальные параметры конвейера не меняются.
При предобучении для Канопус RGB-ядра копируются, NIR получает RED,
bias новой свёртки остаётся случайным; RGB сохраняет исходную предобученную входную свёртку целиком. Внешний бинарный выход
сохраняет разность logits, мультиклассовый — все N+1 logits; checkpoint загружаются без обращения к Hub.
Размер полного окна выбирается из 512, 768, 1024, 1536 (default 512); шаг всегда равен половине размера.
Контекст, дополнение краёв и фильтрация nodata отсутствуют. Каналы и размер сохраняются в checkpoint и экспорте.
Два последовательных случайных разбиения с seed 42 дают 60% train, 20% validation и 20% test.
Порядок и округление совпадают с `train_test_split(0.4)` и `train_test_split(0.5)` ноутбука.
Spatial purge не применяется: общие пиксели перекрывающихся тайлов могут оказаться в разных выборках;
это ограничение явно указано в описании профиля. Manifest сохраняет координаты и индексы трёх выборок.
Общий hard negative перекрывает positive и считается фоном. Class-specific отрицательные области исключены из полного
CE/Tversky и частот фона, штраф `-log(1-p_class)` относится только к назначенным типам; valid mask ограничивает оба loss.
Все маски синхронно аугментируются. Только по train рассчитываются обратные частоты
всех классов и фона со средним весом 1. WeightedRandomSampler с возвращением назначает вес 7 при доле любого типа >0.001,
вес 8 любому тайлу с hard negative и 1 фону. Это веса отдельных тайлов, не доли категорий.
Ко всем train-тайлам до min-max применяются Albumentations: H/V flip и RandomRotate90 с p=0.5,
affine scale 0.9–1.1/translate ±32/rotate ±15 с отражёнными границами и p=0.4,
OneOf шум (дисперсия 5–30)/Gaussian blur (3–5) с p=0.3 и яркость/контраст ±0.15 с p=0.3.
Неподдерживаемые параметры исходного ноутбука заменены действующими эквивалентами Albumentations 2.
Нормализация каждого канала каждого окна — min-max; постоянный канал становится нулём.
Validation и test полные, без аугментаций и сэмплирования. Batch определяется архитектурой и окном
512/768/1024/1536: B0 — 16/8/4/2, B1 — 8/4/2/1, B2/B3 — 4/2/1/1. Для инференса batch вдвое больше;
его выбор учитывает архитектуру checkpoint. На RTX 5090 проверены шаги FP32 обучения всех пяти сетей
со всеми размерами; максимальный замер — 23,6 ГиБ для SMP B3, 1536, batch 1. Это фактический batch без накопления градиентов;
уменьшение batch меняет число optimizer steps за эпоху, сохраняя формулу loss. Float32, AdamW LR 1e-4,
weight decay 0.01, без gradient clipping. Loss — 0.25 × weighted CrossEntropy + 0.75 × SMP multiclass
Tversky (alpha 0.75, beta 0.25). Полная validation каждую эпоху; scheduler
`ReduceLROnPlateau(mode=min,patience=3,factor=0.5)`, best и early stopping используют validation loss.
При равенстве сохраняется ранняя эпоха. После штатного обучения best один раз проверяется на test
при пороге 0.5; для multiclass сохраняются per-class, macro, micro и foreground pixel F1 без поиска другого порога.
Результаты пишутся в MLflow как `test/*` и `reports/test_metrics.json`.
Новые runs получают `checkpoint_selection_metric=val_loss`; исторические теги `quality_f1` продолжают
читаться по F1. История запусков и сохранённые модели не изменяются.
В UI изменяемы предобученные веса, размер тайла, максимум эпох (default 20), early stopping patience (10) и максимальная
длительность (без лимита). Остальной профиль закреплён в интерфейсе, обработке шаблонов, worker и settings;
старые шаблоны next-gen2 однократно получают новые defaults, последующие изменения размера и условий сохраняются.
Подсказка объясняет особенности кратко, подробное описание с визуализацией тайла находится внизу формы.
Seed остаётся 42; число DataLoader workers относится к серверному исполнению и наследуется из settings.yml
(8 на сервере) для train/validation/test. Prefetch ограничен двумя batch на worker, persistent_workers=False;
при CUDA используется pinned memory. Каждый worker инициализирует собственный RNG Albumentations через
worker_seed, ограничивает OpenCV одним потоком и отключает OpenCL. Воспроизводимость аугментаций сохраняется
при одинаковых seed и числе workers; основные Torch pools остаются 4/2. Фактические параметры загрузчиков
выводятся в журнал и сохраняются в loader_runtime отчёта tile_preparation в MLflow.
Псевдоразметка и контрольная оценка сохранённых моделей
сохраняют отдельный eval-профиль: Gaussian merge и строгий порог >0.9, inference batch 32/16/8/4 по размеру окна.
Multiclass усредняет N+1 вероятностей до argmax; порог применяется к победившему foreground. ONNX/Triton возвращают
N+1 FP32 вероятностей. После `SlidingWindowSegmentation` брик `MulticlassProbabilityMasks` выбирает одну метку
с учётом фона и формирует отдельные маски типов. Расширения и инструкция входят в переносимый ZIP.
Очереди, пауза, остановка с
сохранением, экспорт и прежние варианты обучения работают через существующие фасады.

1. CLI получает стабильный `settings.yml` через `--settings` и задание конкретного обучения через `--run`, вызывает `settings.api.load_settings(settings_path, run_path)` и инициализирует текущие настройки процесса. Совместимый legacy-режим `--config` остается для старых полных YAML.
2. Создать или открыть запуск MLflow через `mlflow_adapter` и записать YAML задания запуска в артефакты.
3. `dataset_preparing` принимает локальные пути, проверяет подготовленные TIFF, число каналов и `uint8`, затем возвращает список независимых `PreparedScene`. При проверке явно описанных каналов `GREEN/GRN` и `BLUE/BLU` равнозначны без учёта регистра и окружающих пробелов; порядок остаётся строгим, TIFF не изменяется. Поддерживаются legacy binary/multiclass и per-image binary/multiclass через `dataset.annotations_dir`; multiclass-схема читается из manifest. Общие растровые мозаики не создаются; перекрывающиеся TIFF остаются независимыми.
4. Если `dataset_preparing` вернул ошибки, `train_pipeline` записывает отчет подготовки в MLflow и
   завершает конвейер с ошибкой.
5. После успешной подготовки `train_pipeline` сохраняет в MLflow legacy TXT/GeoJSON либо все per-image GeoJSON вместе с manifest в `dataset/`.
6. `train_pipeline` вызывает `tile_preparation.create_tile_dataloader` для train и val со списком сцен и одинаковым `tile_split`. В `legacy` split детерминирован по `scene_id+x+y`, train использует прежний category-aware sampling, а val — фиксированный balanced subset. В `next_gen` split выполняется по сценам со spatial purge, train sampler зависит от epoch/draw, а val всегда полный и несбалансированный. Binary mask: `-1/0/1`, multiclass: `-1/0/1..N`; геометрические аугментации синхронно преобразуют image, target и valid-mask.
7. `train_pipeline` создаёт одну из девяти UI-архитектур SMP. Для SegFormer B0/B1/B2/B3 предобученные веса выбираются независимо от конвейера; HF остаётся для исполнения и чтения исторических заданий. Спецификация checkpoint обязана совпадать с запросом, поэтому варианты, preprocessing и число каналов нельзя перепутать. Для multiclass `train.output_channels` строго равен числу manifest-классов плюс background.
8. `train` выполняет PyTorch обучение segmentation-модели, validation, early stopping и best/final checkpoints. `legacy` сохраняет AdamW с cosine scheduler и прежние binary/multiclass loss и пороги; `next_gen` использует AdamW с `ReduceLROnPlateau`, полную validation и scene-macro pixel F1. Для binary рассчитываются пиксельная и объектовая F1; `train.quality_metric` выбирает метрику best checkpoint и early stopping в `legacy` и `next_gen`; `next_gen2` использует минимум validation loss. Объекты сопоставляются один к одному при `IoU ≥ 0,5`. Для multiclass основной score — macro pixel F1 по типам. В `legacy` nodata представлен target background `0` и входит в loss и TP/FP/FN; в `next_gen` valid-mask полностью исключает его из этих расчётов. `background_weight`, `pos_weight` и `hard_negative_weight` сохраняют прежнюю семантику на valid pixels. Binary checkpoint остаются совместимыми; next-gen metadata дополнительно содержит variant, preprocessing, band contract, split/fold, scheduler, threshold policy, pretrained provenance и dataset/code revision.
9. `train_pipeline` передает в `train` progress sink. Train-loss пишется для каждой завершённой эпохи; val-метрики `next_gen` существуют только для эпох с полной validation.
10. `mlflow_adapter` записывает итоговые метрики, checkpoint, SHA-256, resolved JSON, split manifest, preprocessing, runtime/CUDA/packages/dataset revision, per-scene validation, optional Gaussian comparison, tile/timing и итоговый отчёты.

`mlflow_adapter` сопровождает каждую публикуемую метрику русским описанием в
`reports/metric_descriptions.html` и `.json`; в Description запуска добавляет ссылку, сохраняя
пользовательский текст. Справочник содержит формулу, назначение, единицы, ориентир и особенности
агрегации/порога выбранного конвейера; HTML показывает подсказку при наведении на название.
Штатные имена, значения, шаги и алгоритмы расчёта не меняются. Обновляются только метаданные при
изменении набора метрик; после завершения выполняется контроль с учётом отложенной записи MLflow.
Справка не должна прерывать обучение. Публичный
`mlflow_adapter.api.log_metric_descriptions` позволяет дополнить завершённый или текущий запуск
без повторного старта, завершения и изменения весов. Собственная сборка интерфейса MLflow не нужна.

## Конвейер next-gen4

`train.pipeline_variant=next_gen4` наследует автоматический фон, loss, optimizer, scheduler и полную
validation/test next-gen3. Размер окна остаётся выбираемым: 512/768/1024/1536; шаг подготовки равен
размеру окна, context=0. Сетка привязана к (0,0) исходного TIFF, краевые окна дополняются nodata.
Зоны одного TIFF используют общую сетку. Случайный split 60/20/20 назначает все зональные представления
одного исходного тайла одной части. По сценам данные не делятся; пересечения разных TIFF разрешены.
Manifest содержит `grid_policy=non_overlapping_padded_v1`, `split_unit=source_tile`, число исходных
тайлов и проверку `same_source_overlap_pairs=0`. Соседние тайлы и разные съёмки одной территории
не гарантируют независимость территорий; обычная тестовая разметка внутри train также не становится
независимой автоматически. Остальные варианты обучения и существующие шаблоны не переключаются.

Нативный, ONNX и Triton checkpoint next-gen4 сохраняют `mask_output_nodata=true` в preprocessing:
вход с нулём во всех модельных каналах даёт фон. Raster mask/alpha дополнительно учитывается
исполнителем инференса. Gaussian-инференс сохраняет шаг половины окна, отдельно от обучающей сетки;
next-gen4 дополняет края для полного покрытия. Невалидные пиксели не участвуют в накоплении весов,
а вход next-gen4 обнуляется под raster mask до нормализации, как при обучении;
результат обнуляется после морфологии и обрезается по valid footprint после геометрических фильтров.
Тот же nodata-fix применяется к новым инференсам существующих next-gen2/3 весов без изменения весов
и исторических обучающих метрик. Сохранённые предсказания не переписываются; сигнатура текущей
тестовой оценки меняется на `notebook_valid_data_v2`. Переносимый ZIP содержит тот же приватный
код маски валидности и финальный брик `ClipToRasterValidData`.

## Конвейер next-gen3

`train.pipeline_variant=next_gen3` — отдельный вариант автоматического подбора фона внутри существующих
модулей; прежние варианты, шаблоны и результаты не переключаются. Архитектуры SegFormer, RGB/RGB+NIR,
размеры тайла, min-max, loss CE/Tversky, AdamW, scheduler по val loss, полная validation каждую эпоху
и однократный test лучших весов наследуют next-gen2. Изменений верхнеуровневых модулей, HTTP API и БД нет.
Политика `adaptive_background_v1` не требует ручных коэффициентов; её параметры фиксируются в ModelSpec.

Сэмплер видит только train после исходного оконного разбиения 60/20/20. Любой допустимый пиксель объекта
делает тайл положительным. Nodata, raster mask, территория вне зоны и заполнение геометрической аугментации
исключены из loss и метрик; частично отрицательный multiclass не считается подтверждённым пустым фоном.
Частоты классов вычисляются только по допустимым train-пикселям, включая малые объекты. Пусть P — число
информативных тайлов (положительные и частично отрицательные), B — допустимых полностью фоновых, S — снимков.
Резерв фона C=min(B,max(8P,256,32S)), неизменный бюджет эпохи N=min(P+C,20P), не больше допустимого train.
Ограничение 20P защищает крайне редкие объекты: большой резерв охватывается ротацией, а не сотней повторов.
Каждый информативный тайл показывается минимум один и максимум четыре раза; фон внутри эпохи уникален.
При наличии фона квота ограничена снизу min(C,max(1,ceil(0.25N),N−4P)), сверху min(C,N−P,floor(0.9N)); начальное значение — ближайшее допустимое
к N/2. При B<P берётся весь фон. Нет train-пикселей объектов — понятная ошибка до обучения.

Обычный фон ротируется по снимку и пространственной зоне размером четыре тайла; циклические курсоры и
детерминированные перестановки постепенно охватывают весь пул. До 25% фоновой квоты получают явные hard
negative и ошибки пустых train-тайлов, наблюдавшиеся в обычном forward, без дополнительного обхода GPU.
Оценки сложности сглаживаются 0.3/0.7. Не меньше 75% квоты остаётся ротационной выборкой; сложные примеры
не вытесняют всё разнообразие. Seed аугментации включает общий seed, эпоху, draw, сцену и координаты,
поэтому повторные выборы меняются воспроизводимо независимо от назначения worker.

`tile_preparation.contracts.AdaptiveSamplingController` задаёт управление train-сэмплером, а
`SamplingFeedback` — исключительно агрегированные счётчики полной validation. `train` не импортирует
частные загрузчики. На фиксированном пороге 0.5 измеряются FP/допустимые пиксели полностью пустых тайлов,
доля пустых тайлов с FP не меньше max(4,ceil(valid_pixels×0.0001)) и TP/положительные пиксели. Для multiclass
foreground означает любой известный тип; неизвестные частично отрицательные области исключены.
EMA имеет alpha=0.3. Две первые эпохи — прогрев. Затем падение сглаженной полноты больше 0.05 от лучшей
имеет приоритет и уменьшает фон; иначе pixel FPR>0.001 или tile FPR>0.1 увеличивают его. При обоих FPR
ниже половины этих границ фон уменьшается. Шаг round(0.05N), минимум один тайл; квоты имеют приоритет.
Эталон лучшей полноты фиксируется только при обоих сглаженных FPR в допустимых пределах: почти
сплошной foreground с полнотой около единицы не становится якорем и не блокирует уменьшение FP.
Недостаточный фон или объекты validation замораживают коррекцию. Test никогда не обновляет контроллер;
validation используется для настройки, не является внешним независимым тестом.

Checkpoint metadata и `reports/adaptive_sampling.json` сохраняют политику, seed, курсоры, train-оценки,
историю квот, ошибки и причины. `EpochMetrics.adaptive_sampling` содержит компактный снимок; MLflow пишет
числовые sampling/FPR/recall-графики и поэпохальные JSON. Продолжение от весов — новый этап с новым
контроллером, optimizer и scheduler, не восстановление прерванной итерации. Инференс и экспорт сохраняют
ABI next-gen2 (Gaussian, исходная сетка, порог 0.9), но точный вариант в metadata остаётся `next_gen3`.
Обучающие оценки при 0.5 нельзя выдавать за оценку production при 0.9. Оконные пересечения между частями
по-прежнему возможны: next-gen3 не обещает географическую независимость. Для неполной разметки нужны
подтверждённые зоны; автоматический баланс не исправляет пропущенные полигоны и не гарантирует прирост F1.

Точные train-частоты и категории next-gen3 рассчитываются существующим ограниченным пулом статистики
в `tile_preparation`, до восьми процессов по `num_workers`; возвращаются только счётчики, не растры.
Порядок окон/суммы сохраняются при 0/1 и нескольких процессах. Старые объектные цели и веса не меняются.

## Конвейер Инференса

1. CLI получает путь `--config`, вызывает `settings.api.load_settings` и инициализирует текущие настройки процесса.
2. Загрузить модель или чекпойнт и определить точное число входных каналов из `ModelSpec`.
3. Выполнить инференс напрямую в Python/PyTorch по локальной папке `dataset.images_dir`; снимок с несовпадающим числом каналов отклоняется без обрезки или дополнения каналов.
4. Записать результаты и отчеты в MLflow.


## Конвейер object f1

`train.pipeline_variant=object_f1` — отдельный фиксированный профиль SegFormer B0/B1/B2/B3 (`smp_segformer_b0`…`smp_segformer_b3`) на основе next-gen2. В UI он доступен всем четырём архитектурам, с соответствующим encoder MiT и независимой галочкой предобученных весов; legacy/next-gen2 и исторические HF checkpoint сохраняются. Доступны тайлы 512/768/1024/1536 и три условия остановки. Batch size выбирается по архитектуре и размеру тайла: B0 — 16/8/4/2, B1 — 8/4/2/1, B2 и B3 — 4/2/1/1. Нормализация min-max, sampler 7/8/1, FP32, AdamW 1e-4/0.01 и серверные workers/prefetch наследуются из next-gen2.

Разбиение `scene_groups` с seed 42 выделяет примерно 60/20/20 по целым снимкам. Пересекающиеся valid footprints образуют неделимую группу, требуется минимум три группы. Manifest фиксирует группы и части. Polygon — объект; части MultiPolygon получают разные постоянные ID. Порядок записей разрешает пересечения, их пиксели и соседняя полоса исключаются из loss границ. Разметка источника не меняется.

Профиль принимает RGB, RGB+NIR и RGBA с тремя модельными каналами: alpha задаёт valid mask, не NIR. Разрешение RGB+alpha в подготовке задаётся явно `allow_rgb_alpha`; прежние профили сохраняют строгую проверку числа каналов. DataLoader получает `input_channels`. Общие геометрические аугментации применяются к изображению, ID, valid и conflict mask; заполнение affine для этого профиля нулевое и исключено из loss. Внутренние границы толщиной 2 px вычисляются после геометрии, края окна не становятся целевыми границами.

Модель имеет два logits области и один независимый logit границ на общем decoder. Семантический `ModelSpec.output_channels=1` сохраняется; `output_layout=background_foreground_boundary` явно задаёт внутренний ABI. Loss: прежние 25% weighted CE + 75% Tversky (0.75/0.25), плюс 0.5 × (0.5 BCE + 0.5 Dice) границ; только valid pixels. Scheduler следит за суммарным val_loss. Best/early stopping — максимум object F1, при равенстве ранняя эпоха. Полная validation каждую эпоху собирает сцены до расчёта метрик. Сопоставление один к одному при IoU ≥ 0.5, TP/FP/FN суммируются. Test использует best один раз, не влияет на обучение.

Общий CPU API `inference` собирает два канала вероятностей Gaussian-весами и выполняет watershed с сохранением ID. Область ≥0.5, маркеры внутри области с границей <0.5, связность 4, минимум маркера 4 px. Если маркеров нет, остаётся один объект. Полное покрытие краёв, nodata исключён. Дисковые карты и обработка bbox компонентов ограничивают RAM. Каждый ID векторизуется отдельно, фильтры геометрии применяются к объектам; NMS удаляет межсценовые дубли без объединения соседей. Для object_f1 существующий алгоритм вызывается только внутри групп реально пересекающихся объектов разных снимков; независимые объекты не проходят через накопление unary_union.

Ортофото по-прежнему проходит Geoalert/Triton. Зарегистрированный `ObjectF1Segmentation` использует общий CPU API после инференса вероятностей, `VectorizeMasks` сохраняет `instance_id`. ONNX отдаёт [foreground,boundary] float32; metadata и версия кэша отличают его от бинарного выхода. MLflow сохраняет существующие object/pixel-метрики, LR и компоненты loss; quality-дубли не добавляются. Новых HTTP API, таблиц или миграций нет.

## Конвейер object f1 v2

`train.pipeline_variant=object_f1_v2` — отдельный бинарный профиль SMP SegFormer B0/B1/B2/B3 в тех же модулях и формах запуска/шаблонов. Старые профили, checkpoint и метрики не переинтерпретируются. Предобучение, RGB/alpha/Канопус, размеры окон, полные эпохи, Gaussian-сборка, scheduler и независимые `scene_groups` наследуют объектный профиль; требуются минимум три независимые группы. Новых верхнеуровневых модулей, HTTP API и таблиц нет.

Источники GeoJSON сохраняются. Стабильная растеризация разрешает наложения по постоянному порядку объектов; небольшое наложение больше не исключает общий шов из обучения. Дубли и существенные перекрытия отражаются в диагностике разметки. После общей геометрической аугментации из полных ID строятся три взаимоисключающие цели: фон, внутренняя часть, внутренняя полоса границы до 8 px. Для узкого объекта ширина адаптивно ограничивается половиной внутреннего радиуса, чтобы сохранить сердцевину. Края вырезки и nodata не становятся границами. Разметка площади и эталонные ID не сужаются.

Модель возвращает три сырых logits, `output_layout=background_interior_boundary`, логическое `output_channels=1`. Loss — 0.25 weighted CrossEntropy + 0.75 трёхклассовый Tversky (0.75/0.25), только допустимые пиксели. Три обратных частотных веса вычисляются исключительно по train; вес границы дополнительно умножается на 3, отсутствующий класс не подавляет остальные. Счётчики/веса сохраняются в manifest. `region_loss` и `boundary_loss` в этом профиле — диагностические Dice-loss полной площади и полосы, а не слагаемые общей функции потерь.

Вероятность области равна сумме softmax внутренности и границы, вероятность границы — третьему softmax-каналу. Общий накопитель v2 принимает только конечные вероятности, допускает округление float32 до 1e-6 за пределами [0,1] и ограничивает такие значения диапазоном без изменения входных массивов; существенный выход остаётся ошибкой. После Gaussian-нормализации диапазон также восстанавливается. Исторический object_f1 сохраняет прежнюю строгую проверку. CPU-разделение удаляет компоненты меньше 16 px до резервных маркеров, замыкает короткие разрывы границы радиусом 1 px и использует внутренние маркеры от 16 px. Внутренность для маркеров должна быть вероятнее и границы, и фона; условие проверяется по трём softmax-вероятностям. При отсутствии маркеров значимые максимумы расстояния (выраженность 2 px) и резервный центр также ограничены такой внутренностью; компонент без неё не превращается в объект. Плоский watershed расширяет связные сердцевины внутри foreground и valid mask: граничная полоса распределяется по соседям, не получает самостоятельный ID и не присоединяется длинной петлёй к одному участку. Маленькие выходные фрагменты перераспределяются без искусственных дыр. Чужие ID не объединяются в общий полигон.

Исправленная постобработка обозначается `interior_geodesic_v1` в новых checkpoint, экспортах и отчётах.
Она применяется общим CPU-кодом validation/test, PyTorch и Geoalert к тем же вероятностям модели.
Старые веса и записанные обучающие метрики не переписываются. Кеш тестовых оценок и поснимочной
псевдоразметки инвалидируется только для v2; кеш сценария обновляется без переэкспорта ONNX.
Для ортофото v2 `VectorizeMasks` согласует общие вершины instance-контуров в исходном CRS до
репроекции; нодирование не перемещает границы, не разрешает наложения и сохраняет каждый ID.
При ненулевом `postprocess.simplify_m` независимый `Simplify` заменяется совместным
`CoverageSimplify` (`shared_edges_v1`) в UTM: упрощаются только внутренние общие рёбра,
внешнее покрытие и отверстия сохраняются. Допуск задаёт масштаб алгоритма Visvalingam,
а не максимальное смещение Douglas–Peucker. Проверяются валидность покрытия, число объектов,
частей и отверстий и равенство внешнего покрытия. До сохранения проверяется также точный путь
Geoalert `FeatureCollection.to_crs(EPSG:4326)`: обратная репроекция не должна создавать
самопересечения и последующее дробление через `make_valid/explode`. Если исходный допуск
небезопасен в конечном CRS, он уменьшается вдвое для всего покрытия, не для отдельных участков;
не больше восьми попыток, каждая от исходных контуров. Запрошенный и фактический допуски
записываются в диагностике. Неподходящий вход или отсутствие поддержки
GEOS либо исчерпание безопасных попыток сохраняют исходные геометрии с явной причиной
в журнале; наложения не скрываются обрезкой и мелкие осколки не удаляются постфактум.
Исходные контуры при таком fallback также проверяются в конечном CRS; если и они
небезопасны, сцена завершает обработку понятной ошибкой до сохранения вместо искусственного дробления.
Значение 0 отключает упрощение. Исторические профили сохраняют прежнюю постобработку.

В ортофото v2 Triton CUDA EP отключает TF32, а нативный одноразовый PyTorch-инференс использует
ту же полную точность FP32. Число окон в запросе Geoalert по умолчанию равно 1: увеличение
пакета на установленном Triton не дало ускорения. Экспорт v2 поддерживает динамический NCHW
без изменения ABI остальных профилей. Версии экспорта, сценария и текущих оценок различают
профиль точности и совместного упрощения; исторические оценки обучения не переписываются.
Внутренний Compose runner v2 допускает не больше двух независимых снимков одновременно,
каждый со своим Compose и Triton-клиентом в собственном потоке. Загрузка YAML сериализована.
Число одновременно запущенных сцен ограничено доступной RAM и консервативной оценкой
66 байт на пиксель; при неизвестной оценке или нехватке памяти выполняется одна сцена.
Порядок итоговых отчётов и объектов остаётся исходным. Пауза прекращает запуск новых сцен,
дожидается текущих, выгружает модель и после продолжения не повторяет готовые снимки.
Без внутреннего запроса параллелизма и для остальных профилей сохранён последовательный путь.

Каждая validation собирает полные сцены один раз. Порог границ выбирается из 0.35/0.5/0.65 по суммарной object F1, затем precision, близости к 0.5 и большему порогу; foreground фиксирован 0.5. Повторное разделение использует дисковые карты. Best/early stopping используют эту object F1 с прежним one-to-one IoU≥0.5. Выбранный профиль разделения сохраняется в ModelSpec и metadata конкретного checkpoint. Test проверяет best с сохранённым профилем, без калибровки. Инференс, ONNX и Geoalert используют те же две вероятности, CPU-алгоритм и параметры из checkpoint; несовместимая схема отвергается.

История и `reports/validation_by_scene.json` содержат поиск порога, boundary precision/recall/F1, количество эталонных и предсказанных объектов, склеек и дроблений. Эталон полосы в перекрытии берётся из наиболее центрального допустимого окна; при равном приоритете используется объединение, поэтому порядок обхода окон не влияет на диагностику. Последние два счётчика диагностические: связь фигур учитывается при перекрытии не менее 10% площади каждой; она не меняет IoU-сопоставление основной метрики. В `reports/test_metrics.json` сохраняются параметры и поснимочная диагностика без повторной настройки. Сложные структуры пишутся как JSON, а в числовые MLflow-метрики попадают только скаляры. Основная сеть автоматически не назначается.

Подготовка v2 вычисляет точные частоты целей по всем train-окнам отдельными `spawn`-процессами
с существующим `num_workers`; очередь ограничена, возвращаются только счётчики и коэффициенты,
их порядок совпадает с исходными окнами. Неиспользуемая карта наложений для этого подсчёта не строится.
CPU-проверка независимых полных сцен использует до четырёх потоков, не больше числа загрузчиков,
с дополнительным консервативным ограничением по доступной RAM и размеру снимков. Пороги одной сцены
считаются последовательно, порядок итогового отчёта не зависит от скорости потоков; управление CUDA
и паузой остаётся в главном потоке. Карты закрываются только после завершения CPU-задач.
Целочисленные пары ID считаются через точную упаковку без структурной сортировки строк;
для исторических ID вне диапазона сохраняется прежний путь. В v2 неизменная foreground-карта
переиспользуется между порогами границ; единственный маркер заполняет связную область напрямую,
пропуски ID не запускают лишний watershed. Маски, сопоставления, формулы F1, разбиение, веса и
выбор checkpoint не изменяются. Журнал явно показывает подготовку, обучение на GPU, инференс
проверки и CPU-проверку снимков с временем каждого этапа.
