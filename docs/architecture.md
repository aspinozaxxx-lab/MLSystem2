# Архитектура

MLSystem 2.0 — простая система командной строки с явными границами модулей.
Обучение и основной CLI-инференс используют локальные подготовленные изображения. AOI-инференс QGIS
дополнительно поддерживает независимый выбор локального или разрешённого внешнего источника снимков.
Основной принцип реализации системы и построения архитектуры - необходимо и достаточно. Это касается документов, интефейсов, модулей, функционала и всего остального что есть в проекте.

## Ахритекутурные правила обязательные к соблюдению зафиксированы тут: 
- Данный документ - главный источник правды для всего проекта. 
- Архитекутурные правила в архитектурных документах должны абсолютно соблюдаться
- Любые изменения в архитектурных документах - согласуются.
- В репозитории не должно быть функционала повторяющиего функционал модулей.
- Недопустимо оставлять deprecated wrapper в репозитории.
- Новые модули и код не принадлежащий к какому либо модулю создавать запрещено без отдельного согласования

Основное приложение обучения:

```bash
mlsystem2-train --settings configs/settings.server.yaml --run configs/run.example.server.yaml
```

Основное приложение инференса:

```bash
mlsystem2-infer --config configs/example.server.yaml
```

Веб-интерфейс обучения:

```bash
mlsystem2-training-ui-api
mlsystem2-training-ui-worker
python frontend/build.py
```

`training_ui_api` — отдельный модуль MLSystem2 и единственная серверная точка доступа frontend к
данным UI обучения. Frontend не обращается к Postgres напрямую. Управляемый каталог классов и
датасетов, шаблоны, очереди, custom datasets и результаты хранятся в отдельной Postgres БД/схеме. Инфраструктура
Postgres разворачивается вручную по runbook и не входит в CI/CD. UI-сервис может читать публичные
данные MLflow для списка experiments, best checkpoint и скачивания checkpoint, но не открывает
training runs и не пишет MLflow-метрики; запись метрик выполняет `train_pipeline`.

Каталог `dataset_classes` → `datasets` является источником истины для названий, основной метрики,
основного датасета, типа снимков класса и источника разметки. Тип `kanopus` использует строго четыре канала
`RED, GRN, BLU, NIR` из `/data/mlsystem2/prepared_images/kanopus`, тип `ortho` — строго три канала
`RED, GRN, BLU` из `/data/mlsystem2/prepared_images/orto`. Синхронизация с MLMarkup при
старте и при изменении дешёвой ревизии папок class/dataset только добавляет неизвестные папки и вычисляет файловую версию: она не удаляет
историю и не перезаписывает ручные настройки. Пути источников хранятся относительно корня MLMarkup. Первый
импорт сохраняет исторические `dataset_key`; сущности, обнаруженные позднее, получают независимые UUID.
Удаление датасета мягко архивирует его строку в Postgres и исключает её из активного каталога, но не удаляет
задания, результаты и данные MLflow.

MLMarkup поддерживает legacy и per-image форматы. Legacy сохраняет `TXT + positive GeoJSON + optional
hard-negative GeoJSON`, включая legacy multiclass. Per-image не содержит TXT: каждому TIFF соответствует файл
разметки `<родительская_папка>_<имя_TIFF_без_расширения>.geojson` и companion-файл фактической valid-data mask
`<родительская_папка>_<имя_TIFF_без_расширения>_footprint.geojson`. Footprint хранится в CRS TIFF, не является
разметкой и не участвует в подсчёте сцен, объектов или supervision. Исторические per-image наборы без companion-файла
остаются читаемыми, но редактор создаёт пару для каждого нового снимка и пересборки. Binary per-image сохраняет
прежнюю совместимость ролей. Multiclass per-image определяется файлом `.mlsystem2-dataset.json`: manifest хранит
версию схемы, классы с ID/slug/color/priority, source-ревизии, build ID и baseline-хеши, а каждый GeoJSON строго
повторяет schema/task/classes. Positive feature имеет `_mlsystem2_role=positive` и известный `_mlsystem2_class`,
hard negative содержит только роль; ID и origin-key стабильны. Коллизии формулы, несовпадающая схема,
неоднозначные и отсутствующие TIFF делают датасет невалидным. Пустой управляемый per-image датасет доступен
редактору, но не запуску обучения.

Управляемый датасет — виртуальный multiclass-набор, состав которого хранится в Postgres как упорядоченные
ссылки на несколько обычных binary per-image датасетов. У каждого источника свой тип объекта, цвет и приоритет;
пока допускается не более одного источника от класса. Отдельной папки управляемого датасета в MLMarkup нет.
Для редактора и неизменяемого snapshot обучения он детерминированно материализуется в служебный cache из
актуальных исходных GeoJSON; версия включает состав, приоритеты, явно добавленные сцены и файловые версии всех
источников. Поэтому публикация обычного источника автоматически меняет версию зависимого управляемого датасета
и обрабатывается его действующим правилом автоматизации.

Снимок, добавленный через управляемый редактор без объектов, хранится только в `managed_dataset_scenes` и не
создаёт пустые GeoJSON в источниках. При публикации positive снимок и объект записываются только в источник
выбранного типа; hard negative записывается во все источники, а в виртуальном представлении одинаковые копии
схлопываются. Удаление снимка остаётся черновым действием и при публикации удаляет его явное членство и связанные
исходные файлы. Все source-изменения одной публикации образуют один Git-коммит пользователя. Удалить обычный
датасет, пока на него ссылается активный управляемый, нельзя; удаление самого управляемого датасета мягко архивирует
только строки БД и не затрагивает источники.

Одноразовая миграция исторических наборов «Переувлажнения и заболачивания/main» и «Опустынивание и ветровая
эрозия/main» сохраняет `dataset_key`, историю jobs, checkpoint, MLflow и псевдоразметок, а их materialized-папки
заменяет ссылками на актуальные базовые источники. Полнота перехода проверяется относительно последнего полного
Git-снимка combined-папок, а не только относительно ручных изменений после первой сборки: отсутствующая
положительная геометрия добавляется в соответствующий источник как разность с его текущей разметкой, поэтому
более поздние правки источника не удаляются. Исторические и более поздние hard negative объединяются,
дедуплицируются и с одним origin-key записываются во все источники. Восстановительная операция идемпотентна,
проверяет покрытие каждой исторической геометрии и после успешного запуска должна давать пустой dry-run.
Миграция и восстановление выполняются только после резервной копии и при пустой очереди. На время применения
автоматизация выключается и остаётся выключенной до подтверждения публикации нового MLMarkup release-marker:
это исключает обучение на переходной версии live-каталога. Существующие успешные результаты засчитываются новой
файловой версии; для базовых источников обновляется только псевдоразметка, переобучение не запускается.
Рабочий MLMarkup после завершающей миграции содержит только per-image источники с обычными именами
`main`, `test`, `strict` и другими без суффикса `_new`. Строки прежних legacy-источников мягко архивируются,
а их jobs, результаты обучения, псевдоразметки, тестовые разметки и ссылки на MLflow переводятся на
соответствующий действующий per-image датасет; сами исторические MLflow runs и checkpoint не переписываются.
Чтение legacy остаётся частью совместимого контракта для архивных и внешних наборов.

Страница `#/dataset-editor` редактирует только per-image датасеты. TIFF выбираются из существующего
`prepared_images` по одному или прямыми файлами папки, без browser upload и рекурсии. OpenLayers отображает
авторизованный GeoTIFF через HTTP Range без экранной интерполяции пикселей, допускает nearest-neighbor overzoom до
`1000%` с умеренным экранным контрастом и позволяет полностью скрыть разметку отдельной кнопкой. Доступны
Draw/Modify/Snap, смена роли/типа, удаление и undo. Снимок перемещается перетаскиванием с зажатым колесом;
нативная автопрокрутка браузера внутри карты подавляется, поэтому страница при этом остаётся неподвижной.
Левая кнопка протягивает рамку выбора всех попавших в неё вершин. У выбранных полигонов видны все вершины:
клик по ребру добавляет вершину, а `Delete` удаляет выбранную группу, оставляя в каждом кольце не менее трёх
вершин и автоматически замыкая его; все правки проходят через общую проверку footprint и историю undo.
Для binary остаётся positive/hard negative, для multiclass
единый segmented control содержит два смысловых типа и общий hard negative; типы имеют цвета manifest, hard negative
красный, выбранный объект — голубой контур. Легенда и счётчики считаются по типам; в списке снимков каждое
число окрашено тем же цветом, что и соответствующий контур. Псевдоразметка multiclass также использует сохранённые
цвета каждого типа из схемы сети, а не единый цвет слоя. Черновик каждого снимка хранится в Postgres
отдельно для пользователя и датасета, автоматически восстанавливается после обновления страницы и не меняет
MLMarkup. Клиент автоматически сохраняет изменённые черновики с короткой задержкой и показывает состояние
сохранения; отдельной ручной кнопки сохранения нет. Отмена удаляет все черновики пользователя и возвращает
опубликованную разметку, а только отдельная публикация отправляет изменения одним batch. Удаление снимка является
тем же отменяемым черновым действием: до публикации GeoJSON остаётся в MLMarkup, пометка переживает обновление
страницы и снимается через undo либо общую отмену. Новые объекты до
публикации рисуются пунктиром; заливка отключается независимо от разметки. Для четырёхканального Канопуса доступны
экранные сочетания `RGB`, `NRG`, `NGB`, для трёхканального ортофото переключатель не показывается. Сервер обязательно
строит footprint по фактической valid-data mask TIFF, обрезает выдаваемую для редактирования разметку этим контуром и
проверяет CRS, `Polygon/MultiPolygon`, валидность и попадание в него; свойства и feature ID
сохраняются. Optimistic lock использует Git blob revision, конфликт возвращает `409`, автоматического слияния
геометрий нет. Исторический материализованный комбинированный датасет получает индикатор `current|stale` по всей каждой исходной папке `main`.
Перед пересборкой endpoint preview фиксирует target/source trees и показывает локальные изменения и конфликты;
`merge` сохраняет ручную версию конфликтующего объекта, `replace` полностью заменяет per-image файлы. Любое изменение
после preview даёт `409`, успешная замена каталога и публикация выполняются атомарно одним Git-коммитом.

Редактор никогда не пишет в live-каталог. Все мутации сериализуются межпроцессным lock в отдельном клоне
`/data/mlsystem2/mlmarkup-editor`, принадлежащем `MLMarkup_deploy_user` и использующем отдельный write deploy key.
Fetch и fast-forward перед обычным чтением выполняются не чаще одного раза в минуту, а перед каждой Git-мутацией
обязательны; перед push повторно проверяется blob revision. Сохранение серверного черновика не выполняет Git-коммит,
push или инференс. Одиночный save совместим, а batch-публикация всех черновиков, включая помеченные на удаление
снимки, создаёт один атомарный commit. Для обычного датасета добавление папки пропускает уже присутствующие GeoJSON,
создаёт разметку и footprint одним commit; для управляемого пустые сцены добавляются только в БД без Git-публикации.
Публикация удаления убирает соответствующие исходные файлы. В браузере снимков уже добавленные TIFF остаются в исходном порядке, показываются зелёной
рамкой и не имеют повторного выбора. Канонический вошедший пользователь является реальным Git author/committer,
а его имя дополнительно сохраняется trailer. Разрешён один rebase/retry для постороннего коммита, но не для изменения целевого
GeoJSON.
Удаление всего датасета доступно из редактора классов: после проверки отсутствия активных заданий папка обычного
датасета удаляется отдельным Git-коммитом, а виртуальный управляемый датасет архивируется без Git. Основной датасет
класса снимается, строка `datasets` сохраняется с временем удаления. Live-каталог переключается только штатной
атомарной публикацией MLMarkup.

MLMarkup публикуется атомарно: неизменяемые каталоги `/data/mlmarkup-runtime/releases/<commit>`, ссылка
`/data/mlmarkup-runtime/current` и стабильная внешняя ссылка `/data/MLMarkup -> current`. CI сначала собирает и
проверяет staging-релиз, дедуплицирует неизменённые файлы через `rsync --link-dest`, затем атомарно переключает
`current`. Current и previous сохраняются всегда, прочие релизы — 30 дней. Маркер `.mlsystem2-release` содержит
commit релиза. Save сразу возвращает `publishing`; commit становится `published`, когда является предком live SHA,
что допускает последующий автоматический README-коммит.

Автоматизация обучения и псевдоразметки является частью `training_ui_api`. Она хранит правила
`датасет × модель` в Postgres, отслеживает управляемую версию датасета и файловую версию его источника
MLMarkup по git-коммиту, release metadata или filesystem mtime fallback и создает auto jobs только через те же очереди, что
и ручной запуск. Jobs диспетчеризуются общей очередью: ручная псевдоразметка выше ручного обучения,
ручное обучение выше auto псевдоразметки, auto псевдоразметка выше auto обучения. Auto jobs отменяются
изменением правила автоматизации или заменяются при новой версии конкретного датасета; frontend не
имеет прямого доступа к БД и не запускает процессы напрямую.
HTTP API и исполнители очередей запускаются разными systemd-сервисами. Обучение и его дочерние DataLoader-процессы
наследуют ограниченный worker-cgroup, низкие CPU/IO weights, `nice` и `ionice`; часть CPU остаётся доступной API.
В серверном профиле используются восемь DataLoader workers и Torch pools `4/2`. `prefetch_epochs=1` сохраняется:
`prefetch_factor` автоматически компенсирует меньшее число workers, поэтому целевое количество готовых batch не уменьшается.
Поснимочная псевдоразметка редактора имеет срочный приоритет. Если GPU занят обучением, train loop на
границе batch переносит модель и optimizer state в CPU, освобождает CUDA и подтверждает состояние `paused`;
worker запускает срочный инференс только после этого подтверждения, затем возвращает тот же процесс и тот же
MLflow-run на GPU. DataLoader workers при наличии `pause.request` также прекращают чтение и растеризацию новых
тайлов, но накопленный префетч не сбрасывается. Обычный running-инференс не прерывается.
Глобальное отключение автоматизации отменяет все active auto jobs, останавливает running automatic
process и помечает известный MLflow run как `KILLED`; повторное включение создает jobs заново по
текущим правилам и версиям датасетов.
Шаблоны обучения в `training_ui_api` бывают базовыми для сети и привязанными к конкретному
датасету. При создании job сервис сначала ищет шаблон `(architecture, dataset_key)`, затем использует
базовый `(architecture, null)`, поэтому frontend не дублирует эту бизнес-логику.
Обучение и нативный инференс используют единый контракт окна: `tile_preparation.tile_size` задаёт полный вход сети, `tile_preparation.context` — исключаемую рамку, полезный центр равен `tile_size - 2 × context`. Для действующих шаблонов с входом `768` используется context `128` и центр `512`; `context=0` сохраняет старое поведение. Подготовка строит окна с отрицательным начальным смещением, а loss, validation и выбор checkpoint считаются только по центру. Nodata, raster mask и padding внутри центра остаются обучающим фоном. Seed подготовки задаёт Python, NumPy, Torch и CUDA до создания модели и сохраняется в MLflow/checkpoint.

Псевдоразметка Training UI запускается отдельным процессом с backend `pytorch_one_off`: worker пишет
`pseudo_config.yaml`, runner загружает нативный checkpoint через `models.load_checkpoint` либо проверенный по
SHA-256 TorchScript из ZIP импортированного результата, выполняет локальный
PyTorch-инференс и после обработки освобождает CUDA cache. Сцены разрешаются через публичный
`dataset_preparing.resolve_scene_images`: точное имя `SCNxx` не расширяется до соседних сцен, а одинаковые
имена в подпапках выбираются по GeoJSON датасета. Этот путь не экспортирует модель в Triton, не
создает Geoalert pipeline YAML и не добавляет запись в Triton model repository; Triton остается ручным
production-инференсом и явным экспортом. Эффективный inference-шаблон выбирается по датасету обученной
модели независимо от источника снимков. Для трёхканального checkpoint этот одноразовый инференс принимает
RGB и совместимые RGBA GeoTIFF, читая из RGBA только первые три канала; остальные несовпадения числа каналов
отклоняются. `external_torchscript` является только inference-архитектурой, отсутствует в каталоге обучаемых
сетей и имеет базовый inference-шаблон. Нативная псевдоразметка читает полный вход, записывает только полезный центр и при ненулевом context идёт с шагом размера центра; старые jobs без context используют прежнюю сетку. Её манифест в исходном `JobRow.config` фиксирует адаптер, MLflow artifact,
SHA-256, RGB-вход, разрешение, окна и постобработку. ЗУ500 сохраняет instance ID и confidence, выполняет NMS и
не объединяет соседние участки; ОКС500 строит крышу из классов `1,2` и корректирует footprint по стенам класса
`4`. Оба профиля обнуляют alpha/nodata. Нативный multiclass checkpoint использует `softmax → argmax → общий confidence threshold`; перекрытия окон и сцен разрешаются по confidence, затем priority и class ID. Морфология, векторизация и слияние выполняются отдельно по типам. Каноническая псевдоразметка остаётся одним FeatureCollection с родительским `class_id` и `object_type_id/slug/name/color`; дополнительный endpoint отдаёт ZIP с GeoJSON по типам. Подготовка датасета, обучение и основной CLI-инференс сохраняют строгую проверку каналов.
Перед обучением worker копирует legacy-файлы либо все per-image GeoJSON в неизменяемый snapshot задания. Для
псевдоразметки per-image набора временный TXT строится из строго сопоставленных TIFF, а в runner передаются все
файлы разметки этого набора.
Редактор per-image датасета по умолчанию не показывает псевдоразметку. Для подсказки редактора явно назначенная
основная сеть класса имеет приоритет; без звезды выбирается последняя успешная сеть открытого датасета, а при её
отсутствии — последняя успешная сеть класса. По явному переключателю редактор сначала берёт последнюю успешную
полную псевдоразметку выбранной таким образом сети, чей список сцен содержит выбранный TIFF, независимо от исходного
датасета или папки результата, и обрезает её по valid-data footprint. Нормализация ссылки
удаляет только явное расширение TIFF и сохраняет точки внутри имени сцены. Исторический `scenes_file` с одним
именем файла без подпапки принимается только тогда, когда оно однозначно разрешается в тот же TIFF внутри корня снимков.
Если legacy-TXT был удалён миграцией, полный результат того же датасета принимается по точному совпадению
`dataset_key` и управляемой версии: версия фиксирует состав снимков, в том числе сцены с пустым предсказанием.
Если результат не покрывает снимок,
клиент сначала выполняет read-only проверку готового результата и только после ответа `unavailable` запрашивает
создание. Затем создаётся идемпотентное срочное задание: одноэлементный список сцен проходит через общий `pseudo_config.yaml` и тот
же `pytorch_one_off` runner штатной псевдоразметки; уникальный ключ включает сеть, TIFF и effective inference-конфигурацию.
Повторные клики и конкурентные запросы используют ту же строку job, готовый GeoJSON хранится как StoredFile, а
frontend сохраняет состояние по снимкам при переключении. Polling идёт по лёгкому endpoint `job_id` без Git и полного
сканирования каталога. Выбранная сцена принадлежит конкретному успешно загруженному списку: при смене датасета
выбор синхронно очищается, а запросы прежней сцены отбрасываются до обращения к API. Запоздавшие ответы также
принимаются только для всё ещё открытого датасета. Ошибочное задание повторяется только явным действием
пользователя. Готовый GeoJSON показывается отдельным нередактируемым слоем.
Распознавание AOI для QGIS является дополнительным HTTP-контрактом того же `training_ui_api` и проходит
через общую inference-очередь и тот же `pytorch_one_off` runner. Клиент передаёт класс, выбранный источник,
Polygon или MultiPolygon и CRS. Сервер фиксирует основную сеть класса. Источник выбирается независимо:
локальные `kanopus` и `ortho`, OpenAerialMap либо настроенные XYZ/TMS/WMTS. Внешние тайлы существуют только
в scratch задания. Для перекрёстного запуска источник приводится к медианному размеру пикселя обучающих TIFF;
импортированная модель всегда использует точное разрешение манифеста, включая локальное ортофото;
трёхканальная модель читает RGB, четырёхканальная получает RGB+NIR только от Канопуса, а для RGB-источника —
RGB и нулевой NIR. Альфа-канал является только маской валидности. Сервер выбирает все пересекающие TIFF,
обрабатывает AOI окна и расширяет соседний контекст до окончания связных объектов. Полностью внешние объекты
удаляются, а пересекающие AOI сохраняются целиком с площадью и средней уверенностью в `stored_files`.
Метаданные результата фиксируют источник, схему каналов, целевое разрешение, лицензию и attribution.
QGIS-плагин находится в отдельной корневой папке
`mlsystem_plugin`, не импортирует пакет сервера и связан с ним только HTTP. Решения пользователя сохраняются
в одном каноническом локальном GeoPackage staging. Для multiclass сохраняются object type ID/slug/name/color,
фильтр типа меняет ту же единую очередь и общие review-статусы. Пользователь выбирает один категоризированный
слой либо группу синхронизированных представлений по типам. Плагин также фильтрует кандидаты по площади и уверенности, позволяет разбить
один или все прошедшие фильтры крупные объекты и создаёт по явной команде новый временный слой из текущего
отбора. Существующие слои проекта плагин не изменяет и поля с ними не сопоставляет.
Страница экспорта моделей в `training_ui_api` показывает последние успешные training results по датасетам
MLMarkup и по умолчанию выбирает основные датасеты классов, скачивает `checkpoints/best.pt` либо внешний ZIP из MLflow по сохраненным run id,
собирает временный общий zip-архив для `models-serving-service` и Triton через тот же сборщик, что одиночный
экспорт, отдаёт его пользователю и не пишет данные в Postgres, MLflow, S3 или рабочий каталог сервиса инференса. ONNX получает полный вход, а Geoalert YAML получает `bounds=context` и `sample_size=полезный центр`. Для старого checkpoint без metadata context экспорт использует `bounds=0`; оператор может явно задать context. Binary ABI остаётся прежним. Multiclass ONNX возвращает `uint8 [B,N,H,W]` one-hot foreground-каналов после threshold; pipeline содержит semantic `output_labels` и отдельный GeoJSON каждого типа, а export metadata — task, полную schema, threshold, размеры окна и checkpoint metadata.
Страница создания списка сцен в `training_ui_api` принимает GeoJSON и тип снимков, рекурсивно сопоставляет
полигональные объекты с фактическими валидными пикселями TIFF только внутри соответствующего корня
`prepared_images/kanopus` или `prepared_images/orto` и возвращает ZIP с UTF-8 TXT полных относительных путей
внутри выбранного корня без расширений и GeoJSON реальных футпринтов тех же снимков в WGS84. GeoJSON содержит
по одному объекту на строку TXT и позволяет проверить покрытие разметки в QGIS. Файлы не сохраняются в БД или
постоянном хранилище; их имена повторяют имя загруженного GeoJSON. Совпадающие имена TIFF в разных папках
различаются путём; сцена, где вся площадь пересечения приходится на `nodata`, исключается. Совпадение
относительного пути без расширения считается неоднозначностью. Старый HTTP-режим
без флага футпринтов продолжает возвращать только TXT.
Нарезка тестовой разметки является самостоятельной функцией `training_ui_api` и не входит в конвейер обучения,
training/inference-очередь или автоматизацию. Она читает исходные TIFF только из `MLSYSTEM2_IMAGES_ROOT` с серверным значением
`/data/mlsystem2/prepared_images`, выбирает полностью валидные непересекающиеся тайлы по положительной разметке
датасета MLMarkup и формирует TIFF, GeoJSON, PNG class-ID mask и цветное PNG-превью. Для per-image источника каждый TIFF
использует только свои features с ролью `positive`; hard negative в тестовую разметку не попадает. Multiclass-отбор
гарантирует оба типа при наличии кандидатов, стремится к равным квотам и сообщает о дефиците. Совместимые endpoints
`/markup-export` хранят временный ZIP один час в `scratch_root`. Основной интерфейс создаёт постоянные тестовые
разметки: описание и состояния тайлов хранятся в Postgres, а файлы — в
`MLSYSTEM2_TRAINING_UI_STORED_FILES_ROOT/test-samples/{uuid}` без TTL. Разметку можно переименовать, удалить,
а тайлы — выключить и включить обратно; ZIP содержит только включённые тайлы. При скачивании они получают
последовательные имена `tile001..tileNNN` независимо от внутренних индексов. Пользователь выбирает полный
состав либо вариант без превью, содержащий строго TIFF и GeoJSON. Полный состав дополнительно включает
PNG-маску и сформированные на лету полноразмерные JPEG-превью с жёлтым контуром разметки и без него:
для трёхканального ортофото
только RGB (`RED, GRN, BLU`), для четырёхканального Канопуса дополнительно NRG (`NIR, RED, GRN`) и
NGB (`NIR, GRN, BLU`); адаптивное качество
ограничивает каждый JPEG размером `300 KiB`. Тестовая разметка принадлежит классу, а сохранённый `dataset_key`
является только неизменяемым указанием, на основе какого датасета сформированы её тайлы. Последняя успешная
псевдоразметка текущей основной сети для этого исходного датасета используется только при создании набора,
предварительной оценке и оптимизации его состава. Если её нет, редактор показывает основную сеть и её обучающий
датасет и предлагает идемпотентно запустить штатную полную псевдоразметку исходного датасета. Для неё
редактор считает пиксельный и объектовый F1 с `IoU ≥ 0,5`; multiclass-оценка возвращает per-class, macro, micro и
foreground-метрики. Один протяжённый объект в разных непересекающихся тайлах считается отдельным объектом в каждом
из них. Черновой расчёт не изменяет сохранённую контрольную метрику, а название, основной статус и полный состав
применяются одной атомарной операцией. Каждый тайл хранит отдельный кэш pixel/object F1 по псевдоразметке для
оптимизатора; карточка выбирает значение по `quality_metric`, а отсутствующий старый кэш заполняется при открытии.
Групповое скачивание принимает явный список сохранённых разметок, не более одной для класса.
Основные разметки предварительно выбраны только в frontend; backend не подменяет переданный список и отклоняет
повтор класса либо коллизию нормализованных имён папок. Каждая разметка готовится в отдельном временном
каталоге задачей пула до восьми потоков без общей SQLAlchemy-сессии и без общего `ZipFile`, после чего один
поток детерминированно собирает общий ZIP без сжатия (`ZIP_STORED`). Папка разметки имеет стабильное имя
`<класс>_<датасет>` без имени разметки, даты и UUID.
Групповое создание доступно на `#/test-markups/create`; форма использует тот же критерий готовности, что и сервер:
набору старого формата нужны TXT и общий GeoJSON положительной разметки, а поснимочному набору — непустой каталог однозначно сопоставленных
с TIFF GeoJSON без диагностик. Карточный каталог и редактор доступны на
`#/test-markups` и `#/test-markups/{id}`; технические HTTP-контракты сохраняют имена `test-samples`.
Групповое создание последовательно обрабатывает выбранные датасеты отдельным фоновым исполнителем
`training_ui_api`: для итогового диапазона `Nmin..Nmax` тайлов и минимальных `M` объектов строится пул до
`3 × Nmax` с целью `3M`, после чего по последней точной псевдоразметке включается оптимальный состав внутри
заданного диапазона. Полигональная геометрия восстанавливается через `make_valid` после преобразования CRS
до пространственных операций. Сначала несколько детерминированных жадных вариантов ищут допустимый итоговый
состав, а при их неудаче используется отдельная MILP только для `Nmin..Nmax` и `M`; найденный состав затем
детерминированно расширяется непересекающимися тайлами до размера пула. Допустимый incumbent MILP при лимите
времени принимается только после проверки всех ограничений. Для невыполнимых ограничений отдельная MILP-задача
показывает достижимый максимум объектов с учётом перекрытий. Состояние запуска и
строк хранится в Postgres, поэтому незавершённая группа продолжается после перезапуска; параметры последнего
запуска служат значениями формы по умолчанию.
Для каждой сохранённой тестовой разметки, включая неосновные разметки и датасеты `main`, `test`, `strict` и
архивные строки того же класса, итоговые pixel/object-метрики рассчитываются прямым инференсом эффективной
сети класса. Задание `test_sample_f1` с `metric_target=test_sample` проходит через общую
inference-очередь, обрабатывает только включённые TIFF и сохраняет агрегированные TP/FP/FN, threshold и
multiclass-структуру в `test_samples`; поснимочный кэш псевдоразметки при этом не заменяется. Оценка актуальна только
для той же эффективной сети, ревизии состава, эффективного inference-шаблона, профиля и версии алгоритма. Смена
эффективной сети, шаблона или состава, создание набора и старт сервиса ставят недостающие оценки в очередь; страницы
каталога и редактора вызывают идемпотентную сверку и опрашивают активное задание. Старые значения сохраняются с
признаком устаревания, результат потерявшего актуальность задания отбрасывается, а ошибка той же сигнатуры не
перезапускается автоматически до ручной команды.
Для класса может быть не более одной основной тестовой разметки. Она применяется к успешным сетям всех датасетов
этого класса. Исполнитель проверяет канонический класс, схему типов и идентификатор текущей основной разметки, но
не требует совпадения исходного датасета её тайлов с датасетом обучения сети. По ней для каждой успешной сети считаются
отдельные пиксельный и объектовый F1: задание с назначением `test_sample_f1` проходит через общую inference-очередь, загружает
best checkpoint с threshold либо внешний ZIP без вымышленных метрик, применяет действующий inference-шаблон и независимо обрабатывает каждый
включённый TIFF-тайл. Компоненты прогноза, касающиеся границы TIFF, считаются обрезанными фрагментами и не
удаляются фильтрами минимальной площади и компактности; для внутренних компонентов inference-шаблон применяется
полностью. Для ЗУ500 объектовая метрика использует настоящие instance ID вместо connected components. Внешнее
предсказание сначала выполняется в разрешении модели, затем возвращается в исходную сетку TIFF. TP/FP/FN
суммируются без объединения совпадающих географических областей. Метрика хранится в Postgres,
не пишется в MLflow и считается актуальной только для тех же `sample_id`, ревизии состава, профиля и версии
эффективного inference-шаблона и алгоритма оценки. Результат показывает метрику, сохранённую вместе с запуском
обучения. Новая успешная сеть, смена основной разметки или её состава автоматически ставят недостающие и
устаревшие оценки в очередь. Восстановление также выполняется при старте и изменении эффективного профиля или
inference-шаблона; неуспешная попытка той же ревизии не повторяется циклически.
Класс может хранить явную ссылку на основную успешную сеть, которую пользователь назначает звездой на странице
результатов и снимает повторным нажатием на заполненную звезду. Снятие очищает ссылку, но не удаляет результат.
Если ссылка отсутствует, эффективной считается последняя успешная сеть среди всех датасетов класса:
этот выбор не записывается в БД и не показывает звезду. Завершение обучения также не назначает звезду, но при
смене неявно выбранной последней сети запускает сверку зависимых метрик. Эффективная сеть используется групповым экспортом,
публичным тестовым F1 класса, прямой оценкой всех тестовых разметок класса, выбором псевдоразметки для создания и
оптимизации их состава и AOI-инференсом QGIS. Поснимочная подсказка редактора датасета является отдельным
контекстом: при отсутствии звезды она сначала использует последнюю сеть открытого датасета, чтобы переиспользовать
его готовую полную псевдоразметку. Редактор тестовой разметки явно показывает имя сети и датасет её
обучения как для сохранённой метрики, так и для поставленного нового расчёта.
Каталог результатов выделяет назначенный основной датасет класса. F1 эффективной сети класса рассчитывается один
раз по основной тестовой разметке и отображается на карточке каждого активного датасета класса; это одно классовое
значение, а не отдельный инференс для каждой карточки.
На странице результатов обучения тот же временный zip-экспорт доступен для успешного training result: сервис
скачивает нативный `checkpoints/best.pt` либо исходный ZIP импортированной модели из MLflow. Для внешней модели
безопасно переименовываются корневая папка и `config.pbtxt`, добавляется профиль pipeline; общий batch может
содержать оба вида результатов.

Каноническое место хранения результатов обучения — MLflow. Локальные директории используются как временная
рабочая область, кроме явно постоянных файлов UI: загруженных файлов и тестовых разметок в
`MLSYSTEM2_TRAINING_UI_STORED_FILES_ROOT`.

## Конвейер Обучения

1. CLI получает стабильный `settings.yml` через `--settings` и задание конкретного обучения через `--run`, вызывает `settings.api.load_settings(settings_path, run_path)` и инициализирует текущие настройки процесса. Совместимый legacy-режим `--config` остается для старых полных YAML.
2. Создать или открыть запуск MLflow через `mlflow_adapter` и записать YAML задания запуска в артефакты.
3. `dataset_preparing` принимает локальные пути, проверяет подготовленные TIFF, число каналов и `uint8`, затем возвращает список независимых `PreparedScene`. Поддерживаются legacy binary/multiclass и per-image binary/multiclass через `dataset.annotations_dir`; multiclass-схема читается из manifest. Общие растровые мозаики не создаются; перекрывающиеся TIFF остаются независимыми.
4. Если `dataset_preparing` вернул ошибки, `train_pipeline` записывает отчет подготовки в MLflow и
   завершает конвейер с ошибкой.
5. После успешной подготовки `train_pipeline` сохраняет в MLflow legacy TXT/GeoJSON либо все per-image GeoJSON вместе с manifest в `dataset/`.
6. `train_pipeline` вызывает `tile_preparation.create_tile_dataloader` для train и val со списком сцен и одинаковым `tile_split`. Окна строятся отдельно внутри каждого TIFF, включая nodata-padding края; split детерминирован по `scene_id+x+y`. Train читает raster/rasterize лениво, использует LRU дескрипторов, category-aware sampling и prefetch. Val выбирает фиксированный balanced subset и кэширует его при безопасном лимите RAM, иначе лениво читает те же индексы. Binary mask: `-1/0/1`, multiclass: `-1/0/1..N`; nodata по значению, невалидная `dataset_mask` и padding за границей TIFF объединяются и принудительно получают target background `0`, а `-1` декодируется в background target с повышенным pixel weight. Полностью невалидные тайлы отфильтровываются, частично невалидные остаются в обучении. Аугментации геометрически преобразуют маску невалидности вместе с изображением и target и восстанавливают исходное значение nodata после фотометрических изменений.
7. `train_pipeline` создаёт одну из семи UI-архитектур (`smp_deeplabv3plus_resnet50`, `smp_segformer_b2`, `smp_segformer_b3`, `smp_unet_resnet34/50/101/152`) через `models.create_model` с `train.input_channels` или загружает checkpoint через `models.load_checkpoint`, если `train.initial_checkpoint_uri` задан. Спецификация checkpoint обязана совпадать с запросом, поэтому трёх- и четырёхканальные модели нельзя перепутать. Для multiclass `train.output_channels` строго равен числу manifest-классов плюс background.
8. `train` выполняет PyTorch обучение segmentation-модели: AdamW, cosine scheduler, binary BCE/Dice-family loss или multiclass cross entropy/CE+Dice, validation metrics, early stopping и best/final checkpoints. Для binary рассчитываются пиксельная и объектовая F1 по порогам; `train.quality_metric` выбирает метрику best checkpoint и early stopping. Объекты сопоставляются один к одному при `IoU ≥ 0,5`, каждый тайл оценивается независимо; независимые пары «порог × тайл» обрабатываются ограниченным пулом не более чем из 8 CPU-потоков с последовательной агрегацией счётчиков. Для multiclass основной score — macro pixel F1 по типам; дополнительно сохраняются per-class precision/recall/F1/IoU, micro и foreground F1. Единый confidence threshold выбирается по macro F1, затем macro precision и большему threshold. Nodata уже представлен target background `0`, поэтому ложный прогноз класса на нём входит в loss и TP/FP/FN как обычный false positive. Background имеет фиксированный вес `1`, `pos_weight` усиливает positive pixels в binary loss, а `hard_negative_weight` усиливает штраф только на пикселях supervision mask со значением `-1`; эти пиксели становятся target background `0`, но получают повышенный pixel loss weight. Binary checkpoint остаются совместимыми; multiclass metadata дополнительно содержит task, полную class schema, threshold и структурированные метрики.
9. `train_pipeline` передает в `train` progress sink, который пишет метрики каждой завершенной эпохи в MLflow сразу через `mlflow_adapter.log_training_epoch`.
10. `mlflow_adapter` записывает итоговые train/val метрики, артефакты, модель или чекпойнт, отчет tile preparation, отчет времени и итоговый
   отчет.

## Конвейер Инференса

1. CLI получает путь `--config`, вызывает `settings.api.load_settings` и инициализирует текущие настройки процесса.
2. Загрузить модель или чекпойнт и определить точное число входных каналов из `ModelSpec`.
3. Выполнить инференс напрямую в Python/PyTorch по локальной папке `dataset.images_dir`; снимок с несовпадающим числом каналов отклоняется без обрезки или дополнения каналов.
4. Записать результаты и отчеты в MLflow.
