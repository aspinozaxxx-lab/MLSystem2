# Модуль training_ui_api

## Назначение

`training_ui_api` — FastAPI-сервис сайта MLSystem2. Он хранит UI-данные и управляемый каталог датасетов, управляет очередями training/inference и предоставляет редактор per-image разметки с версиями и связями в UI-БД. Git хранит собранные датасеты. Опубликованные файлы читаются из серверного `mlmarkup-editor` сразу после commit/push, без обратной доставки с GitHub. Публикация и чтение согласованы межпроцессным lock; задания получают отдельную копию файлов, личные черновики остаются в БД.

Синхронизация каталога и его дешёвая файловая ревизия пропускают скрытые папки и `__pycache__`
на уровнях классов и датасетов. Служебный кэш Python не создаёт сущности каталога;
обычные пустые классы и legacy-разметка непосредственно в папке класса по-прежнему поддерживаются.

Frontend — React + TypeScript + Vite SPA. TypeScript-типы генерируются из OpenAPI командой
`npm run generate:api --prefix frontend`, production static собирается в `frontend/dist`, а сервер Node.js
на проде не нужен.

Компактный интерфейс включается до 700 CSS-пикселей по ширине либо до 1000 × 500 при повороте
телефона. Страницы и HTTP-контракты общие с настольной версией. Меню показывает иконки с доступными
названиями; очередь, результаты и экспорт моделей — карточки; матрицы прокручиваются внутри панели.
На телефоне шаблоны выбираются списком, отдельно для обучения и инференса. Формы сохраняют действия
и шрифт ввода не меньше 16 px; учитываются safe area и динамическая высота, масштабирование разрешено.
Списки снимков можно свернуть. Каждый снимок редактора открывается на телефоне в режиме просмотра
без выбора, правки и рисования; «Править» включает инструменты, «Просмотр» отключает их. Карты
поддерживают перемещение одним пальцем и масштаб двумя, а полный экран — запасной режим внутри
страницы. Правила — `styles/mobile.css`, стили просмотрщика и общий `useCompactLayout` во frontend.

В результатах плашки датасетов внутри класса отсортированы по последнему успешному обучению, свежие первыми;
без успешных обучений — в конце, при равной дате — по названию и ключу. Сортировка использует историю независимо
от выбора основной сети, исторический результат без `trained_at` — его `created_at`. Строка «Обновлено»
под названием класса не показывается.

Каталоги результатов и редактор классов используют общее компактное меню классов с количеством датасетов;
редактор также показывает число пользовательских черновиков. На телефоне меню заменяется списком сверху.
Результаты, тестовые разметки и их мастер, редакторы классов и датасетов используют единый выбор класса
в текущей вкладке и localStorage: переход, обновление и возврат назад сохраняют его. Если на странице
класс недоступен, она показывает первый доступный, сохраняя общий выбор для остальных страниц;
прямая ссылка на датасет в редакторе выбирает его класс. Рабочая область показывает только выбранный класс.
На странице результатов под карточками датасетов сразу показаны сети выбранного датасета,
а ниже — все обучения класса по всем его датасетам, включая ошибки и активные задания.
Карточка выбирает датасет в той же странице; прежние адреса результатов остаются действующими.
По умолчанию выбран основной датасет, при его отсутствии — первый в текущей сортировке.
На узкой рабочей области таблицы сетей превращаются в карточки независимо от ширины окна;
на телефоне история обучений также показана карточками без горизонтальной прокрутки.
История обучений ограничена выбранным классом; редактор сохраняет незавершённую правку названий
при переключении классов внутри страницы. Настройки и карточки используют доступную ширину, новый класс
создаётся в диалоге из заголовка; формы ввода на телефоне сохраняют шрифт не меньше 16 px.

Редакторы шаблонов обучения и инференса сохраняют только выбранный шаблон, без кнопок «Ко всем».
Во время сохранения поля и действия отключены, кнопка показывает вращающийся индикатор; успешный
ответ подтверждается названием шаблона под кнопкой. Правка, сброс, новая попытка и смена шаблона
убирают прежнее подтверждение. Ошибка использует общее окно ошибок и не показывает успешное сохранение.

Доставка `frontend/deploy.py` сначала публикует зависимости и атомарно заменяет `index.html`.
Хешированные файлы предыдущих сборок в `assets` сохраняются до семи суток с общим целевым пределом
128 МиБ; старейшие неактуальные файлы вытесняются, файлы текущей сборки не удаляются. HTML отдаётся
с `Cache-Control: no-store`. При ошибке загрузки модуля очень старой вкладки только страница просмотра
псевдоразметки может автоматически перечитаться, не чаще раза в минуту; редактор и формы не перезагружаются.

Главная показывает новости из `frontend/src/News.tsx` с датой и адресом `#/news/<slug>`. Новая существенная
возможность описывается большой статьёй о пользе и использовании, с обязательной подходящей картинкой
из `frontend/public/news/` (скриншот либо обозначенная схема, альтернативный текст, без секретов и личных данных).
Мелкие доработки, улучшения и исправления — компактный список `updates`, одна строка на изменение; большая
статья и картинка не требуются. Новости выходят с функционалом, старые публикации и адреса сохраняются.
Внутренние технические изменения без пользовательского эффекта новости не требуют.
Таблица последних событий сохраняется только в результатах.

## Публичный интерфейс

- `create_app() -> Any` - создает FastAPI-приложение.
- `get_openapi_schema() -> dict[str, Any]` - возвращает OpenAPI-схему сервиса.
- `main() -> None` - запускает `uvicorn` для сервиса.
- `worker_main() -> None` - отдельно запускает исполнителей общей очереди и batch-задач тестовых разметок.

## Публичные контракты

`AnnotationVersionUsage`: `dataset_key`, `dataset_name`, `indirect` (использование через управляемый набор).
`AnnotationVersionInfo`: `id`, `name`, `revision`, `created_at`, `updated_at`, `usages`. `AnnotationVersionCatalog`: `image_id`, `revision`,
`selected_id`, `versions`. `AnnotationVersionDetail`: `catalog`, `version_id`, `geojson`.
`AnnotationVersionEdit`: `id`, `name`, необязательный `source_id`, `geojson`.
`AnnotationVersionDraft`: `catalog_revision`, `selected_id`, `edits`, `replacements` (удаляемый UUID → заменяющий UUID).
`DatasetEditorSaveDraftRequest` и `DatasetEditorDraftInfo.annotation_versions` передают этот личный черновик;
`DatasetEditorDraftSummary.selected_version_id` показывает его выбор. `DatasetEditorSceneDetail.annotation_versions`
содержит опубликованный каталог. `DatasetEditorSceneInfo` добавляет `image_id`, `annotation_version_id`,
`annotation_version_name`, `annotation_version_count`; `revision` становится непрозрачной ревизией файла и выбора.
`GET /api/v1/dataset-editor/datasets/{dataset_key}/scenes/{annotation_name}/versions/{version_id}` возвращает
`AnnotationVersionDetail` после проверки класса и снимка. Изменения используют существующие save/discard/publish,
без отдельных немедленных мутаций. Каталог вариантов, связей и журнал завершения публикации хранятся в UI-БД;
Git содержит собранные датасеты. Импорт прежних файлов не объединяет одинаковые разметки разных датасетов.
`AnnotationVersionInfo.updated_at` — дата последнего опубликованного изменения версии в UTC;
для прежних файлов это дата импорта в каталог. Переключение версии и черновик её не меняют.
Манифест `.mlsystem2-annotation-selections.json` явно добавляется в Git вопреки ignore-правилам;
исключение не распространяется на посторонние файлы или каталоги.
При публикации общей версии обновляются все активные использования; удаление требует замены, конфликт — 409.
Подробные правила сущностей, независимого копирования и восстановления — в `docs/architecture.md`.

`AnnotationFeatureHistoryEntry`: `id`, `action` (baseline/created/updated/deleted), `username`,
`published_at`, `commit`, `feature`, `crs`. У baseline автор и дата неизвестны, feature содержит
прежний контур; у удаления feature=null. `AnnotationFeatureHistory`: `version_id`, `feature_id`, `entries`.
`GET /api/v1/dataset-editor/datasets/{dataset_key}/scenes/{annotation_name}/polygon-history` принимает
`feature_id` и необязательный `version_id`, проверяет принадлежность и возвращает опубликованные
состояния одного полигона. Управляемый редактор разрешает источник через служебные origin-ключи.
`annotation_feature_events` записывается только при завершении подтверждённой публикации, атомарно
с версиями и журналом; черновики и отмены в историю не попадают. Нужна миграция `20261019_0036`.
Плашка числа версий в списке снимков открывает карточки с датами, использованием и действиями;
клик снаружи закрывает меню. При выборе полигона доступны история и сравнение контуров без редактирования.
Старым полигонам без ID чтение назначает стабильные виртуальные ID, не переписывая исходники.
Рисование и Modify автоматически обрезают зоны и объекты по footprint на клиенте, save/publish
повторяют обрезку на сервере. ID и свойства сохраняются, исчезновение всех зон из-за обрезки запрещено.
Прежняя полностью внешняя зона сохраняется при чтении с предупреждением, чтобы её исправили либо
удалили явно и не включили весь снимок случайной публикацией другого объекта.

Разовая служебная очистка точных копий — приватная команда
`python -m mlsystem2.training_ui_api._annotation_deduplication --report <новый_отчёт.json>`;
`--apply-plan <проверенный_отчёт.json>` применяет его после повторной проверки. Она использует штатный
журнал публикаций, сохраняет вариант из `main` в приоритете, пропускает каталоги с черновиками и записывает
исключение автозапуска только для технических итоговых ревизий. Ни HTTP-контракты, ни независимое
копирование датасетов не меняются. Порядок и проверки описаны в архитектуре.

`UsageConfig`: `metrica_counter_id` — номер счётчика Яндекс Метрики или `null` при отключении;
`metrica_user_id` — стабильный обезличенный ID текущего канонического пользователя.
`GET /api/v1/usage/config` доступен только по пользовательской сессии и не кэшируется.
Настройка — `MLSYSTEM2_METRICA_COUNTER_ID`. Явные операции API помечаются заголовком
`X-Grovika-Action` и `X-Grovika-User` для передачи события frontend в Метрику; тела запросов и ключи сущностей
не включаются в событие. Обработка запроса не зависит от доступности Метрики. Отчётов и
хранения аналитики в UI-БД нет; правила — в `docs/architecture.md` и
`docs/runbooks/grovika_usage_metrica.md`.

`DatasetEditorImportRequest` содержит `scenes` (от 1 до 100 элементов `DatasetEditorImportSceneRequest`):
`annotation_name` — имя per-image GeoJSON, `geojson` — FeatureCollection. Общий предел — 50 МиБ.
`POST /api/v1/dataset-editor/datasets/{dataset_key}/drafts/import` проверяет весь пакет и однозначное
соответствие серверным TIFF; возвращает `DatasetEditorSceneListResponse`. Создаются только личные черновики,
без файлов разметки, Git-коммита и изменения состава обучения. Отсутствующая опубликованная сцена имеет
`revision="new"`, её черновик — `base_revision="new"`; она видна владельцу в списке и на карте, доступна
изменению, отмене и общей публикации. Уже добавленные снимки и собственные черновики не перезаписываются.
При публикации новые и изменённые сцены сохраняются вместе; появление файла после импорта даёт `409`.
Управляемый датасет получает членство новой сцены и правки исходных классов только при публикации.
Импорт принимает `clip_to_footprint=false`. При выходе объектов за валидные данные возвращается `400`
с `detail` и `code="annotation_outside_footprint"`, количеством объектов и предложением обрезки, без
записи черновиков. Подтверждение повторяет запрос с true: существующая обрезка учитывает отверстия и
nodata, исключает пустые объекты, сохраняет ID/атрибуты. Зоны обрезаются автоматически, даже без
подтверждения обрезки импортируемых объектов; удаление всех зон обрезкой запрещено. Остальные проверки строгие;
весь пакет повторно проверяется перед атомарным сохранением.
Ошибки роли и типа включают файл, номер объекта, поле, неверное значение и допустимые роли либо
типы текущего датасета. Названия ролей строго канонические, `negative` не заменяется на `hard_negative`.
Frontend показывает ошибку внутри окна импорта без сброса выбранных файлов и текущего снимка;
при `401` сохраняется общий переход к входу. В окне заранее перечисляются роли и multiclass-типы датасета.

`DatasetEditorSceneInfo`, `DatasetEditorDraftSummary` и унаследованный `DatasetEditorDraftInfo` содержат `annotation_zone_count=0`. В GeoJSON редактора поддержана служебная роль `annotation_zone`, optional `_mlsystem2_class` задаёт исходный класс управляемого датасета. Отсутствие класса означает все источники. Зоны проходят штатные черновики, публикацию, копирование и пересборку, отдельно отображаются и считаются. Как и объекты, зоны автоматически обрезаются по valid footprint TIFF, включая отверстия и отдельные части; проверки типа, геометрии и CRS обязательны. Подготовка обучения дополнительно ограничивает историческую внешнюю разметку снимком. `dataset_preparing.api.annotation_regions` ограничивает создаваемые эталонные тайлы размеченной территорией; обычная псевдоразметка остаётся поснимочной.

`ConfigSchema.pipeline_descriptions` содержит подробные описания профилей.
`ConfigSchema.pipeline_defaults` содержит серверные наборы параметров при переключении конвейера;
по умолчанию это пустой словарь. `JobSummary`, `JobDetail` и `TrainingResultInfo.pipeline_variant`
принимают `legacy|next_gen|next_gen2|next_gen3|next_gen4|next_gen4_global_norm|next_gen4_augmentation_v3|next_gen4_augmentation_v4|object_f1|object_f1_v2`. Новая таблица БД не требуется.

Next-gen3 доступен в том же выборе для поддерживаемых SegFormer в шаблонах и ручном запуске, binary/multiclass, Канопус/RGB. Его defaults отдельные, прежние сохранённые шаблоны не переключаются. Фиксированный профиль наследует next-gen2, заменяя сэмплер автоматической политикой без новых полей. Описание объясняет квоты, ошибки фона, защиту полноты и ограничение территориальной независимости. Нативный инференс, F1 и ZIP наследуют Gaussian/вероятности/порог 0,9 next-gen2, сохраняя точное имя `next_gen3` в metadata. Публикуется статья `#/news/next-gen3-adaptive-background` с явно обозначенной схемой. HTTP endpoints, таблицы и автоматические правила не добавляются.

Next-gen4 — отдельный выбор с автоматическим фоном и обучающим шагом в размер тайла; размеры 512/768/1024/1536 остаются доступными в запуске и шаблонах. Инференс использует Gaussian с половинным шагом и padding краёв. Нативный и переносимый инференс next-gen2/3/4 исключает nodata/raster mask до и после постобработки; текущая версия оценки и экспорта — `notebook_valid_data_v2`, финальный брик — `ClipToRasterValidData`. Сохранённые предсказания и метрики обучения не переписываются. Новость — `#/news/next-gen4-disjoint-tiles`.

Next-gen4-global-norm — отдельный выбор `next_gen4_global_norm` в тех же шаблонах SegFormer и ручном запуске, binary/multiclass, RGB/RGB+NIR. Общие train-границы хранятся внутри checkpoint; UI и runners их не пересчитывают и не нормализуют вход повторно. Worker сохраняет точный вариант и stride=tile_size, инференс/экспорт наследуют Gaussian и padding next-gen4. Старые шаблоны не переключаются. Новость `#/news/next-gen4-global-norm` содержит описание, порядок запуска, ограничения и поясняющую SVG-схему. Новых HTTP endpoints и таблиц нет.

Next-gen4-augmentation-v3 — отдельный выбор `next_gen4_augmentation_v3` в тех же формах с прежними ограничениями, нормализацией, Gaussian, padding и порогами. Описание объясняет попиксельную защиту valid-mask, отмену небезопасного блока и отсутствие гарантий роста F1. Worker передаёт профиль без подмены; checkpoint и ZIP сохраняют `augmentation_policy=validity_guard_v3` и train-границы. Старые шаблоны не переключаются, новых HTTP endpoints и таблиц нет. Статья `#/news/next-gen4-augmentation-v3` публикуется вместе с поясняющей SVG-схемой.

Next-gen4-augmentation-v4 — дополнительное значение `pipeline_variant` контрактов задач и результатов и отдельный выбор в тех же формах SegFormer. Наследует ограничения v3, добавляет защищённые вырезки внутри train и отчёты плотных окон. ZIP сохраняет `augmentation_policy=validity_guard_v4_context_crop_v1`, `context_crop` и общую нормализацию. Worker, псевдоразметка и test F1 сохраняют прежний Gaussian, padding и пороги. Профиль не назначается старым шаблонам автоматически; статья `#/news/next-gen4-augmentation-v4` с поясняющей SVG объясняет применение, отчёты и ограничения.

`object_f1_v2` показывается как «object f1 v2» отдельным выбором для SMP SegFormer B0/B1/B2/B3
в шаблонах и ручном запуске. Он доступен только бинарным датасетам Канопуса и ортофото;
многоклассовая форма скрывает оба object-профиля, сервер также проверяет ограничение.
При запуске назначается объектовая метрика. Предобучение, тайл 512/768/1024/1536 и три условия
остановки изменяемы; остальные параметры фиксированы, batch зависит от архитектуры и окна.
Описание объясняет обучение фона, внутренности и широкой адаптивной границы, независимые группы
снимков, восстановление полной площади и необходимость проверки качества. Исходные шаблоны,
автоматические правила и основная сеть не меняются. Статья `#/news/object-f1-v2-boundaries`
публикуется со схемой механизма, явно отличённой от реального результата распознавания.

- Тестовый F1 в результатах открывает `#/test-f1/<training_result_id>`. Карта общая с псевдоразметкой: поснимочный выбор, независимые слои эталона и прогноза, обе оценки выборки и снимка одновременно, переключение пиксельных областей и целых объектов TP/FP/FN зелёным/красным/жёлтым. Runner сохраняет использованные маски, экземпляры, пары ID того же сопоставления IoU ≥ 0,5 и поснимочные счётчики; worker переносит их в `stored_files_root/test-f1/<job_id>` до удаления scratch и записывает непрозрачные ссылки в `metrics.viewer_jobs`. Частичный managed-пересчёт сохраняет ссылки остальных классов. Старая ревизия показывается с предупреждением; при сохранённых масках объектовая карта восстанавливается на CPU без ML: исходный GeoJSON используется только при совпадении ревизии и маски, иначе связные области с явным предупреждением; оценки просмотра пересчитываются согласованно с картой, историческая запись БД сохраняется. Кэши ограничены и учитывают ревизии файлов. Только отсутствующий прогноз требует явной подготовки полным F1-job, удалённый TIFF допускает слои без подложки. Список на телефоне заменяется селектором, карта поддерживает жесты и полный экран.
- `PseudoMarkupViewInfo` — ID результата/сети, названия сети, источника и обучающего датасета, дата, ссылка GeoJSON, счётчики объектов/снимков, список `scenes` и предупреждения. `PseudoMarkupSceneInfo` — ID снимка, относительное имя, авторизованные `raster_url` и `footprint_url`, bounds в EPSG:3857, признаки `has_alpha`, `has_nir` (по умолчанию false) и nodata. Просмотр предлагает RGB/NRG/NGB для снимков с NIR; RGB/RGBA сохраняют RGB и прозрачность. Сочетания каналов общие с редактором. Колесо работает при наведении без фокуса, кнопок «+» и «−» нет. Frontend сопоставляет bounds снимков с текущим кадром карты и подсвечивает соответствующие строки списка, включая частичное пересечение и полноэкранный режим; счётчик не зависит от поиска. Глаз строки независимо скрывает её снимок; подсветка и счётчик учитывают только включённые снимки. Наведение или фокус подсвечивает фактический контур данных без nodata, нажатие на имя приближает снимок и закрепляет контур; повторное нажатие сразу снимает выделение, сохраняя охват карты. Готовый кадр сбрасывается при изменении видимости. Временные ошибки загрузки повторяются ограниченно, отмена не создаёт предупреждения; невосстановленные ошибки можно повторить кнопкой.

Оба маршрута авторизованы, проверяют состав каждой разметки, ограничение prepared_images и ревизии (412); не ставят ML-заданий и не меняют БД. Точные счётчики обрабатывают TIFF окнами до 512×512, полигоны объединяются в foreground на нативной сетке без nodata/alpha; маски обзора ограничены размером карты. Разрыв соединения отменяет расчёт без сохранения частичных значений.

  strict model config Triton принимает HF-граф с изначально символической размерностью каналов.

  (окно сети, шаг в половину окна, Gaussian sigma 0.25), затем строгий порог 0.9 либо явный override.
  SplitRaster сохраняет исходные пиксели под nodata, VectorizeMasks строит контуры по границам пикселей.
  Для серверного Compose runner расширения регистрируются из `_geoalert_notebook.py` перед загрузкой YAML:
  полные окна через Triton adapter, Gaussian-объединение с полосовым буфером и SplitRaster без изменения исходных пикселей.
  В заданиях сохраняется вариант конвейера: `next_gen2` применяет только явные параметры постобработки
  общего шаблона, назначенного классу, без автоматических профилей по числу снимков.

  источникам и продолжениям. Архив/отмена не перенумеровывают оставшиеся сети; имя датасета счётчик не меняет.

  лимита времени — 3600 секунд), `last_checkpoint_available` после проверки артефактов завершённого MLflow run.
- `POST /api/v1/results/training/{result_id}/continue` — новый ручной training job от выбранного checkpoint.
  `TrainingContinuationCreate` принимает три строго положительных целых лимита, `dataset_source=original|current`
  (по умолчанию `original`, включая старые запросы), `checkpoint=best|last`
  (по умолчанию best) и UUID `request_id` для идемпотентной отправки. Иные параметры не принимаются.
  Оба маршрута требуют пользовательскую сессию. Источник — успешный нативный result с завершённым training job
  и сохранёнными параметрами; импортированные модели и незавершённые работы не подходят. Worker скачивает
  `best.pt`/`final.pt` из исходного завершённого запуска и передаёт через существующий `train.initial_checkpoint_uri`.
  При недоступности артефакта новый этап получает ошибку, обучение с нуля не начинается.
  Приватный `_training_continuation.py` копирует конфигурацию без применения текущего шаблона, сохраняет
  исходные версию и снимок разметки при `original`, восстанавливает их из MLflow при утрате временной папки.
  При `current` доступность того же активного датасета, задача, ID/slug классов и число каналов проверяются
  при отправке и старте. Штатный snapshot под блокировкой MLMarkup берёт опубликованные снимки и геометрию,
  включая правки за время ожидания; job/result получают фактическую ревизию. Другой одноимённый набор,
  личные черновики и текущий шаблон не подставляются. Custom-upload использует `original`.
  Выбор, исходная и фактическая версии сохраняются в JSON происхождения без новой таблицы. При наличии
  используется полный `config/resolved_train_config.json`; исторический резерв — исходный YAML запуска.
  Все новые задания сохраняют полный валидированный снимок обучения `SystemSettings` без блока `inference` в `run.yml` до старта процесса.
  Оптимизатор/scheduler и счётчики создаются заново; это дополнительный этап от весов, а не восстановление
  процесса после паузы. Диалог предлагает `run_inference_after_training` и `secondary_priority` с исходными
  значениями: обе опции можно изменить для нового этапа. Эти поля в `TrainingContinuationCreate` допускают
  `null`/отсутствие для наследования при запросе старого клиента; `TrainingContinuationOptions` возвращает
  фактические булевы значения. Изменение опции при повторе одного `request_id` отклоняется, как изменение
  лимитов или чекпойнта. Используются штатные создание псевдоразметки и приоритет очереди; новые механизмы
  доставки результата не вводятся. Ссылки на уже поставленные задания
  и запрос прежней остановки очищаются. Исходный result, его звезда и псевдоразметки не меняются.
  `TrainingResultInfo.can_continue_training` определяет наличие кнопки без сетевого обхода артефактов на
  каждой строке; `continued_from_result_id`, `continued_from_epoch` (для best), `continued_from_checkpoint`
  и `continued_from_dataset_source` (`original|current`, `null` у исходной сети)
  обозначают происхождение нового этапа. Доступность файла уточняется при открытии диалога и отправке.
  UI группирует цепочки и ответвления продолжений с исходной сетью; псевдоразметки остаются под своим
  этапом. `PseudoMarkupResultInfo.checkpoint_epoch` и `PseudoMarkupViewInfo.checkpoint_epoch` показывают
  эпоху выбранных весов исходного результата псевдоразметки (либо `null`, если эпоха неизвестна).
  `PseudoMarkupResultInfo.checkpoint_kind` и `PseudoMarkupViewInfo.checkpoint_kind` возвращают
  `best|last`; исторические задания без выбора считаются `best`.
  Прежние MLflow run и checkpoint сохраняются; номера эпох относятся к своему этапу.
- Запуск строится как «архитектура → конвейер → предобученные веса». SegFormer B0/B1/B2/B3 поддерживают
  `legacy` и `next_gen2` с независимой галочкой `train.pretrained` для binary и multiclass; остальные сети — `legacy`.
  HF исключён из каталога и новых ручных/автоматических обучений. Исторические результаты и инференс сохранены.
  Профили и batch для архитектуры передаются через `ConfigSchema.pipeline_defaults`.
  `next_gen` отклоняется в новых заданиях и изменениях шаблонов; прежние шаблоны обновляются на next-gen2.
  История и уже созданные задания не меняются. Бинарный профиль next-gen2 поддерживает RGB и RGB+NIR.
- `POST /api/v1/jobs/{job_id}/stop-and-save-best` - кооперативно остановить выполняющееся ручное обучение и выдать `best.pt` максимальной валидационной F1 как успешный результат; до появления первого лучшего чекпойнта операция недоступна.
- `GET /api/v1/queues/count` - лёгкое число active jobs (`queued|running|paused`) для счётчика меню; `GET /api/v1/queues` остаётся полным снимком очереди.
- `JobSummary.started_by` и `JobDetail.started_by` — логин инициатора из `ui.started_by` либо `null`.
  В очереди он показан в колонке «Автор»; автоматизация обозначается отдельно. Перед первым сохранением
  новых ручных заданий HTTP-сессия записывает канонического пользователя; существующим заданиям автор
  не меняется при повторе запроса, параметры клиента не могут его подменить. Заказанная после обучения
  псевдоразметка наследует инициатора этого обучения; исторические данные без автора не дополняются догадками.
- `PUT /api/v1/test-samples/{sample_id}/primary` - совместимо назначает, заменяет или снимает единственную основную разметку класса.
- `GET /api/v1/results/datasets/{dataset_key}`, `POST /api/v1/results/datasets/{dataset_key}/pseudo-markup` и `POST /api/v1/results/datasets/{dataset_key}/test-f1` - результаты датасета, ручная псевдоразметка и ручная постановка оценок всех успешных сетей этого датасета в inference-очередь.
  Ручная псевдоразметка принимает multipart-поле `checkpoint=best|last`, по умолчанию `best`.
  `last` означает точный `checkpoints/final.pt` завершённого нативного запуска; отсутствие файла,
  включая остановку с сохранением лучшего результата, и импортированные сети отклоняются до постановки.
  Worker повторно проверяет файл и сохраняет фактические эпоху, порог, метаданные и SHA-256
  в `JobRow.config`, затем передаёт тот же локальный файл штатному runner. Кеш Geoalert различает
  файлы по SHA-256. Выбор не меняет F1, автоматизацию, основную сеть и неявные источники
  тестовых наборов/редактора: они используют только лучшие веса. Сохранённые явные ссылки
  на псевдоразметку не заменяются.
- `POST|DELETE /api/v1/results/training/{result_id}/primary` - явное назначение успешной сети основной для её класса или снятие отметки; без назначения расчёты используют последнюю успешную сеть без звезды. Реальная смена только помечает зависящие от неё контрольные метрики устаревшими; инференс не запускается. Актуальные оценки остальных сетей сохраняются.
- `GET /api/v1/pseudolabel/classes`, `POST /api/v1/pseudolabel/jobs`, `GET|DELETE /api/v1/pseudolabel/jobs/{job_id}` и `GET /api/v1/pseudolabel/jobs/{job_id}/result` - серверное распознавание AOI без передачи клиентских растров; полный контракт описан в `docs/pseudolabel_api.md`.

Сохранённая контрольная метрика каждой тестовой разметки получается прямым инференсом эффективной сети класса:
явно назначенной либо, при отсутствии назначения, последней успешной. Неявный выбор не сохраняется и не показывает
звезду. Метрика фиксирует сеть, её обучающий датасет, ревизию состава, effective inference-шаблон, профиль и версию
evaluator. Поле датасета тестовой разметки означает источник её тайлов, а отдельные ссылки фиксируют использованные
сеть этого датасета и точную псевдоразметку. Эта пара используется отдельно для создания набора, черновых
`evaluate-preview`/`optimize-preview` и поснимочного кэша оптимизатора. Матрица `training_result_test_metrics`
остаётся независимым контуром: успешные сети всех
обычных датасетов класса оцениваются на единственной основной тестовой разметке класса. Для сети управляемого
датасета матрица хранит составную оценку: каждому semantic-каналу соответствует основная тестовая разметка его
исходного класса, а сигнатура задания включает весь набор sample/revision/enabled tiles. Pixel/object F1 каждого
класса считается независимо только на его выборке; общий F1 равен простому арифметическому среднему поклассовых
F1 без взвешивания по числу пикселей, объектов или тайлов. Сверка только отмечает устаревшие оценки,
не ставя заданий. Единственный автоматический запуск F1 — успешное завершение обучения новой сети;
прямые оценки наборов также запускаются, если эта сеть стала эффективной сетью класса. Ручная команда
датасета охватывает все его успешные сети, иконка возле устаревшего F1 — только выбранную сеть.
Изменение разметки, состава, основной сети, шаблона, профиля и старт сервиса не запускают пересчёт;
устаревшие результаты отбрасываются без автоматического повтора. Явный частичный пересчёт semantic-канала
остаётся поддержан очередью; без полной сохранённой структуры выполняется полный расчёт.
Ручной F1, включая прямую оценку тестовой разметки, имеет обычный ручной приоритет без срочности
и второстепенности. Автоматический F1 новой эффективной сети срочный: обучение кооперативно
приостанавливается через `pause.request`.
Оценка новой неэффективной сети имеет фоновый приоритет; ручная команда повышает его без дубликатов.
Семантическая PNG-маска объединяет пиксели одного класса и применяется только в пиксельном контуре оценки.
Соприкасающиеся исходные объекты остаются отдельными feature в GeoJSON; визуализация и помеченные JPEG проводят
границы по их instance-ID, а объектовая метрика сопоставляет эти векторные feature один к одному.
При включённом `exclude_boundary_objects` исходный объект должен полностью помещаться в footprint тайла;
пересекающий границу объект целиком исключается из отбора, квот, GeoJSON, маски, превью и объектовой метрики.
Флаг разрешён только для классов с основной объектовой метрикой и сохраняется в batch-запуске и тестовом наборе.
Каталог результатов выделяет основной датасет и на каждой карточке показывает F1 сети этого датасета: явно
отмеченной основной, если она принадлежит ему, либо последней успешной. Оценка берётся по общей основной тестовой
разметке класса из существующего результата; для управляемого датасета карточка отдельно показывает средний и
цветные поклассовые F1 по основным выборкам источников. Каждый поклассовый показатель занимает собственную строку
в границах своей карточки или ячейки; длинное имя переносится, а числовой F1 остаётся видимым. Блоки метрик не
конкурируют с названием датасета, количеством снимков и действиями. Открытие каталога не создаёт отдельный
расчёт.

Seed inference-шаблона рек идемпотентно добавляет Smooth `1 / 0.125`, меняет Simplify с `15` на `1 м` и
сохраняет явные пользовательские переопределения. В Geoalert pipeline речные полигоны помечаются в полосе одного
пикселя от границы растра, затем проходят цепочку
`FilterSmallObjects → RemoveSmallHoles → FilterCompactObjects → Smooth → Simplify`; служебный тег удаляется
последним brick. Compact-фильтр не имеет порога площади. Граничные и вырожденные геометрии сохраняются,
а невалидные не приводят к ошибке фильтрации. Озёрный шаблон не включает compact-фильтр и сглаживание.
Промежуточная конфигурация Geoalert сохраняет режим фильтра: `keep_compact` выбирает
`FilterNonCompactObjects`, `remove_compact` — `FilterCompactObjects`. Объектные профили сохраняют
опции пометки краёв `VectorizeMasks` наряду с `instance_id`; смена постобработки обновляет
сценарий кеша, не веса модели. В ортофото `object_f1_v2` общие вершины instance-контуров
согласуются до репроекции; ненулевое упрощение выполняется совместно в UTM через
`CoverageSimplify` (`shared_edges_v1`). ID, внешнее покрытие, части и отверстия сохраняются;
конечная репроекция проверяется до сохранения. Небезопасный допуск уменьшается вдвое
совместно для всего покрытия, максимум восемь попыток; запрошенный и фактический допуски
видны в журнале. Если безопасного варианта нет, сохраняются проверенные исходные контуры;
небезопасный исходный контур даёт ошибку до сохранения. Исторические профили
используют прежний `Simplify`.
В ортофото v2 запрос Triton содержит одно окно; CUDA EP и нативный runner используют FP32
без TF32. Compose может перекрывать обработку двух независимых сцен, ограничивая RAM;
неизвестная оценка памяти оставляет одну сцену. Каждый поток имеет собственный Compose
и клиент, итоговый порядок сохраняется. Пауза дожидается текущих сцен перед выгрузкой
модели. Версии кеша фиксируют новый профиль; обучающие метрики и исторические профили
не переписываются. Новых HTTP-контрактов нет.

## Список используемых данным модулем модулей и с какой целью

- `models.api` - получить публичный список поддерживаемых архитектур и прочитать выбранный последний чекпойнт на CPU через штатный загрузчик.
- `mlflow_adapter.api` - получить и создать MLflow experiments, прочитать лучший нативный checkpoint либо произвольный артефакт завершённого run и скачать его для инференса; сервис не пишет MLflow-метрики.
- `mlflow_adapter.contracts` - передать публичные DTO experiment, нативного checkpoint и артефакта завершённого run.
- `settings.contracts` - валидировать YAML-настройки, сформированные для запуска training CLI.
- `dataset_preparing.api` и `dataset_preparing.contracts` - сопоставлять legacy TXT и per-image GeoJSON с TIFF.

### Автоматизация

Автоматизация хранится в таблицах `automation_controls` и `automation_rules`. Правило задается парой
`dataset_key + architecture` и двумя флагами: `training_enabled` и `pseudo_markup_enabled`. `Custom` не участвует в
автоматизации. Рабочий Git-клон и сохранённый архивный runtime с `.mlsystem2-release-metadata.json` сохраняют формат
`git:{commit_sha}`; иначе используется `fs:{mtime_ns}`. После изменения источника, типа снимков или метрики версия содержит управляемую ревизию и
файловую версию, поэтому активное правило видит значимое изменение.

HTTP API и worker очередей запускаются отдельными процессами; API не исполняет фоновые jobs и не материализует управляемые датасеты. Каталог создаёт идемпотентный запрос, а worker под межпроцессным lock строит по одному cache и атомарно публикует его. Готовая сводка устраняет повторный разбор GeoJSON; footprint переиспользуется из источника. Dispatch очереди выполняется с коротким интервалом, а синхронизация автоматизации — с отдельным более редким интервалом. При включенном глобальном switch автоматизация создаёт
auto training job для текущей версии датасета, если нет текущего auto result/job для этой версии. Defaults берутся
из активного шаблона конкретного датасета `(architecture, dataset_key)`. После смены ключа датасета осиротевшая
связь однозначно восстанавливается по имени `класс\датасет`; если датасетный шаблон не создан, используется
базовый шаблон сети `(architecture, null)`. После успешного auto training result с MLflow run id создается auto pseudo-markup job;
для per-image датасета временный TXT формируется из сопоставленных TIFF. Очередь jobs единая: ручная псевдоразметка имеет приоритет выше ручного обучения,
ручное обучение выше auto псевдоразметки, auto псевдоразметка выше auto обучения, а второстепенные ручные jobs идут после всех обычных. Auto jobs нельзя удалить или двигать
через endpoints очереди; снятие галочки отменяет соответствующие queued/running auto jobs. Если меняется версия
конкретного датасета, активные auto jobs предыдущей версии отменяются только для этого датасета и модели. Failed
auto attempt не ретраится до новой версии или снятия и повторного включения галочки.
Срочный поснимочный инференс редактора обгоняет queued jobs. Точный ключ дедупликации фиксирует основную сеть,
ревизию TIFF, effective inference-конфигурацию и версию алгоритма; повторные запросы возвращают существующий job,
а ошибочный job перезапускается только явно. Running training получает файловый
pause-request: на границе batch модель и optimizer state переносятся в CPU, CUDA освобождается, а job получает
`paused`. После завершения срочных jobs запрос снимается, тот же PID и MLflow-run продолжают обучение. Обычный
выполняющийся inference не прерывается.

При ручном запуске обучения оператор может включить штатный инференс по снимкам обучающего датасета. Опция
хранится как служебная часть задания и не попадает в train YAML. После успешного создания каждого результата
worker идемпотентно ставит обычный full pseudo-markup job через общий builder; ошибка постановки инференса не
меняет успешный статус уже завершённого обучения. Счётчик рядом с пунктом «Очередь» читает отдельный лёгкий
endpoint и показывает сумму `queued`, `running` и `paused`, а строка задания ведёт в тот же экран Job, что и
кнопка из результатов обучения. На экране задания обучения доступны переход к результатам его датасета
и открытие связанного запуска MLflow в новой вкладке; до появления ссылки кнопка MLflow недоступна.
Флаг `secondary_priority` также хранится только в служебной части задания и наследуется этой full-псевдоразметкой.
Второстепенный job запускается только при отсутствии разрешённых обычных jobs. При их появлении training
освобождает CUDA штатным batch-boundary pause, PyTorch inference сохраняет завершённые поснимочные результаты и
переносит модель в CPU между снимками, а Geoalert Compose между снимками выгружает модель из Triton. После
опустошения обычной очереди запрос паузы снимается и тот же процесс продолжает работу без повторной обработки
готовых снимков. Состояние `paused` в API одинаково для обучения и псевдоразметки.

Для active manual training очередь и страница Job открывают единый диалог остановки. Если локальный
`scratch/checkpoints/best.pt` уже создан, оператор может записать `stop-and-save-best.request`: API не завершает
процесс и не пишет MLflow, а конвейер обучения сам отбрасывает незавершённую эпоху, публикует чекпойнт лучшей по
F1 завершённой эпохи и завершает run со статусом `FINISHED`. Worker после exit code `0` создаёт обычный успешный
результат и сохраняет прежнюю семантику заказанного post-training inference. Альтернатива «без результата»
использует отмену с `SIGTERM` всей группе процессов и `KILLED` в MLflow. Остановка ожидает до пяти
секунд, затем отправляет `SIGKILL` оставшимся процессам и проверяет завершение ещё до двух секунд.
Временные данные и PID удаляются только после подтверждения; при ошибке задание сохраняется.
Worker проверяет также дочерние процессы после выхода лидера группы, чтобы следующий job не занял
GPU во время завершения предыдущего. Завершившиеся zombie-процессы не удерживают очередь.

Глобальное выключение автоматизации через `PUT /api/v1/automation/enabled` с `enabled=false` отменяет все active
auto jobs: queued rows уходят из очередей, running process получает SIGTERM, временная директория удаляется,
результаты получают `cancelled`, а известный MLflow run помечается как `KILLED`. При повторном включении worker
создает новые jobs по текущим правилам и версиям датасетов, а не восстанавливает старую очередь.

## Алгоритм работы и его особенности

Отдельный `next_gen4_consistency_v1` доступен в шаблонах и запуске SegFormer как профиль
v4 со штрафом согласованности, без изменения старых defaults. Дополнительный необязательный
параметр `train.diagnostic_checkpoint_interval_sec` сохраняет текущие временные срезы;
экспорт переносит `context_consistency` в metadata, не добавляя вычислений при инференсе.

`next_gen4_consistency_v2` доступен отдельно только для SMP SegFormer B0/B1/B2/B3;
старые шаблоны не переключаются. Экспорт дополнительно сохраняет точный маркер
`decoder_normalization`; нативная и ONNX-модель используют одну попиксельную LayerNorm.

`next_gen4_consistency_v3` отдельно доступен тем же SMP-архитектурам и наследует defaults
v2. Экспорт сохраняет двунаправленную `context_consistency` и прежнюю нормализацию;
исторические шаблоны и результаты не переключаются. Описание и новость объясняют
усреднение направлений, отсутствие градиента при двух неуверенных учителях и неизменный инференс.

`TrainingJobCreate.auto_test_f1_after_training: bool = True` позволяет отключить для
одного задания автоматический внешний F1 и оценки тестовых разметок по завершении;
`ui.auto_test_f1_after_training=false` наследуется продолжением в исходной конфигурации.
Полная псевдоразметка независимо управляется прежним флагом. Другие задания, данные,
назначенные тесты, ручные оценки и обязательная внутренняя validation/test не меняются.

HTTP проверяет сессию и работает с UI-БД через сервисный слой. Каталог синхронизируется с MLMarkup,
история сохраняется. Обучение выбирает шаблон модели и датасета; инференс — общий именованный шаблон,
назначенный классу. Без назначения создание псевдоразметки недоступно. Старые настройки перенесены.
Задания фиксируют
конфигурацию и входные данные; worker исполняет очереди, обновляет результаты и MLflow через фасады.
Продолжение обучения создаёт связанную новую сеть из сохранённых параметров и выбранного checkpoint.
Канопус использует нативный runner, ортофото — Geoalert/Triton; окно и профиль определяет checkpoint.
F1 использует версионированные настройки; экспорт фиксирует конфигурацию. Просмотрщики загружают
слои выбранного снимка, остальные сравнения считают фоном. Редактор хранит личные черновики в БД
и публикует согласованные изменения одним Git-коммитом. Новости выпускаются с кодом.
Подробные правила подготовки, очередей, инференса и редактора — в `docs/architecture.md`.
